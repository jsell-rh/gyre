## Findings

- [ ] **F1 (moderate): `attestation_level` claim omitted for the default no-compute-target spawn path — contradicts the code's own comment and identity-security.md, in the fail-open direction for the spec's example deny.** `crates/gyre-server/src/api/spawn.rs` (`spawn_agent_core`, the `mint_worker_scoped` call): `resolved_ct_entity.as_ref().map(|ct| match ct.target_type { Container => 3, Ssh => 2, Kubernetes => 1 })` yields `None` when no compute target is configured (no request `compute_target_id`, no workspace assignment, no tenant default) — i.e. the plain local-subprocess path every default deployment uses. The adjacent comment states "No target (None) is a plain local subprocess: level 1", and identity-security.md's Task-Scoped JWT Claims reference says every JWT minted by `POST /api/v1/agents/spawn` carries `attestation_level` (1=raw subprocess). One of the comment and the code is wrong; per the spec it is the code. Consequence: in default deployments, spawned workers carry no `attestation_level` claim, so `subject.attestation_level` is unset at evaluation and Deny policies keyed on it — e.g. the spec's own §Policy Examples `gate-approved-persona` (deny `gate_review` when `attestation_level < 3`) — silently do not match raw-subprocess agents, the least-attested class. (Allow policies keyed on the attribute fail closed, so only the Deny direction is exposed.) No test covers the no-target spawn path's claim content — `agent_jwt_persona_and_attestation_level_reach_live_evaluation` mints with explicit `Some(3)`/`Some(1)`, so the gap is invisible to the suite. Reproduce: spawn with no compute target on a default-config server, decode the minted worker JWT (`kv agent_tokens`), observe `attestation_level` absent. Remedy: map the no-target case to `Some(1)` (e.g. `resolved_ct_entity.as_ref().map_or(Some(1u8), |ct| ...)`) and add a test asserting the no-target spawn's token carries `attestation_level: 1`.
