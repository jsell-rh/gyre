## Findings

- [-] **F1 (moderate, code): parent-id leak in `resource.id` on merge-requests- and agents-parented child routes.** `extract_path_attributes` (abac_middleware.rs:620-700) suppresses the parent `:id` only for patterns under `/api/v1/workspaces/` or `/api/v1/repos/`. On `/api/v1/merge-requests/:id/gates` (type `gate`), `/api/v1/merge-requests/:id/dependencies` (type `dependency`), and `/api/v1/agents/:id/messages` (type `message`) — collection routes with no `{resource_type}_id` param — the else-branch sets `resource.id` to the PARENT MR/agent id. This is the exact defect class this same change fixed for the repos prefix (d779f1e89 + regression tests); §Attributes defines `resource.id` as the addressed entity, and the function's own doc comment states the `:id` on a parent-scoped child route "is the parent, not the addressed entity, so no resource.id is fabricated from it". Consequence: policies keyed on `resource.id` for gate/dependency/message types evaluate against the parent id — an `Allow` keyed on an MR id with `resource_types: ["gate"]` grants that MR's gate operations, and a Deny keyed on a real gate id never fires on the MR collection route. Deterministic reproduction (unit, mirrors the candidate's own repos-prefix test): `extract_path_attributes(&mut ctx, "/api/v1/merge-requests/:id/gates", "/api/v1/merge-requests/mr-9/gates", "gate")` → `resource.id == Some("mr-9")`, expected `None`. Repair: generalize the guard to the `/api/v1/merge-requests/` and `/api/v1/agents/` parent prefixes (or to "any route whose `:id` names an entity of a different type than `resource_type`"), and extend `path_attributes_repos_parented_child_routes` plus one live middleware test to cover them, mirroring the repos-prefix coverage.
