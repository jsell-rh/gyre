## Findings

- **F1 (moderate, code + coverage honesty): `resource.id` is never populated on `:path`-addressed spec routes.** `extract_path_attributes` derives `resource.id` only from an `:id` or `{resource_type}_id` path param; every `/api/v1/specs/:path*` route has neither, and `extract_entity_attributes`' spec arm sets owner/approval_status/repo_id/workspace_id but not `resource.id`. The spec's §Attributes table defines `resource.id` (source "Request path") with the example `system/identity-security.md` — a spec path — so the table's own canonical example is unimplemented for that resource type: no policy can condition on the addressed spec's identity (a resource-keyed Deny like the §Policy Examples pattern is inexpressible for specs). It fails closed, so it is a capability gap, not a security hole. Probe (temporary test `review_probe_spec_path_resource_id`, added then reverted): `extract_path_attributes(ctx, "/api/v1/specs/:path", "/api/v1/specs/system%2Fdesign.md", "spec")` leaves `resource.id` unset — evidence `probe-spec-resource-id.log`. Compounding: coverage row 3 (§Attributes, marked `implemented`) claims "resource id/workspace_id/repo_id from the request path" and discloses `resource.team`/`resource.visibility` as unpopulated but not this — the same overstatement class the round-2 review flagged. Remedy: populate `resource.id` from the percent-decoded `:path` on spec routes with a live-evaluation test, or amend the coverage note to record it as unpopulated (the team/visibility precedent) if the omission is deliberate.
- **F2 (minor, doc/code divergence): `normalize_agent_jwt_attributes` claims "Never overwrites an attribute already present in the context" but sets unconditionally.** All three setters are bare `ctx.set`/`set_number` with no `contains_key` guard. No exploitable impact today — it runs only for agent subjects, immediately after the insert-only `merge_agent_jwt_claims` on the same claims object, so it can only overwrite values defined by the same verified token — but the stated invariant is false as written, and it is precisely the invariant the round-2 anti-spoofing fix documents. A future reordering would silently violate it with no test catching the divergence. Remedy: add the guard the doc promises, or fix the comment.
