Findings:

- [x] [process-revision-complete] **F1 (major): atomic-group post-merge failure recovers only the LAST member — the rest of the group stays `Merged` on red main.** Spec §6: on post-merge gate FAIL, "2. Forge creates a REVERT commit undoing the merge … 5. Original MR is re-opened with status `Reverted` … 6. Author agent receives RevertNotification … 7. Task created … 8. The MR's gate results are invalidated". An atomic group lands N merge commits as one transactional unit (`merge-dependencies.md` §Atomic Group Rules: "merges all members in dependency order with no interleaving"), so post-merge failure means the whole unit must be undone. But `merge_atomic_group` at HEAD resolves the branch HEAD and calls `handle_post_merge_failure(state, &repo, last_mr, …)` for `merged_entries.last()` only (`merge_processor.rs:1118-1140`): one revert commit (which itself only undoes the final merge commit — earlier members' commits remain in history), one MR → `Reverted`, one notification, one remediation task, one gate-result invalidation. The other N−1 members remain `Merged` with no revert, no notification, no invalidation, while main is red and the queue is paused. The prior fix commit on this task's branch (`107de4fa`, "fix(merge): run post-merge validation and pause check on atomic-group merges (task-095)") implemented `recover_atomic_group_from_post_merge_failure` — reverting every group merge commit newest-first and running recovery steps 4–7 per member — but that function was dropped when the work was squashed into `03dc80a7` (`git diff 107de4fa 03dc80a7 -- crates/gyre-server/src/merge_processor.rs` removes `recover_atomic_group_from_post_merge_failure`, `group_merge_shas`, and the atomic-path pause check; main carries the full version as commit `86c7d382`). No test covers an atomic group hitting a failing post-merge gate.
- [x] [process-revision-complete] **F2 (major): the five new recovery endpoints are absent from the ABAC route registry — any authenticated agent can pause/resume queues, revert merged MRs, and rewrite post-merge gate configs, across tenants.** Routes registered at `api/mod.rs:166-175` (`/repos/:id/status`, `/repos/:id/queue/pause`, `/repos/:id/queue/resume`, `/repos/:id/revert/:mr_id`, `/repos/:id/post-merge-gates` GET+PUT). The ABAC `ResourceResolver` has entries for neighboring repos routes (`abac_middleware.rs:100-127`) but none for these five; `resolve()` is an exact-pattern match (`:470-472`) and unmatched patterns fall through with NO policy evaluation (`:769-773`: `None => return next.run(req).await`). The fallthrough comment claims "check-api-auth.sh catches missing entries at CI time" (`:767-768`) — it does not: the script only greps `lib.rs` for the three middleware layers and checks per-handler extractors on routes mounted OUTSIDE the api router (`scripts/check-api-auth.sh` Check 1/Check 2); it never compares registered routes against the resolver. The handlers (`api/recovery.rs:71-322`) take only `State`/`Path`/body — no `AuthenticatedAgent` extractor, no tenant/workspace scoping. This violates the ABAC model's stated default-deny posture ("Default deny at tenant level catches everything not explicitly allowed", `specs/system/abac-policy-engine.md:266`) for exactly the most destructive operations the protocol adds: unauthenticated-by-policy revert and gate-config rewrite.
- [x] [process-revision-complete] **F3 (major): the author AGENT never receives a RevertNotification via MCP — spec step 6 unmet.** Spec §6 step 6: "Author agent receives RevertNotification via MCP". `notify_mr_reverted` (`notifications.rs:186-235`) resolves the author agent's `spawned_by` USER and creates an inbox `Notification` (NotificationType::MrReverted, `:227`) for that user — and silently `return`s when `spawned_by` is `None` (`:201-205`), so agents with no spawning user get no notification at all. The message-bus kind `MessageKind::MrReverted` exists (`gyre-common/src/message.rs:130`, Event tier) but no code ever emits it (the only producers/consumers of `MrReverted` are its serde definitions; grep across `gyre-server` finds zero `emit_event`/bus sends). The MCP SSE stream relays the message bus (`mcp.rs:3050-3065`), so without a bus emission there is no MCP delivery path. The codebase's own pattern shows the intent: the pause path emits `MergeQueuePaused` on the bus (`merge_processor.rs:75-85`); the revert path emits nothing.
- [x] [process-revision-complete] **F4 (moderate): `&combined[..4096]` byte-index slice can panic on multibyte UTF-8 in gate output.** `run_post_merge_command` (`merge_processor.rs:165-169`): `String::from_utf8_lossy` output sliced at byte 4096 — if byte 4096 falls inside a multibyte character (any CI output containing non-ASCII: compiler diagnostics, test runners, localized tools), `&combined[..4096]` panics ("byte index 4096 is not a char boundary"). This runs inside the merge-processor task on every post-merge gate execution, so one verbose non-ASCII gate output aborts the queue loop. Fix is mechanical: truncate on char boundary (`combined.char_indices().take_while(|(i,_)| *i <= 4096)`) or use `floor_char_boundary`-equivalent.
- [x] [process-revision-complete] **F5 (major): duplicate Diesel migration version `20260930000051` — the `post_merge_gates` table is never created on fresh databases; the repo's own guard test FAILS on this tree.** Two tracked migration directories share prefix `000051`: `2026-09-30-000051_orchestrator_type` (task-093, ancestor of this HEAD) and `2026-09-30-000051_post_merge_gates` (this commit). Diesel derives the migration version from everything before the first `_` minus dashes — both map to `20260930000051`, and only one migration runs per version (alphabetically `…_orchestrator_type` wins). Consequence: on any fresh/deployed database the `post_merge_gate_configs` table is never created and every post-merge-gate lookup fails at runtime — the entire §6 feature is dead on fresh installs. Hard evidence: the guard test `no_duplicate_migration_version_prefixes` (`gyre-adapters/src/sqlite/mod.rs:274-306`) FAILED when run on this tree: "Duplicate Diesel migration versions detected — only one will run per version: version 20260930000051: [2026-09-30-000051_orchestrator_type, 2026-09-30-000051_post_merge_gates]". Main has already renumbered the colliding migration (`e4a1cb6f` "fix(migrations): renumber orchestrator_type to 000052 after version-prefix collision"); this tree must apply the same renumber (or take the next free prefix).
- [x] [process-revision-complete] **F6 (minor): escalation message reads "revert still failing after revert".** The `Err` branch of `handle_post_merge_failure` calls `escalate_revert_failure(…, "revert", …)` (`merge_processor.rs:341-348`), and the fixed template is `"{gate_name} still failing after revert"` (`:395-397`) → "Post-merge recovery failed for MR X: revert still failing after revert". The branch means the revert commit could not be created at all; the message should say that (it does pass the real error in `output`, but the title is misleading). Cosmetic; humans triaging AgentEscalation notifications see a self-contradicting title.
- [x] [process-revision-complete] **F7 (minor): revert count is incremented before the revert is attempted — the circuit breaker counts failed revert attempts as reverts.** `handle_post_merge_failure` increments the counter before calling `git_ops.revert_commit` (`merge_processor.rs:242-257`), and the `Err` branch also checks `revert_count >= 3` (`:350-352`). Spec: "If the same MR is reverted 3 times" — a merge that is never successfully reverted (e.g. revert conflict) still consumes circuit-breaker budget, so an MR reverted twice with one failed revert attempt is permanently removed from the queue without ever having been reverted 3 times. Increment on successful revert (or count only the `Ok` branch) to match the spec wording.
- [x] [process-revision-complete] **F8 (minor): no test exercises real git revert logic.** All merge-processor recovery tests run against `mem.rs`'s `NoopGitOps::revert_commit`, which returns `Ok("0000…")` unconditionally (`mem.rs:145-153`), and the "reverted HEAD" the re-run gates are tested against is therefore fictional — the tests validate orchestration, not the git-level revert (3-way merge, revert-conflict path, revert of a merge commit) that the spec's step 2–3 depend on. `git2_ops.rs`'s real `revert_commit` has no coverage in this change. Low severity given F1 dominates the atomic-group gap, but the conflict branch (`Err` → escalation) is only reachable via a fake that never errors.

### Round 3 findings

- **R3-F1 (major): manual revert endpoint reverts the wrong commit — the current target-branch HEAD, not the MR's merge commit.** `revert_mr` (`api/recovery.rs:274-286`) resolves "the merge commit" as `refs/heads/{target_branch}` HEAD with the comment "the merge landed it". That is only the MR's merge commit if no other merge landed since. After any subsequent merge (or manual revert — each revert is itself a new HEAD), `POST /repos/:id/revert/:mr_id` reverts the **latest** commit on the branch, then marks the **named** MR `Reverted` and records the wrong revert SHA against it. Root cause: `MergeRequest` persists no `merge_commit_sha` (`gyre-domain/src/merge_request.rs` — only `revert_commit_sha` exists), so the MR's own merge commit is not recoverable from the MR row; `merge_processor` receives `merge_commit_sha` in-flight (`Ok(MergeResult::Success { merge_commit_sha })`, `merge_processor.rs:1483`) but never persists it. Spec §6 CLI requires "Manual revert of a **specific** MR" — with current-HEAD semantics this is unimplementable for any MR that is not the most recent merge. Compounding: the handler does not verify `mr.repository_id == repo.id` (a path-repo/MR-repo mismatch reverts repo A's HEAD while marking repo B's MR), and manual reverts bypass the circuit breaker entirely (`revert_mr` calls `apply_revert_side_effects` directly, never `increment_revert_count`). **Untested**: `api/recovery.rs` (385 lines) contains no test module — zero coverage for `revert_mr`, `repo_status`, pause/resume, and the gates endpoints.

- **R3-F2 (moderate): the "re-open" semantics of spec step 5 are unimplemented, leaving the circuit breaker unreachable in the intended workflow.** Spec step 5: "Original MR is **re-opened** with status `Reverted`". In the implementation `Reverted` is terminal (`transition_status`, `gyre-domain/src/merge_request.rs:130-148`, has no `Reverted → Open` edge — consistent with the enum comment, so this is partly spec-internal tension), and the remediation task created by step 7 instructs the agent to "Re-do the work on a **fresh branch** and re-open **a merge request**" (`merge_processor.rs`, remediation-task body) — i.e. a new MR id. The revert count is keyed by MR id (`kv revert_counts`/mr_id), so a resubmission per the remediation instruction starts at 0 and the "same MR reverted 3 times" condition can never accumulate across the fix-and-resubmit cycle the protocol itself prescribes. The only path that accumulates is re-enqueueing the **same** Reverted MR — which nothing prevents (`enqueue`, `api/merge_queue.rs:60-80`, does not validate MR status, and `process_next`'s selection loop checks dependencies/gates/pause/atomic-group but not MR status), but that path both contradicts the remediation instruction and means a `Reverted` MR can be silently re-merged. Either the counter must key on something stable across resubmission (e.g. source-branch/spec linkage), or a re-open path with count carry-over must exist; spec item 3 of the Circuit Breaker ("the spec it references may need revisiting") is likewise unimplemented and `enqueue`'s missing status validation is what "removed from the merge queue permanently" silently relies on.

- **R3-F3 (minor): `repo_status` `main_green` fails open on ref-resolution failure.** `repo_status` (`api/recovery.rs:224-235`) computes `head_sha = resolve_ref(...).unwrap_or_default()`; on resolution failure the empty string goes to `run_post_merge_gates` → `create_detached_worktree(repo, "", "")` fails → the gate falls back to running commands in the **server cwd** (the R2-1-accepted fallback) → `cargo test` may run against the gyre-server tree and the endpoint returns `main_green: true`. This is the exact value the spec's CLI surfaces for the human's "is main green / may I resume the queue" decision; a fail-open default on the branch-health signal inverts the protocol's safety posture (the queue-pause mechanism elsewhere is deliberately fail-closed). Resolution failure should yield `main_green: false` or an explicit error field, not a green reading from an unrelated tree.

- **R3-F4 (process): review-record drift — `5aaded21` is task-095-labeled surface invisible to review scoping.** `5aaded21` (+880 lines: circuit breaker, REST recovery surface, CLI) is absent from task-095's `commits:` frontmatter (list has only `7c723298`, `86c7d382`, `3a9b11f6`), so a scope-following reviewer would never examine it — this round only caught it because the R2 scope note's "not implemented on main" claim was re-checked against HEAD. Consequences already materialized: the R2 scope note is now factually wrong, and task-096 remains `not-started` declaring ownership of surface `5aaded21` already delivered (duplicate-ownership / conflicting-redit risk). Cosmetic sub-finding folded here: the five recovery routes are registered **twice** in the ABAC resolver (`abac_middleware.rs:107-111` and `:129-137`); `resolve()` uses first-match, so the second block is dead — including its `post-merge-gates → "gate"` mapping, meaning that route is actually evaluated as resource type `"repo"`. Fix: frontmatter must list `5aaded21`; task-096 must be re-scoped to the remaining UI work (or closed with a note); duplicate resolver entries removed.
