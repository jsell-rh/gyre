Findings:

- [ ] **F1 (major): atomic-group post-merge failure recovers only the LAST member — the rest of the group stays `Merged` on red main.** Spec §6: on post-merge gate FAIL, "2. Forge creates a REVERT commit undoing the merge … 5. Original MR is re-opened with status `Reverted` … 6. Author agent receives RevertNotification … 7. Task created … 8. The MR's gate results are invalidated". An atomic group lands N merge commits as one transactional unit (`merge-dependencies.md` §Atomic Group Rules: "merges all members in dependency order with no interleaving"), so post-merge failure means the whole unit must be undone. But `merge_atomic_group` at HEAD resolves the branch HEAD and calls `handle_post_merge_failure(state, &repo, last_mr, …)` for `merged_entries.last()` only (`merge_processor.rs:1118-1140`): one revert commit (which itself only undoes the final merge commit — earlier members' commits remain in history), one MR → `Reverted`, one notification, one remediation task, one gate-result invalidation. The other N−1 members remain `Merged` with no revert, no notification, no invalidation, while main is red and the queue is paused. The prior fix commit on this task's branch (`107de4fa`, "fix(merge): run post-merge validation and pause check on atomic-group merges (task-095)") implemented `recover_atomic_group_from_post_merge_failure` — reverting every group merge commit newest-first and running recovery steps 4–7 per member — but that function was dropped when the work was squashed into `03dc80a7` (`git diff 107de4fa 03dc80a7 -- crates/gyre-server/src/merge_processor.rs` removes `recover_atomic_group_from_post_merge_failure`, `group_merge_shas`, and the atomic-path pause check; main carries the full version as commit `86c7d382`). No test covers an atomic group hitting a failing post-merge gate.
- [ ] **F2 (major): the five new recovery endpoints are absent from the ABAC route registry — any authenticated agent can pause/resume queues, revert merged MRs, and rewrite post-merge gate configs, across tenants.** Routes registered at `api/mod.rs:166-175` (`/repos/:id/status`, `/repos/:id/queue/pause`, `/repos/:id/queue/resume`, `/repos/:id/revert/:mr_id`, `/repos/:id/post-merge-gates` GET+PUT). The ABAC `ResourceResolver` has entries for neighboring repos routes (`abac_middleware.rs:100-127`) but none for these five; `resolve()` is an exact-pattern match (`:470-472`) and unmatched patterns fall through with NO policy evaluation (`:769-773`: `None => return next.run(req).await`). The fallthrough comment claims "check-api-auth.sh catches missing entries at CI time" (`:767-768`) — it does not: the script only greps `lib.rs` for the three middleware layers and checks per-handler extractors on routes mounted OUTSIDE the api router (`scripts/check-api-auth.sh` Check 1/Check 2); it never compares registered routes against the resolver. The handlers (`api/recovery.rs:71-322`) take only `State`/`Path`/body — no `AuthenticatedAgent` extractor, no tenant/workspace scoping. This violates the ABAC model's stated default-deny posture ("Default deny at tenant level catches everything not explicitly allowed", `specs/system/abac-policy-engine.md:266`) for exactly the most destructive operations the protocol adds: unauthenticated-by-policy revert and gate-config rewrite.
- [ ] **F3 (major): the author AGENT never receives a RevertNotification via MCP — spec step 6 unmet.** Spec §6 step 6: "Author agent receives RevertNotification via MCP". `notify_mr_reverted` (`notifications.rs:186-235`) resolves the author agent's `spawned_by` USER and creates an inbox `Notification` (NotificationType::MrReverted, `:227`) for that user — and silently `return`s when `spawned_by` is `None` (`:201-205`), so agents with no spawning user get no notification at all. The message-bus kind `MessageKind::MrReverted` exists (`gyre-common/src/message.rs:130`, Event tier) but no code ever emits it (the only producers/consumers of `MrReverted` are its serde definitions; grep across `gyre-server` finds zero `emit_event`/bus sends). The MCP SSE stream relays the message bus (`mcp.rs:3050-3065`), so without a bus emission there is no MCP delivery path. The codebase's own pattern shows the intent: the pause path emits `MergeQueuePaused` on the bus (`merge_processor.rs:75-85`); the revert path emits nothing.
- [ ] **F4 (moderate): `&combined[..4096]` byte-index slice can panic on multibyte UTF-8 in gate output.** `run_post_merge_command` (`merge_processor.rs:165-169`): `String::from_utf8_lossy` output sliced at byte 4096 — if byte 4096 falls inside a multibyte character (any CI output containing non-ASCII: compiler diagnostics, test runners, localized tools), `&combined[..4096]` panics ("byte index 4096 is not a char boundary"). This runs inside the merge-processor task on every post-merge gate execution, so one verbose non-ASCII gate output aborts the queue loop. Fix is mechanical: truncate on char boundary (`combined.char_indices().take_while(|(i,_)| *i <= 4096)`) or use `floor_char_boundary`-equivalent.
- [ ] **F5 (major): duplicate Diesel migration version `20260930000051` — the `post_merge_gates` table is never created on fresh databases; the repo's own guard test FAILS on this tree.** Two tracked migration directories share prefix `000051`: `2026-09-30-000051_orchestrator_type` (task-093, ancestor of this HEAD) and `2026-09-30-000051_post_merge_gates` (this commit). Diesel derives the migration version from everything before the first `_` minus dashes — both map to `20260930000051`, and only one migration runs per version (alphabetically `…_orchestrator_type` wins). Consequence: on any fresh/deployed database the `post_merge_gate_configs` table is never created and every post-merge-gate lookup fails at runtime — the entire §6 feature is dead on fresh installs. Hard evidence: the guard test `no_duplicate_migration_version_prefixes` (`gyre-adapters/src/sqlite/mod.rs:274-306`) FAILED when run on this tree: "Duplicate Diesel migration versions detected — only one will run per version: version 20260930000051: [2026-09-30-000051_orchestrator_type, 2026-09-30-000051_post_merge_gates]". Main has already renumbered the colliding migration (`e4a1cb6f` "fix(migrations): renumber orchestrator_type to 000052 after version-prefix collision"); this tree must apply the same renumber (or take the next free prefix).
- [ ] **F6 (minor): escalation message reads "revert still failing after revert".** The `Err` branch of `handle_post_merge_failure` calls `escalate_revert_failure(…, "revert", …)` (`merge_processor.rs:341-348`), and the fixed template is `"{gate_name} still failing after revert"` (`:395-397`) → "Post-merge recovery failed for MR X: revert still failing after revert". The branch means the revert commit could not be created at all; the message should say that (it does pass the real error in `output`, but the title is misleading). Cosmetic; humans triaging AgentEscalation notifications see a self-contradicting title.
- [ ] **F7 (minor): revert count is incremented before the revert is attempted — the circuit breaker counts failed revert attempts as reverts.** `handle_post_merge_failure` increments the counter before calling `git_ops.revert_commit` (`merge_processor.rs:242-257`), and the `Err` branch also checks `revert_count >= 3` (`:350-352`). Spec: "If the same MR is reverted 3 times" — a merge that is never successfully reverted (e.g. revert conflict) still consumes circuit-breaker budget, so an MR reverted twice with one failed revert attempt is permanently removed from the queue without ever having been reverted 3 times. Increment on successful revert (or count only the `Ok` branch) to match the spec wording.
- [ ] **F8 (minor): no test exercises real git revert logic.** All merge-processor recovery tests run against `mem.rs`'s `NoopGitOps::revert_commit`, which returns `Ok("0000…")` unconditionally (`mem.rs:145-153`), and the "reverted HEAD" the re-run gates are tested against is therefore fictional — the tests validate orchestration, not the git-level revert (3-way merge, revert-conflict path, revert of a merge commit) that the spec's step 2–3 depend on. `git2_ops.rs`'s real `revert_commit` has no coverage in this change. Low severity given F1 dominates the atomic-group gap, but the conflict branch (`Err` → escalation) is only reachable via a fake that never errors.

### New findings — main's integrated implementation

- [ ] **R2-1 (major): post-merge gates never execute against `head_sha` — spec §6 "It runs against the new HEAD of the default branch after the merge commit lands" (platform-model.md:492) is not met, and the task's own acceptance criterion "Post-merge gates run after merge against new HEAD" is only nominally satisfied.** `run_post_merge_gates` (`gate_executor.rs:955-1009`) receives `head_sha` but **never uses it to select or prepare a checkout** — `head_sha` appears only in the final log line (`:1007`). Gate commands run with `cwd` = the **first** entry of `git_ops.list_worktrees(repo.path)` (`:970-977`, `.into_iter().next()`), with two failure modes:
  1. *Arbitrary stale worktree.* `list_worktrees` (`git2_ops.rs:394-415`) returns every registered worktree (the main checkout plus agent worktrees) in `git worktree list --porcelain` order; `next()` takes the first. Worktrees are created per agent branch (`create_worktree`, `git2_ops.rs:319+`), so the chosen directory is typically an agent's feature-branch checkout at an unrelated commit. Nothing checks it out to `head_sha` first (grep for checkout/update in `run_post_merge_gates` and the merge path: none). Gates validate the wrong tree: a broken merge can pass (gate runs against old/green code) and a good merge can fail (gate runs against a stale WIP checkout) — the latter **triggers a spurious revert of a correct merge**.
  2. *Server cwd fallback.* When no worktree exists, commands run with `cwd: None` = the **server process's working directory**. Server repositories are created **bare** (`api/repos.rs:167` → `init_bare`, `git2_ops.rs:63-70`), so a repo with no worktrees has no checkout at all; `cargo test` et al. execute against the gyre-server source tree (or fail confusingly), never against the merged repo. The doc comment (`gate_executor.rs:952-954`) says this "match[es] pre-merge gates" — pre-merge gates run before checkout exists in this design, but post-merge validation is *defined* by running against the new HEAD; "matching pre-merge" concedes the point.
  Both paths also apply to the recovery re-run on the reverted HEAD (`merge_processor.rs:1775`, `:1974`) — same wrong-directory execution.
  *Tests don't catch this because the mem test double's `list_worktrees` returns `Ok(vec![])` (`mem.rs:101-103`, `:246-248`), so every recovery test runs gates with `true`/`false` in the server cwd — the worktree-selection code path has zero coverage.* Fix direction: create/detach a dedicated worktree (or use a temp clone) checked out to `head_sha`, run gates there, clean up — the `head_sha` parameter is already plumbed and currently dead weight.

- [ ] **R2-2 (moderate): fast-forward merges revert the wrong tree.** `merge_branches` (`git2_ops.rs:275-286`) fast-forwards when target is ancestor of source and reports the branch tip as `merge_commit_sha`. The recovery protocol then calls `revert_commit(sha)` on that commit, whose semantics are "restore parent(0)'s tree on the branch tip" (`git2_ops.rs:633-635`). For an FF "merge", the reported SHA is the source branch's tip commit — an ordinary commit whose parent(0) is the previous *source-branch* commit, **not** the pre-merge default-branch state. The revert therefore resets the default branch's tree to the feature branch's second-to-last commit: the merged change is undone, but the "reverted HEAD" is not the pre-merge main — it is a tree that never existed on the default branch, and the recovery re-run then validates that fictional tree. No test covers revert-after-FF (`test_merge_branches_fast_forward` at `:938` tests merging only). Fix direction: either skip FF in `merge_branches` (always create a merge commit — `--no-ff` semantics, which also matches the spec's "after the merge commit lands" wording), or have the recovery path record the pre-merge default-branch tip and reset to it instead of relying on parent(0).

- [ ] **R2-3 (minor): `revert_mr_id` stores a commit SHA in an MR-id field.** `apply_revert_side_effects` (`merge_processor.rs:1825`) does `let revert_mr_id = Id::new(revert_sha.to_string())` — the domain field `MergeRequest::revert_mr_id` (`gyre-domain/src/merge_request.rs:157`), named and documented as a reference to the revert *MR*, is populated with a git commit SHA. The code comment (`:1822-1824`) acknowledges no revert MR object is created. Consequence: any future consumer joining `revert_mr_id` against the merge_requests table (the field's evident contract) gets a silent miss; API responses expose the SHA under an MR-id key. Cosmetic-to-contract smell; either rename the field to `revert_commit`/add a sibling, or create a real revert MR and use its id.
