## Findings

- [ ] **F1 (major, code): the Ralph-loop re-spawn failure path does not follow the Phase 7 spawn-failure policy, and leaves the re-spawn JWT behind.** `ralph_loop.rs`, `on_gates_failed` step 5 → `relaunch_agent_session` error handler. agent-runtime.md §1 Phase 7: *"Spawn failure: If `ComputeTarget::spawn_process()` fails … Retries up to 3 times with exponential backoff (1s, 5s, 30s). If all retries fail: task marked Blocked, orchestrator notified, priority-1 notification created for workspace admins."* The re-spawn is a `spawn_process()` call and the policy is not path-scoped — but a single failed re-spawn launch immediately blocks the task: (a) no 3× backoff retry; (b) no priority-1 `ComputeTargetUnavailable` notification for workspace admins (only the `TaskBlocked` orchestrator message); (c) the freshly-minted re-spawn JWT is left in the `agent_tokens` KV bucket for the now-`Failed` agent — unlike the max-iterations path and the scheduler's `teardown_failed_spawn`, which both `kv_remove` it — and agent JWT auth validates token-presence + signature, not agent status (auth.rs §2/2.5), so a terminal Failed agent can still authenticate until the 5-minute default TTL expires. The code comment on this path claims it "follows the Phase 7 spawn-failure policy"; it does not. Reproduce: make the workspace's compute target unreachable, drive one gate failure (`on_gates_failed` with the ceiling not reached) → observe task Blocked after ONE launch attempt, no admin notification, `kv_get("agent_tokens", agent_id)` still returns the fresh token. Remedy: route re-spawn launch failures through the same retry/notification policy as the scheduler path (or reuse `retry_worker_spawn`), and `kv_remove` the token on the terminal failure path.
- [ ] **F2 (minor, code): claimed Implementation tasks have no crash recovery.** `spawn_implementation_workers` claims Backlog→InProgress, but the stale-claim recovery in `scheduler_run_once` deliberately skips Implementation tasks (first loop `continue`s on non-Delegation/Coordination) and the worker scan only selects Backlog. A server crash during the up-to-36s spawn-retry backoff — when the last attempt's agent is already `Failed`, so the stale-agent detector has no Active agent to reap into Blocked — strands the task InProgress permanently. The orchestrator path solved this exact class with stale-claim recovery; the worker path needs the same (e.g. let the stale recovery release or re-queue stale InProgress Implementation claims whose agent is not Active).
- [ ] **F3 (minor, test): process-global env pollution.** `ralph_loop.rs` `gate_failure_respawns_agent_with_fresh_context` sets `GYRE_AGENT_COMMAND=/bin/true` via `std::env::set_var` with no cleanup; every later test in the same lib-test binary spawns `/bin/true` as its agent command (launch behavior is order-dependent). Benign for the current suite (launches are best-effort in the affected tests) but fragile. Remedy: `remove_var` at test end or a one-shot guard, per the repo's test-hygiene conventions.
- [ ] **F4 (verification): `cargo test --all` — an explicit acceptance criterion — has no passing evidence.** The only full run (prior verification, `checks.sh`) failed at compile on E0063; `096cd9bd6` fixed it but the repair note claims only `cargo check --all-targets`. Compile-level verification passes here; runtime execution of the server suites (list above) is deferred to the independent verifier and must pass before this task's coverage rows (agent-runtime.md §1 rows 7–11, all marked `implemented` on this candidate) can be trusted.
