## Verified working (no material findings)

- **Tenant scope on the registry** — `MetaSpecScope::Tenant` with the tenant id in `scope_id` (mirrors the Workspace design; enum stays a plain string column). Migration `2026-11-07-000059` widens the `meta_specs.scope` CHECK via a portable three-table rebuild (children dropped before the parent, parents copied before children — re-read the up.sql; portable on SQLite and PG per the migration-portability gate) and creates `tenant_meta_spec_sets`. Creation validates the scope tenant exists; `scope=Tenant&scope_id=` listing enforces caller-tenant containment (`list_meta_specs_registry`).
- **Tenant set binding** — `TenantMetaSpecSetRepository` port (get/upsert/delete) with mem, SQLite, and PostgreSQL adapters; separate table/store from workspace sets so a shared id string cannot shadow across kinds. `GET/PUT /api/v1/tenants/{id}/meta-specs/set`: Admin-only + caller-tenant containment in the handler, route registered in the ABAC resolver (`abac_middleware.rs:432`, resource `meta_spec`), documented in api-reference.
- **Inheritance with override** — `resolve_effective_meta_spec_set` merges tenant defaults under workspace overrides (workspace pin wins; a persona key rebound by the workspace drops the tenant pin of that path; `workspace_overrides_path` is exactly consistent with `merge_meta_spec_sets`, so "not overridden" always means "inherits the tenant pin" — the consistency claim in the doc comment is real, checked case by case). Every consumer resolves the effective set: workspace set GET, `compute_meta_spec_set_sha` (re-serialization is byte-identical to the stored canonical JSON for tenant-less workspaces — base hashed the stored JSON, and sets are written by `serde_json::to_string` of the same struct, so no false drift on upgrade), blast radius (reason `tenant_inheritance` vs `workspace_binding`, cross-tenant workspaces excluded — test asserts all four shapes), preview blast radius, and the `meta_spec_changed` fan-out.
- **Per-workspace reconciliation (§8 steps 1–3)** — `run_tenant_reconciliation` lists the tenant's workspaces, filters changed paths to those the tenant set actually pins (unbound change → empty blast radius, logged), skips overriders, and runs one §6 `run_reconciliation` wave per non-overriding workspace — which composes with task-157's rollout policies (each workspace's policy applies individually). The override gate fails closed: a workspace whose set cannot be read (storage error / corrupt JSON) is skipped with `workspaces_skipped_error`, never decoded as "no overrides" (mutation A proves the test kills the fail-open form). Triggers: tenant-set PUT path-diff (removals are not triggers) and approval of a Tenant-scoped registry entry; the set-PUT trigger has a killing test (mutation B).

Only the force power is containment-gated, which is the right split (see observations below on the pre-existing registry governance model).
