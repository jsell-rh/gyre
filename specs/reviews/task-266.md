## Minor (non-blocking, recorded for completeness; traces in /tmp/stage/review-evidence/minor-observations-code-trace.md)

- PATCH `remove` whose path filter is not of the form `value eq "..."` (e.g. `members[display eq "Bob"]`) falls back to the op value (typically absent → empty) and removes ALL members — vs RFC 7644 §3.5.2.2, which removes only matching values. The implemented and documented contract is the canonical `value eq` form (used by Okta/Entra/Keycloak) and is tested; the deviation is reachable only by a SCIM-token holder sending an undocumented filter form, and its failure direction is revocation (deny), not privilege grant. Recommendation for a follow-up: return 400 (invalidPath) or no-op on an unparseable filter instead of the remove-all fallback.
- Idempotent POST create on an existing externalId ignores the pushed members and returns the stored resource — identical to the pre-existing Users-surface contract (scim_create_user) and documented in api-reference.md; an IdP retry that includes members on a duplicate create will not apply them (IdPs reconcile via PUT/PATCH).
- `ScimGroupRepository::replace_members` is implemented by all three adapters but unused by handlers (the PUT path diffs via add/remove so effects run per member). Port-completeness, not dead contract enforcement.
- Pre-existing at base (not this candidate): two migrations share sequence 000067 (`2026-11-13-000067_user_manager_id`, `2026-11-14-000067_agent_sessions`); check-migration-versions passes at both base and candidate, and the candidate's 000068 is the next unused number.
