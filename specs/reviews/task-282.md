## Non-blocking observations (pre-existing classes, recorded for a future hardening task — not introduced by this candidate)

- The flat READ routes (`deps/graph`, `deps/stale`, `deps/breaking`) reuse handler cores that list across all tenants with no caller-tenant filter, and the builtin tenant-isolation Deny fires only when `resource.tenant_id` resolves (it does not on flat paths), while the role-band Allow policies carry no tenant condition — so a cross-tenant Developer-role caller can read these lists. This exposure is identical on the pre-existing `/api/v1/dependencies/graph` (registered the same way) and strictly worse on `/api/v1/dependencies/stale` and `/breaking` (fully exempt from ABAC). Task-282 was explicitly scoped to serve the spec paths "backed by the real handler cores" and did not worsen the posture (the new stale/breaking routes gain middleware evaluation the old ones never had). The same applies to `?workspace={id}` accepting another tenant's workspace id (the dedicated workspace route is exempt and behaves identically).
- `add_manual_dependency` does not check the TARGET repo's tenant (a same-tenant caller can declare an edge pointing at another tenant's repo) — exact parity with the existing `add_dependency` core, which checks neither endpoint; the new handler is strictly stricter (source containment + token-scope checks). Cross-tenant edges cannot be created by a cross-tenant caller.
