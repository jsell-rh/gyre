### Findings

- [BLOCKING] **F1 (code/tests, `crates/gyre-server/src/api/preview_envs.rs`): the candidate's server test target does not compile — 21 errors in the try-it test module.** `cargo check -p gyre-server --tests` → exit 101. The test module never imports `gyre_common::Id` (the parent's `use` does not propagate into `mod tests`), passes `Some(sha())` (`String`) where `Option<&str>` is expected (lines 986, 1015, 1165), and calls `.as_deref()` on `Option<Id>` (line 1124). Consequences: `cargo test --all` fails at compile time; NONE of the shipped try-it enforcement tests (the task's primary probe: non-member 403 with zero preview rows / no mesh peer, unresolvable-MR 4xx with no side effects, durable row + peer + teardown) has ever executed; the coverage row's claim that the probe is "killed by" those tests is unvalidated. Repair: add `use gyre_common::Id;` to the test module, fix the three `Some(sha())` call sites (e.g. `Some(sha().as_str())` or change the helper to `Option<String>`), and replace `env.peer_id.as_deref()` with `env.peer_id.as_ref().map(|p| p.as_str())`; then actually run the tests (see F2 — at least one will fail).
- [BLOCKING] **F2 (code, `crates/gyre-server/src/mem.rs:3843-3853): `MemNotificationRepository::list_since` violates the port contract — ascending order and oldest-window truncation.** The port doc (`gyre-ports/src/notification.rs`) says "Ordered by created_at descending"; the implementation sorts `a.created_at.cmp(&b.created_at)` (ASCENDING) and then `truncate(limit)`, so a mem-backed feed returns OLDEST-first and, when the window exceeds `limit`, a different page of rows than SQLite/PostgreSQL (which return the newest `limit` rows descending). This breaks AC #1 ("newest-first ... every adapter") and the port-contract invariant; the sibling mem methods (`list_recent`, `list_by_workspace_type_since`) both sort descending, so mem is the lone divergent adapter. The candidate's own test `unified_activity_honors_since_against_durable_notifications` (mem-backed `test_state`, seeded 900/950/1100/1200, asserts `arr[0]["timestamp"] == 1200` for `since=1000` and `since=0`) FAILS on this — it could not have been run, which F1 explains. The frontend re-sorts client-side, so the user-visible symptom is subtle: the API contract is what's broken (and any non-SPA consumer of `?since=` pages gets the oldest window). Repair: `items.sort_by(|a, b| b.created_at.cmp(&a.created_at));`. The coverage row's "`list_since` (created_at >= since, DESC), implemented by EVERY adapter (mem ...)" is inaccurate until this is fixed.
- [MINOR] **F3 (code, `web/src/components/CrossWorkspaceHome.svelte` ~line 920): gate-failure/test-result entries in the cross-workspace activity timeline do not land on the MR's gate output.** They `nav(event.entity_type, event.entity_id, event)` — MR detail, default tab — without the `_openTab: 'gates'` hint that `WorkspaceHome.svelte:2055` sets. AC #7 ("Every activity entry with a resolvable artifact deep-links ... including gate-failure/test-result entries landing on the MR's gate output") is only met on the WorkspaceHome sidebar. Also note no test on either surface asserts the gate-failure → gates-tab deep link (the only `_openTab` assertions are pre-existing Inbox tests). Repair: mirror the `gateFailure` detection + `data._openTab = 'gates'` in the CWH timeline nav (or route through a shared helper), ideally with one vitest asserting it.
