Findings:

- [open] **F1 (major): repo-access-override management is dead for its intended principals — builtin policy 809 can never match.** `abac_middleware.rs` resolves `subject.workspace_role` only via `extract_workspace_id`, which requires a `workspaces` segment in the route pattern; `/api/v1/repos/:id/access-overrides/:user_id` has none, so the attribute is never set on repo routes and `builtin-repo-access-override-management` (priority 809, conditions `subject.workspace_role In [Owner, Admin]`, actions `[admin]`, resource `repo`) never matches. Through the production router (`build_router` layers `abac_middleware` over `api_router`), a workspace Owner/Admin member whose global role is not `UserRole::Admin` is default-denied 403 on PUT/DELETE access-overrides before the handler's (correct) `can_manage_repo_access` runs. §Repo Access gives the workspace Admin role repo `admin`; the shipped notes claim "Override management is an Owner/Admin capability on the repo's workspace" — in production only platform Admins/TenantAdmins and the system principal can manage overrides. Repro: `/tmp/stage/review-evidence/probe-source-ws-admin-override-abac.rs` → 403 (expected 201), transcript `ws-admin-override-abac-probe-v2.log`; the same probe shape on the workspace-member route returns 204 (control). Fix direction: resolve the caller's membership for repo-addressed routes (load repo by `:id` → `workspace_id`) during attribute resolution, or move these routes to per-handler ABAC evaluation.
- [open] **F2 (test): the committed endpoint tests bypass the ABAC layer entirely.** All four `api::repo_access` tests (and the `api::users` membership tests) build `crate::api::api_router()` without the `abac_middleware` layer that `build_router` adds in production; three of the four repo_access tests authenticate as the system token. The suite is green with F1 present — it cannot detect that the intended managers are denied. `member_management_requires_owner_admin_or_tenant_admin`'s comment ("The request passes ABAC (Developer role may write)") is false in that harness — no ABAC middleware runs; the 403 comes from the handler alone. Authorization tests must layer `abac_middleware` and `seed_builtin_policies` to exercise the production path.
- [open] **F3 (minor): `load_repo_scoped` fails open on an unresolvable workspace.** `if let Ok(Some(ws))` skips the tenant check when the workspace lookup errors or the workspace row is missing (dangling `workspace_id`); a cross-tenant caller then passes the tenant gate. Narrow in impact (mutating paths still require membership/admin; reads leak only role metadata; the pre-existing repo surface had no tenant check at all), but the repo's standards treat unresolvable scope as fail-closed and `git_http`'s `resolve_repo_by_slug` resolves strictly within the caller's tenant.
- [open] **F4 (minor): never-owned workspaces are flagged orphaned.** `create_workspace` seeds no Owner membership for the creator, so `orphaned_workspace_check` records every workspace without a manually invited Owner as ownerless on first observation (not on an owner-departure transition), notifies TenantAdmins, and flags it "orphaned" after the threshold — including agent-operated workspaces that are healthy by design. Spec frames the flag as "when a workspace Owner leaves". Informational surface only; consider seeding an Owner membership at creation or recording only observed owner-present → owner-absent transitions.
- [open] **F5 (test): git-transport repo-access enforcement has no committed coverage.** All 60 `git_http` tests use the system token, which `authorize_repo_access` bypasses unconditionally — deleting the check (or swapping the Read/Write mapping) keeps the suite green. The production behavior is currently correct (independently probed, see above), but a committed test with a user API key + membership/override is needed.
