## Verified working

- **§9 drift evaluation is real.** `reconciliation.rs::mr_meta_spec_drift` resolves the MR's provenance attestation (source-branch head commit via `resolve_ref`, then the author agent's current task, walking derived nodes to the chain root `SignedInput`), reads the recorded `meta_spec_set_sha`, and compares it against `compute_meta_spec_set_sha` (real SHA-256 over the stored set JSON, `lib.rs:475`). Skip paths are graceful and correct: no bound set, no attestation, empty recorded SHA → no drift (cannot assert drift against an unknown baseline).
- **Warning format is exactly §9.** `format_meta_spec_drift_warning` emits `[WARN] meta-spec-drift: code produced under meta-spec set {old}, current is {new}. Reconciliation may be needed.`; recorded as a `GateResult` (gate id `meta-spec-drift`, `GateStatus::Passed` — informational, never blocks by itself; `check_gates_for_mr` treats Passed as pass). Idempotent across retry cycles (existing result updated in place, regression-tested).
- **Hard block is real enforcement, starvation-free.** `selection_meta_spec_drift_hold` runs inside the `process_next` candidate-selection loop (mirroring `selection_trust_hold`): under `require_current_meta_spec_set: true` the entry is requeued with the drift reason and the processor tries the next candidate in the SAME cycle — a drifted head-of-queue entry cannot starve the shared queue (same-workspace and cross-workspace later entries still merge; covered by two dedicated regression tests). Atomic-group candidates expand to all group members, so a drifted member holds the group as a unit. All merge paths flow through `process_next` (background loop + `run_once`); there is no bypass added.
- **Policy storage and API follow the house rules.** `WorkspaceMergePolicy` is persisted through the port-backed KV store (namespace `workspace_merge_policies`) — not an in-memory `Arc<Mutex>`; default false (warn only). `GET/PUT /api/v1/workspaces/:id/merge-policy`: route registered in the ABAC resolver (registry gate green), PUT Admin-only with tenant-ownership check in the handler body (404 for cross-tenant), partial-update semantics, corrupt stored policy errors on direct lookup and degrades to the spec default inside the merge processor (a policy-store outage cannot wedge the queue). API behavior is covered by a router-driven test (default false, Developer 403, Admin round-trip, unknown workspace 404).
- **UI surfaces the drift.** Queue graph API parses the recorded gate result back into `meta_spec_drift {produced_set_sha, current_set_sha}` per node (same source as gate results, so graph and gates cannot disagree); `MergeQueueGraph.svelte` renders the ⚠ badge, the tooltip row `Meta-spec drift: produced under v{old}, current is v{new}` (8-char SHA prefixes) and a legend entry; 5 vitest cases pass.
- **Tests are discriminating, not inflated.** The warn-only test asserts the exact §9 output text on the recorded gate result AND that the MR still merges; the strict test asserts entry stays Queued with the drift reason, MR stays Open, no Passed drift gate result on the blocked path, and that relaxing the policy lets the same entry merge with the warning recorded (proves the block and the warn paths are distinct). Match/no-attestation tests assert the negative (no drift gate result) plus merge. Starvation tests assert later same-workspace and cross-workspace MRs merge while the drifted head stays held.

## Minor observations (non-blocking, recorded for spec lifecycle / follow-ups)

1. **Canonical-spec policy shape vs task contract.** Spec §9 sketches `MetaSpecPolicy { warn_on_drift, block_on_drift, drift_tolerance }` (default `drift_tolerance: 1` — block only if more than one version behind). The assigned task contract specifies the simpler `require_current_meta_spec_set` bool (block on any drift when strict), which is what shipped; the task's "Spec Excerpt" restates §9 in that form. Sets are content-SHA-addressed with no version ordering, so `drift_tolerance` has no data model to bind to today. The opinionated default (warn always, block never) matches the spec. If §9's tolerance semantics are still wanted, amend the spec / open a follow-up task rather than treating row 13 as hollow — the coverage row's notes honestly describe the shipped shape.
2. **Drift is evaluated at merge-candidate selection, not at enqueue.** A drifted MR queued behind other entries (or with failing gates) gets its §9 warning recorded only once it becomes the mergeable candidate. This matches the task plan ("before processing an MR"); noting the timing nuance against §9's "when an MR enters the merge queue" phrasing.
3. `selection_meta_spec_drift_hold` expands atomic groups via `merge_requests.list()` + filter — O(all MRs) per cycle, consistent with the pre-existing `atomic_group_ready`; perf note only.
4. The merge-policy PUT's Admin rejection does not emit an `rbac::record_rbac_denied` audit record, unlike the sibling `put_meta_spec_set` (which does). Enforcement is still real (Forbidden + middleware ABAC); consistency nit.
5. Pre-existing (untouched by this task, base `cfeefbda`): a human can set an MR to `merged` via `PUT /merge-requests/:id/status`, bypassing all queue gates. This is the "override" path the task text anticipates ("until reconciled or overridden"); noting it because it equally bypasses the strict drift block.
