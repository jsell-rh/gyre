Findings:

- [-] **F1 (major): the bootstrap admin user is never bound to the created tenant.** Spec line 47: "Every user belongs to exactly one tenant"; §8 step 2: "Register admin user". `create_user` builds the user via `User::new` (`users.rs:800`), which leaves `tenant_id: None` (`gyre-domain/src/user.rs:126`), and `CreateUserRequest` has no tenant field at all — so no caller can supply one. Worse, the API-key path in the auth extractor hardcodes `tenant_id: "default"` for every API-key user (`auth.rs:577-588`), so the bootstrap admin authenticates as tenant "default" in perpetuity. Steps 3-8 still succeed only because the Admin role satisfies the workspace-create tenant override and the priority-900 `builtin-admin-all-operations` policy (`abac_middleware.rs:530-553`, condition `subject.global_role == "Admin"`, actions `*`, resources `*`) allows everything regardless of tenant. Net effect: tenant isolation for the primary human identity of a fresh install is absent — the admin is a global superuser on every path the extractor's `"default"` tenant reaches, and can never be constrained to the tenant bootstrap created. The spec's model (user → exactly one tenant → tenant admins manage that tenant) is not what ships.
- [-] **F2 (major): step 8's "with repo-orchestrator persona" is not implemented — the spawn path attaches no persona, and the personas bootstrap registers are never consulted by it.** Spec §8 step 8: "Spawn repo orchestrator agent with repo-orchestrator persona". `spawn_repo_orchestrator_core` (`orchestrator.rs:252-298`) calls `validate_persona(state, "repo-orchestrator")` — but that helper reads `state.meta_specs` (server-seeded persona meta-spec stubs, `orchestrator.rs:56-70`), a different store from the `state.personas` table the bootstrap CLI populates, its return value is discarded (`:283`), and it only warn-logs. The `Agent` created by `spawn_orchestrator` (`orchestrator.rs:76-152`) carries name/type/workspace/repo and nothing persona- or prompt-related; `gyre_domain::Agent` has no such field. The four persona prompts embedded in the CLI (`bootstrap.rs:11-56`) are write-only data: nothing reads them back after registration. Scope note for fairness: the §8 "Protocol Injection" prompt-injection machinery is decomposed to task-101 (not started), so the missing injection layer itself is not counted against this task — but the persona *attachment* clause of step 8 is in the "What It Does" section this task declares, and it does not exist. Relatedly, the task's `coverage_sections` lists "platform-model.md §8 Protocol Injection", over-declaring coverage of a section assigned elsewhere.
- [-] **F3 (major): step 8's "Orchestrator reads specs/index.md, observes backlog, begins Ralph loop" — nothing runs.** `spawn_orchestrator` persists the agent row, mints a repo-scoped JWT, bootstraps a signing keypair, bumps budgets, and returns (`orchestrator.rs:76-152`). No compute target resolution, no container or process launch — contrast `spawn_agent` in `api/spawn.rs`, which resolves compute targets and launches a workload. The printed summary claims "Your repo orchestrator is running" (spec's step-9 wording), but the artifact is a database row. The spec's bootstrap promise — a *running platform* — is met only for the control plane.
- [-] **F5 (major): the starter-kit manifest is schema-invalid for the server's manifest parser, so the starter-kit path silently produces an empty spec registry.** Spec §8 step 6: "If not, create a starter manifest with default policies"; Starter Kit section: `specs/manifest.yaml` "# Default manifest with design-principles spec". `STARTER_MANIFEST` (`bootstrap.rs:142-150`) emits `approval: human` as a bare string, but the server's `SpecEntry.approval` requires `ApprovalConfig { mode: human_only|agent_only|human_and_agent, ... }` (`spec_registry.rs:97-151`). `parse_manifest` therefore fails on a starter-kit manifest, and the push-side `sync_spec_ledger` warn-and-returns on parse failure (`spec_registry.rs:346-352`) — the user's spec registry stays empty with only a log line. The repo's own `specs/manifest.yaml` and the server's `SAMPLE_MANIFEST` both use the correct `approval: {mode: human_only}` form, so this is a client-side authoring defect, not a schema ambiguity. The CLI's manifest-shape test checks generic YAML structure only and cannot catch it.
- [-] **F4 (moderate): step 6 "INITIALIZE SPEC REGISTRY" is report-only, and the starter-manifest branch is skipped entirely.** Spec §8 step 6: "If repo contains specs/manifest.yaml, parse and register specs; If not, create a starter manifest with default policies". The implementation only prints "ledger syncs on push" / "registry stays empty until specs are pushed" (`main.rs:1726-1733`). No parsing, no registration. For manifest-less repos, the "create a starter manifest" branch is simply skipped unless `--starter-kit` is passed — and `--starter-kit` is a separate opt-in that writes to the local repo path, not the platform registry. Counter-context: `spec-lifecycle.md` documents push-based server-side sync ("When a push lands on the default branch that modifies files in specs/... server-side post-receive hook"), so deferring registration to push has architectural grounding and the implementation notes state this openly. But the acceptance criterion "Spec registry initialized from manifest or starter kit" is checked `[x]` while neither branch registers anything at bootstrap time, and the starter-manifest branch does not exist. Checked criterion without the behavior.
- [-] **F6 (moderate): starter kit is written to a relative `./<repo-name>/` path when `--repo-path` is omitted.** `main.rs:1734-1738`: `repo_path.clone().unwrap_or_else(|| PathBuf::from(&repo_name))` — with no `--repo-path`, files land relative to the CLI's cwd. This violates the repo's own mechanical invariant (AGENTS.md: "Never store or pass relative `./...` path literals that a child process or filesystem consumer will resolve"); `check-relative-path-defaults.sh` passes only because it does not cover this site. It is also internally inconsistent: step 6's manifest detection treats a missing `repo_path` as "No spec manifest found" while step 6b silently fabricates a different target for the same missing value.
- [-] **F7 (minor): the minted API key is never exercised through the auth extractor, and the implementation notes describe a superseded design.** The test `admin_creates_user_with_authenticating_api_key` (`users.rs:1184-1218`) verifies only the store round-trip (`state.api_keys.find_user_id(hash)`) — never an HTTP call with `Bearer <raw_key>`. Given F1 (the extractor hardcodes tenant "default" and takes `roles: user.roles` on this path), the extractor is exactly where a bug would live, and the criterion-level claim "key authenticates as the new user" is evidenced one layer below the boundary that matters. Separately, the task notes claim client methods "`create_task`, `spawn_agent`" and a step-8 design of "creates task first with task_type implementation then POST /api/v1/agents/spawn" — that was the `c903a80b` design, replaced in `c2755e1b` by `spawn_repo_orchestrator` (task-093 endpoint, no synthetic task). The notes were not updated and describe code that no longer ships.

Summary: the happy path is genuinely good — a real 9-step REST orchestration with thoughtful resumability, a correct admin-gated user-creation endpoint with hashed keys, both fix commits legitimate and regression-tested, and 23 relevant tests green under this review. But the spec's bootstrap promise is undermined at its load-bearing points: the admin identity has no tenant (F1), the spawned orchestrator has neither its persona nor a running process (F2, F3), and the spec-registry step both skips its specced behavior (F4) and ships a starter manifest the server cannot parse (F5) — with the acceptance criterion checked regardless. Revision required.
