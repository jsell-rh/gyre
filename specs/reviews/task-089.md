## Verified working (no findings)

- **NL question → valid view definition.** The generate endpoint's fallback prompt (`PROMPT_EXPLORER_GENERATE`) now carries the full ViewSpec grammar (name, description, data{concept, node_types, edge_types, depth, repo_id, trace_source}, layout ∈ {graph, hierarchical, list, flow}, encoding, annotations, highlight, explanation) plus the spec's layout-selection rules, the read-only query-translator constraint, and refinement-turn instructions. LLM output is gated by the pre-existing `parse_and_validate` (ViewSpec grammar incl. "flow requires trace_source") + `validate_repo_ownership`; invalid output yields `view_spec: null` + fallback list view, never a raw forward. User input never enters the system prompt (question and validated `previous_spec` ride the user prompt only).
- **Renders on ExplorerCanvas.** `viewSpecToViewQuery` translates ViewSpec → the canvas ViewQuery grammar (concept scope with normalized snake_case edges + depth, node-type filter scope, `$governed_by('…')` computed filter with quote escaping, annotations → callouts, name+explanation → query annotation). The full-tree integration test renders ExplorerView → ExplorerCanvas with only the `api` module mocked and asserts the `.query-annotation` sidebar contains the LLM's explanation — real component wiring, not mirrored logic (mutation probe 2 confirms the flow half).
- **Flow for data movement / graph-hierarchical for structural.** Prompt rules carry the spec's intent mapping; flow is additionally *server-enforced*: `enforce_flow_trace_backing` rewrites `flow`→`graph` and strips `trace_source` unless the MR exists, belongs to this workspace, and currently has a captured trace (`traces.get_by_mr` — the same lookup `GET /merge-requests/:id/trace` serves). Cross-workspace and hallucinated mr_ids fall back too, without confirming foreign MR existence. Mutation probe 1 proves the enforcement is real. Client mirrors the fallback: trace fetch failure or empty spans → structural lens.
- **MR ID discovery.** `recent_mrs_with_traces` (newest-first, capped at 10, same `get_by_mr` semantics) is injected into the user prompt with title/spec_ref/status; empty list → explicit "none — do not use flow" instruction. The specced `GET /workspaces/:id/merge-requests?has_trace=true&limit=10` surface is implemented and tested.
- **Explanation sidebar.** The `complete` SSE event carries the LLM's own `explanation` (→ `description` → generic fallback chain, unit-tested), rendered both in the panel and as the canvas query annotation (integration-tested).
- **Save.** "Save this view" posts `{name, description, spec}` to `POST /workspaces/:id/explorer-views` — matches `CreateViewRequest` exactly; the component test pins the exact payload including the preserved explanation.
- **Refine.** Follow-ups send `previous_spec` (component test pins the request shape: first call without, second with the prior spec); the server validates it against the same grammar + repo-ownership before the LLM sees it (400 on invalid, handler-tested) and injects it as the view being refined.
- **Read-only LLM.** The endpoint's only LLM interaction is `predict_json` — no tools, no writes; the prompt states the query-translator constraint; the frontend panel only ever sends a question.
- **Scope/security.** No new routes (ABAC registry untouched); flow `trace_source` is workspace-scoped; generated-spec `repo_id` ownership enforced (pre-existing check retained); rate limiting pre-existing and still tested.
