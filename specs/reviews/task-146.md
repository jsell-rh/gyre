## Findings

- [F1] **`crates/gyre-server/src/mcp.rs` `handle_search` (gyre_search tool, ~line 1990): full-text search executed via MCP records no `search.query` event.** The spec trigger is "Full-text search executed" — transport-independent. There are exactly two production `SearchQuery` execution sites: `api/search.rs:97` (instrumented, emits with caller-bound identity and validated scope) and `mcp.rs:2006` (not instrumented — the function calls `state.search.search(...)` and returns with no `state.analytics.record` anywhere). On an agent-first platform the MCP tool is the autonomous-agent search path; the candidate itself established and applied this exact parity standard for `task.status_changed` ("The MCP tool is the autonomous-agent path for task transitions; the HTTP endpoint in tasks.rs is the other. Both must record.") and `agent.completed` ("the autonomous-agent path ... must emit ... just like the HTTP endpoint"), and prior repair rounds on this same candidate closed precisely this class of gap ("emit analytics on silent terminal paths"). With gyre_search uninstrumented, the coverage-matrix claim "All 12 events emit at real trigger points" (§Auto-Emitted Events → implemented) overstates reality, and agents' searches — the usage the spec's agent-consumable analytics loop is built to measure — are invisible. Repro: call MCP `gyre_search` with a valid `q`, then `GET /api/v1/analytics/events?event_name=search.query` → 0 events, while `GET /api/v1/search?q=...` records one. **Repair path:** emit `search.query` in `handle_search` (or refactor both paths through a shared emit helper) with the same caller-bound identity and scope rules as the HTTP handler, add a per-event test driving the MCP tool, and append the repair commit to task-146.md `commits:` frontmatter.

Minor (non-blocking, recorded for completeness):

- `group_by` on `GET /events` aggregates the limit-truncated result set (default 100, cap 10_000), not the full filtered population — counts silently cover only the newest N events. The spec does not pin the interplay between `limit` and `group_by`, and `/daily` exists for whole-window series, so this is an ambiguity rather than a violation; worth a doc note or a verifier-side clarification in a later round.
- SQLite `LIKE` is ASCII-case-insensitive while PG `LIKE` is case-sensitive, so a prefix filter like `MR.*` behaves slightly differently across backends. Event names in this codebase are lowercase-by-convention; no action required.
- `web/dist/` untouched by this branch (no web-source changes) — generated-output ownership sits with the verifier; no observation beyond "not modified".
