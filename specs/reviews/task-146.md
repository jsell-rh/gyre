### Findings (blocking)

- [-] **F1 (major): `task.status_changed` missing on production transition paths.** `ralph_loop.rs:208` `complete_task_on_merge` (invoked from the merge watch at `:180`) persists the task's terminal Review→Done transition — the agent-runtime §1 Phase 7 completion — and even emits a WebSocket `TaskTransitioned` message, but never calls `record_task_status_changed`. This contradicts both the spec trigger ("Task transitions status") and the helper's own doc contract (`api/analytics.rs:66-70`: "Every production path that persists a task status transition must call this"). Sibling transitions in the same file (`:288`, `:380`, `:494`) emit. The existing test `merge_completes_task` (`ralph_loop.rs:1403`) asserts Done + the message but not the analytics event, so the gap is unguarded. Additional uninstrumented persisted transitions: the `signal_chain.rs` scheduler claim/release paths (~`:631`, `:691`, `:904`, `:1292`, `:1341`, `:1556`, `:1618`, `:1665`). Repair: call `record_task_status_changed` in `complete_task_on_merge` (both the InProgress→Review and →Done steps, or the net transition) and in the scheduler claim/release paths, with a regression test each (extend `merge_completes_task` to assert the event and its properties).
- [-] **F2 (major): `gate.failed`/`gate.passed` missing on post-merge gate evaluations.** `gate_executor.rs:1385` `run_post_merge_gates` / `:1457` `run_post_merge_gate_commands` run PostMerge-phase quality gates — called from `merge_processor.rs:1593`/`:2771` (post-merge validation) and the revert-decision paths `merge_processor.rs:3250`/`:3504`, plus `api/recovery.rs:256` — with zero analytics emission (no `state.analytics` reference in lines 1385-1545). A required post-merge gate failure that triggers the whole revert/recovery protocol is invisible to gate analytics. Only the pre-merge `run_gate` path emits. Repair: emit `gate.passed`/`gate.failed` (with `gate_id`, `gate_type`, `mr_id` where resolvable, `duration_secs`/`output_snippet`) from the post-merge command loop; note the loop currently returns `Err` on first required failure, so emission must happen per-gate before the early return.
- [-] **F3 (medium): SQLite `LIKE` prefix filter is case-insensitive and unescaped — three-way adapter divergence on a caller-reachable parameter.** `sqlite/analytics.rs:201` (and `count_grouped` ~`:297-317`) build `LIKE '{prefix}%'` from the caller-supplied `event_name` filter without escaping `%`/`_` and without `PRAGMA case_sensitive_like` (`sqlite/mod.rs:73-83` sets only WAL/foreign_keys/busy_timeout). Probe: `'mr.merged' LIKE 'MR%'` → 1 and `'mr.merged' LIKE 'mr.m_rged%'` → 1 on SQLite, while mem (`starts_with`, case-sensitive literal) and Postgres (case-sensitive LIKE) match neither. So `GET /api/v1/analytics/events?event_name=MR.*` returns different results per backend. Repair: escape `\`→`\\`, `%`→`\%`, `_`→`\_` in the prefix with `ESCAPE '\'` (both adapters), and/or set `case_sensitive_like=ON` in the connection customizer; add parity tests using `%`/`_`/case in filter values (currently untested, which is why the divergence survives).
- [-] **F4 (medium, config-dependent): Postgres `count_grouped(Day)` day key is session-TimeZone-dependent.** `postgres/analytics.rs:~269` uses `to_char(to_timestamp(timestamp), 'YYYY-MM-DD')`, which renders in the server's `TimeZone`, while the port contract documents "UTC calendar day" and SQLite/mem compute UTC. On PG with TZ ≠ UTC, `group_by=day` buckets shift relative to the other adapters (mirrors the pre-existing `aggregate_by_day` at `:~360`, now propagated onto new task-146 surface). Repair: `to_char(to_timestamp(timestamp) AT TIME ZONE 'UTC', 'YYYY-MM-DD')` in both methods.
