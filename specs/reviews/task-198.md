### Findings

- [ ] **F1 (major, blocking): cross-repo link-id collision silently loses durable rows.** Link id is `format!("{}-{}-{}", entry.path, link.link_type, link.target)` (`spec_registry.rs:413`) — no repo scope — but `spec_links.id` is the PRIMARY KEY. Two repos pushing the same spec path with an identical link (same type+target): repo-b's `replace_for_source` deletes nothing (scoped `WHERE source_repo_id='repo-b'`), then INSERTs the same id → PK violation → transaction rollback → swallowed as `warn!` (`spec_registry.rs:603-611`). Proven with a temporary end-to-end test (reverted): cache = 2 links, durable table = 1 (repo-a's); after restart repo-b's link is silently gone from the tenant-wide graph — the same silent restart degradation this task closes, now dependent on which repo pushed first. Also corrupts `save()` upserts by id across repos. Raw-SQL reproduction: second INSERT with same id, different `source_repo_id` → `UNIQUE constraint failed: spec_links.id` (exit 19). Fix: scope the id with `source_repo_id` (preferred — aligns with the adapters' `(source_repo_id, source_path)` replace scoping), or composite key `(id, source_repo_id)`. Evidence: `13-defect-cross-repo-id-collision.txt`.
- [ ] **F2 (moderate, test): the cross-repo regression test seeds an id production can't produce.** `sync_replaces_links_scoped_to_source_repo` (`spec_registry.rs:2501`) pre-seeds repo-a's link with hand-built id `...@repo-a/system/target.md`; real syncs generate repo-less ids, so the test's id space diverges from production and it cannot catch F1. Seed via a real sync push (or the production id format) once F1 is fixed.
- [ ] **F3 (minor, test): self-confirming tail in `staleness_query_parity_after_restart`.** The final "staleness checker itself" block re-reads the same `restarted_store` snapshot it just asserted on and compares the store to itself — a no-op. The test's load-sensitive assertions (post-push vs post-restart status/`stale_since`) are genuine (mutation probe), so this is not blocking; remove the block or re-derive the verdict from the ledger SHA.
