Findings:

- [-] [process-revision-complete] **F1 (major): `MemSecretRepository::create` violates the port's uniqueness contract — no duplicate check.** The port documents that `create` "Fails if a secret with the same `id`, or the same `(scope, scope_id, name)` within the tenant, already exists" (`gyre-ports/src/secret.rs:16-20`). SQLite enforces this via `UNIQUE (tenant_id, scope, scope_id, name)` + PK (migration `up.sql:20`); the mem implementation (`mem.rs:3378-3384`) pushes unconditionally, so the same id or same `(tenant, scope, scope_id, name)` can be inserted twice. Because `get_value` (`mem.rs:3386-3394`) and `rotate` (`mem.rs:3420-3433`) use `.find(...)`, only the first duplicate is ever seen and the second is silently unreachable. The divergence is invisible to the 17 adapter tests (they run against SQLite only) and will surface when task-098's Admin API runs against the mem default (`lib.rs:1059-1062` — `store!` → `MemSecretRepository::default()` when no DB URL is set): create-then-create-same-name would succeed in dev/mem mode and fail with a constraint error in SQLite mode. Fix: check-then-error in mem `create` mirroring the SQLite failure mode. Process surface patched: implementation.md item 167 (adapter contract parity — a port-documented constraint must be enforced by every adapter, with a contract-violation test per adapter) + verifier.md flaw-class bullet (mem/SQLite adapter contract divergence) + mechanical check: bash scripts/check-mem-port-contracts.sh fails on a mem create whose port doc documents duplicate rejection while the body inserts unguarded (mem.rs:3378 seeded in its exemption file, frozen at 1). Product fix owned by task-097's revision round.
- [-] [process-revision-complete] **F2 (major): the spawn secret-injection integration has zero test coverage — acceptance criterion checked without evidence.** The task's criterion "Agent spawn uses resolved secrets instead of hardcoded GYRE_CRED_*" is checked `[x]`, but no test exercises the injection path: the `spawn.rs` test module (~50 test fns from `:1825`) contains zero secret references, and `crates/gyre-server/tests/` has no secrets/`GYRE_CRED_` references. The 17 adapter tests cover `resolve_for_agent` only as a repository; the integration loop at `spawn.rs:657-663` (env var naming `GYRE_CRED_{name}`, the `Vec<u8>`→String conversion, the tenant fallback feeding `resolve_for_agent`, and the resolve-failure warn-and-continue branch at `:665-670`) is untested. Flaw class: untested integration point behind a checked acceptance criterion. Fix: add a spawn-level test that seeds the repository with secrets in several scopes, spawns via the mem state, and asserts the resulting `container_env` contains the expected `GYRE_CRED_*` entries (and that a resolve error does not fail the spawn). Process surface patched: implementation.md item 168 (a checked acceptance criterion naming an integration point requires a test exercising that integration, with per-branch coverage of its fallback branches) + verifier.md flaw-class bullet (checked acceptance criterion without integration-test evidence). Not mechanically decidable. Product fix owned by task-097's revision round.
- [-] [process-revision-complete] **F3 (moderate): spawn falls back to a literal `"default"` tenant when the workspace lookup fails, instead of skipping tenant-scope resolution.** `spawn.rs:643-646`: `workspace.as_ref().map(|ws| ws.tenant_id.to_string()).unwrap_or_else(|| "default".to_string())`. The workspace fetch at `:352-357` is `.ok().flatten()`, so a transient store error silently re-targets tenant-scope secret resolution at a fabricated `"default"` tenant: tenant-scoped secrets for the real tenant do not apply (silently), and if a real tenant is actually named `default` its secrets leak to agents whose workspace could not be resolved. The codebase already has the correct pattern: `emit_reconciliation_completed` (`lib.rs:1160-1173`) explicitly refuses to hardcode `"default"` and skips the emit when the tenant cannot be determined. (`emit_event`'s own `Id::new("default")` at `lib.rs:490` is pre-existing single-tenant-dev code, not part of this change.) Fix: on unresolvable workspace, warn and skip tenant-scope resolution (pass the workspace tenant only when known), or fail the spawn. Process surface patched: implementation.md item 169 (never fabricate a scope identity via literal fallback; skip and log, citing emit_reconciliation_completed as the correct pattern) + verifier.md flaw-class bullet (fabricated scope identity on lookup failure, noting the unflagged same-class sibling in constraint_check.rs) + mechanical check: bash scripts/check-fabricated-scope-defaults.sh fails on unwrap_or-style "default" fallbacks bound to tenant_id/workspace_id/ws_id/repo_id (8 legacy sites seeded in its exemption file, frozen at 8, including the unflagged constraint_check.rs sibling). Product fix owned by task-097's revision round.
- [-] [process-revision-complete] **F4 (minor): `String::from_utf8_lossy` on secret values silently corrupts non-UTF-8 secrets.** `spawn.rs:661`. The port contract passes values as `Vec<u8>` and neither the spec nor the task restricts secret values to UTF-8 (the encryption layer is byte-oriented), but the spawn path requires `String` for env vars. A binary secret is lossily mangled with U+FFFD replacement characters with no error and no log — the agent then uses a corrupted credential and fails opaquely downstream. Fix: skip the secret and log a warning naming the secret (not the value) on non-UTF-8 values, mirroring the resolve-failure branch's availability posture. Process surface patched: implementation.md item 170 (byte-oriented security material must not pass through from_utf8_lossy silently; skip and warn naming the item, never the value) + verifier.md flaw-class bullet (silent lossy conversion of security material) + mechanical check: bash scripts/check-lossy-secret-conversion.sh fails on from_utf8_lossy applied to secret-domain arguments or resolve_for_agent values (spawn.rs:661 seeded in its exemption file, frozen at 1). Product fix owned by task-097's revision round.
- [-] [process-revision-complete] **F5 (minor): auto-generated key silently downgrades encryption-at-rest when `GYRE_SECRET_ENCRYPTION_KEY` is unset.** Spec Storage Backend: "Secrets are stored encrypted in Gyre's database by default." When the env var is unset, the adapter auto-generates a key and persists it in the same database (`kv_store`, `secrets`/`encryption_key`; `auto_generated_key_persists_across_reopen` test). The database therefore holds both the ciphertext and the key that decrypts it — encryption-at-rest degrades to obfuscation for any attacker with database read access, which is precisely the threat model "encrypted at rest" addresses. The behavior is a deliberate, documented, tested availability choice (server boots without configuration; documented in `server-config.md`), and the sibling `conversation.rs` precedent is opt-in plaintext, so the designs are at least consistent in intent. The gap versus the spec's wording should be closed somewhere: either a startup `warn!` (the log is currently silent about auto-generation), or spec/task wording that accepts "auto-generated key stored alongside" as the default posture, or an explicit production-mode refusal. Recording as a spec-alignment observation for revision to resolve or explicitly waive. Process surface patched: implementation.md item 171 (a security-posture downgrade must be operator-visible: startup warn! naming the degraded posture and remediation, OR explicit spec wording accepting the posture, OR production refusal) + verifier.md flaw-class bullet (silent security-posture downgrade without operator signal, routing spec-alignment cases through the spec lifecycle). Not mechanically decidable. Product fix owned by task-097's revision round.
