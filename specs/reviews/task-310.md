## Non-blocking observations (hardening; no contract violation found)

- **O1 — shutdown honored without an origin check.** `handleBusMessage` triggers `requestShutdown` on `kind === 'status_update' && payload.action === 'shutdown'` without checking `msg.from`. `StatusUpdate` is NOT `server_only()` (agent-sendable Directed kind), so a same-workspace agent — or a workspace member — could send a `status_update` payload `{status, summary, action: "shutdown"}` (extra fields pass the required-fields-only `validate_payload`) to a live peer and make it gracefully abandon its run. Not blocking because: same-tenant authenticated callers already hold the sanctioned `POST /api/v1/agents/{id}/stop` surface (same effect class: terminal stop of the target), same-workspace agents are inside one trust domain by the bus's designed agent-to-agent Directed messaging, and the impact is bounded (stale detection / task recovery re-drives the work; no data leak, no cross-tenant scope). Suggested hardening for a follow-up: require `msg.from === "server"` (origin is derived server-side from verified auth, so the string is trustworthy) before honoring `action: "shutdown"`, and/or signature verification once the runner has JWKS access.
- **O2 — client-clock replay bound.** `lastSeenMs` starts at the runner's `Date.now()`; on Subscribe the server replays `created_at >= last_seen+1`. Clock skew between container and server can replay a pending Directed message at session start (arguably per the Directed-tier "read by the next session on startup" contract) or skip a sub-skew window of replay (live push is unaffected — delivery to the live session does not depend on `last_seen`). Bounded, documented behavior in the runner comment; not a defect against the contract.
