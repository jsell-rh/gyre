## Verification-infrastructure observation (non-blocking, for the controller)

The durable verification finding (source `61ed5395`, `bash /tmp/stage/checks.sh` exit 1) failed only `check-abac-exempt-handlers` with "ABAC-exempt route `/api/v1/workspaces/:id/meta-specs/preview[:preview_id]` is not registered in api/mod.rs". The candidate tree has no such exemption entries and no such routes — all gates pass on the candidate checkout (probe above). The failure comes from the verification harness: `verifier-script-overlay.py begin` restores `scripts/` from the BASE before the first `static_gates` pass, so the merged tree (candidate routes removed) is judged with the base's exemption data (entries still present). The candidate carries a principled fix (`scripts/verifier-script-overlay.py`: frozen `*-exemptions.txt` data follows the merge while check logic stays base-restored; safety pinned by `dev-check.sh`'s committed-ref growth guard that forbids any added or count-neutral-replaced exemption entry, and by `scripts/test_dev_checks.py` 10/10). However, `scripts/pipeline/verification.py` copies the overlay (and all POLICY_FILES) from the controller's `ROOT/scripts`, not from the candidate — so the candidate's fix does not take effect in the verification sandbox and the same spurious failure will recur on the next round. Remediation belongs to the controller (pick up the fixed overlay in ROOT, or apply equivalent data-follows-merge semantics). This is not a code defect in the candidate; the candidate's own tree is self-consistent.
