## Findings

- **F1 (major): cross-workspace item entry is a silent no-op on any full page load at `/all`.** App.svelte's onMount `cross_workspace` branch never sets `currentWorkspace`, and `goToEntityDetail` begins with `if (!currentWorkspace) return;`. Consequently, when `/all` is the page-load URL (bookmark, shared deep link — §7 makes every state URL-addressable — or a plain refresh while at `/all`), every entity-item click in the cross-workspace dashboard (Decisions items, Specs rows, Activity entity links) does nothing: the URL stays `/all` and no error is surfaced. Demonstrated with a real-App jsdom probe (evidence: `TmpProbeAllEntry.test.js`, `vitest-probe-all-entry.log`): fresh-session and saved-workspace page loads at `/all` both fail to navigate; the identical click after client-side dropdown navigation to `/all` correctly enters the owning workspace/repo (`/workspaces/billing/r/billing-svc/tasks/t-1`, `vitest-probe3.log`), so the defect is specific to the page-load path. This violates Required Behavior 1 ("opening an item must enter its actual owning scope") and 4 ("Lookup/request errors must surface as errors, rather than successful empty data or fallback scope identities"). Fix direction: resolve the owning workspace from the already-loaded membership `workspaces` list (the switch code already does `workspaces.find(w => w.id === ownerWsId)` — only the early return and the `ownerWsId !== currentWorkspace.id` comparison assume a non-null `currentWorkspace`), and surface an error when no owning workspace can be determined. There is currently no regression test for the owning-workspace entry behavior at all; the task contract asks for a regression exactly for demonstrated missing behavior like this one.

## Verdict

Not approved — F1 must be repaired (with a regression test for the `/all` page-load entry path) before the §10 acceptance criterion "Cross-workspace attribution links enter the item's owning workspace/repo" can be considered met.
