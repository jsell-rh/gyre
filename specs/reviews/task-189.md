- **The parent chain is real, not reconstructed from the query.** `resolve_persona` (`api/personas.rs:285-321`) now walks `state.repos.find_by_id(scope_id)` → `Repository.workspace_id` → `state.workspaces.find_by_id(...)` → `Workspace.tenant_id`, building `[Repo(repo_id), Workspace(repo.workspace_id), Tenant(workspace.tenant_id)]`; the Workspace branch derives the tenant the same way; Tenant is pass-through (the id already is the tenant id). No `scope_id.clone()` into a foreign scope variant remains. The walk uses the entities' own parent ids (`repository.rs:50-62`, `workspace.rs:67-90` constructors confirmed to store them), so the fallback levels key on the same ids personas are stored under.
- **Nearest-wins ordering is enforced by the loop, not by luck.** The `for scope in &scopes_to_try` loop (`personas.rs:323-327`) returns the first hit, and the chain is ordered Repo → Workspace → Tenant. The shadowing test seeds all three levels with distinct `id`/`system_prompt` values and asserts the repo body on a repo query and the workspace body on a workspace query — a regression to exact-scope-only matching or to an inverted chain both fail it. Test ids are deliberately distinct (`t1`/`ws1`/`r1`), so a scope-id-reuse regression cannot accidentally match.

The test proves the discrimination by asserting the error message names the entity — and it seeds a tenant persona first, so a silent-skip implementation (returning 200 from the tenant fallback) would also fail it. Matches the task's plan item 3.
