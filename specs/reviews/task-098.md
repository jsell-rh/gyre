## What was verified (independent probes; logs under `/tmp/stage/review-evidence/`, see `MANIFEST.md`)

- **Admin API** (`api/secrets.rs`, registered in `api/mod.rs`): all four endpoints live — `POST/GET /api/v1/secrets`, `DELETE /api/v1/secrets/:id`, `POST /api/v1/secrets/:id/rotate`. Create is create-or-update on `(scope, scope_id, name)` within the tenant (spec's "Create/update"). Handlers derive `tenant_id` from auth context and validate caller-supplied `scope_id` against it through real entity lookups (workspace, repo→workspace, task→workspace) — cross-tenant `scope_id` → 403/404 (tested). Responses are a dedicated metadata struct; the `Secret` domain type carries no value field at all, so values cannot structurally leak into list/create/rotate responses; tests additionally assert the plaintext never appears, and round-trip the stored value through the port to prove real persistence.
- **Admin-only enforcement, two layers**: (1) ABAC — `secret` resource type with `RouteResourceMapping` for all four routes; `builtin-secret-admin-only` (priority 860, Deny on `subject.global_role != Admin`) sits above the Agent allow (700) and Developer allow (800) and below `builtin-admin-all-operations` (900), so every non-Admin role is denied at the policy layer — `secrets_routes_are_admin_only` tests Developer denial + Admin allowance on all four routes through the real middleware; (2) in-handler `require_admin` on every handler — **mutation probe**: removing it from `create_secret` makes `non_admin_jwt_is_forbidden` fail (exit 101), so the test genuinely pins the enforcement, not the middleware's shadow.
- **MCP resources** (`mcp.rs`): `secrets://names` and `secrets://status` registered in `resources/list` and served from `handle_resource_read`. Scope resolves from the agent JWT claims with agent-record/task fallback; the tenant comes from the governing workspace record (no fabricated `"default"` — consistent with the task-097 F3 fix). The metadata cascade (tenant → workspace → repo → task, nearest-wins) mirrors `resolve_for_agent` without any decryption path — `get_value` is never called. Tests cover cascade names, same-name override, cross-workspace invisibility, expiry statuses (active/expiring/expired), values-never-in-payload, and the no-agent-scope error path for user tokens.
- **CLI** (`gyre-cli`): `gyre secret set/list/delete/rotate` with `--scope workspace|repo|tenant`, `--repo`/`--workspace-name` resolution, `--secret-type`, `--expires-at`. Delete/rotate resolve the id by name in the target scope via a real list call. 6 parse tests including the spec-shaped `set --repo gyre DATABASE_URL "postgres://..."` and missing-value rejection.
- **UI**: `SecretsPanel.svelte` mounted as a Secrets tab in Workspace, Repo, and Tenant settings — metadata table, create/delete/rotate actions, write-only value field rendering the fixed `••••••••` placeholder. 4 vitest files / 175 tests pass, including a leak-injection test (a value planted into a mocked list response must not render).
- **Rotation job** (`secret_rotation.rs`, registered as the 5-minute `secret_rotation_check` job in `jobs.rs` + spawned in `main.rs`): scans tenant/workspace/repo scopes for secrets expiring within 1h (or already expired), notifies Admin/Owner members of the owning workspace via `SecretExpiring` notifications, with duplicate suppression and 24h dismissal windows. Tests: expiring+expired notify (admins only, developers excluded), rerun does not duplicate, healthy secrets never notify.
