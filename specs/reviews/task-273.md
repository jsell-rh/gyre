## Findings

- [-] **F1 (blocking — unsafe scope handling / missing enforcement of platform-model §7 on the Vault backend): `launch_taskless_agent_process` resolves the agent's secrets with the SERVER's Vault token instead of the agent's JWT.** `crates/gyre-server/src/api/spawn.rs:3129` calls `state.secrets.resolve_for_agent(...)`. In the Vault adapter, `resolve_for_agent` is wrapped in `server_token_retry` (server static token/AppRole, `crates/gyre-adapters/src/vault/mod.rs:~1030`); the §7 agent-JWT path exists only in `resolve_for_agent_as` (`mod.rs:1061`: JWT-auth login, then cascade with the JWT-derived client token). The agent's freshly minted JWT is already in scope in the same function (`token` param, injected as `GYRE_AUTH_TOKEN` at spawn.rs:3053) but is not passed. The main spawn path is correct (`launch_agent_process`, spawn.rs:2406, `resolve_for_agent_as` with an explicit §7/TASK-273 comment); these are the only two production resolution call sites (grep-verified). Reachable from meta-spec preview runs (`meta_specs.rs:2069`). Consequence: with `GYRE_SECRET_BACKEND=vault`, a preview/taskless agent's `GYRE_CRED_*` values are read with the server's broad admin token, so Vault policies do NOT scope what that agent receives — violating requirement (1): "resolution for an agent authenticates to Vault with that agent's JWT (Vault JWT auth backend) so Vault policies scope the returned secrets". Reproduce: Vault with a restrictive agent JWT policy denying a secret the server token can read; spawn a preview agent; the denied secret arrives in the agent env. Repair: pass `token` to `resolve_for_agent_as` at spawn.rs:3129 (one-line change mirroring spawn.rs:2406).

Minor (non-blocking, recorded for repair):

- **M1** `maintenance_jobs.rs:141`: `maintain_repo` hardcodes `Command::new("git")`, bypassing the `GYRE_GIT_PATH` git-execution-layer convention used at 40+ sites; on GYRE_GIT_PATH-only deployments every repo's maintenance fails.
- **M2** `sops/mod.rs` `sops_encrypt`: writes `"unencrypted_suffix": ""` where the sops CLI emits `"_unencrypted"`; sops's Go decrypt walk (`strings.HasSuffix(key, suffix)`) with an empty suffix matches every key, so a real `sops -d` would likely return raw `ENC[...]` values — failing the "decryptable with the sops CLI" clause of the Required behavior (the Acceptance Criteria allow the spec-conformant native age decryption alternative, which is implemented and tested; sops CLI unavailable in the review sandbox, so this is source-analysis, not a probe). Recommend `"_unencrypted"` or a CLI-generated fixture test.
- **M3** `maintenance_jobs.rs:246`: reap set is `Dead | Stopped | absent`; `Failed` agents are never reaped nor retired (leak path if the clean-exit mark fails); local `PidCheck::Unverifiable` records on /proc-less platforms are logged forever without retirement.
- **M4** `sqlite/secret.rs` / `postgres/secret.rs` `load_sops_identity`: first-boot TOCTOU (kv_get → generate → kv_set overwrite) can permanently discard an identity and its secrets.
- **M5** `secret_rotation.rs`: handlers accept `expires_in == 0` (always-expired secret re-refreshed each cycle) while the enrollment callback filters `> 0`; enrollment create stores `last_rotated_at: None` (one redundant refresh).
- **M6** `admin.rs` `admin_server_logs`: the process-wide log buffer is visible to every tenant's Admin — matches the task's literal "Admin-only" but is a cross-tenant exposure surface worth a spec decision.
- **M7** migration 000070 backfill omits agent-principal legacy rows (stay NULL, invisible to every tenant-scoped admin query).
- **M8** `docs/server-config.md`: documented relative default for `GYRE_CLAUDE_MAX_REDIRECT_URI` contradicts the code's fail-closed absolute-URI requirement.
