## Findings

- [-] **F1 (Medium — code, `crates/gyre-adapters/src/compute/ssh.rs`): SSH `kill_process` implementations swallow failures, so a failed SSH kill is durably recorded as a terminated instance.** `SshDockerTarget::kill_process` (ssh.rs:570-576) discards the result of `remote_docker(["rm","--force",id])` — which returns `Err` on SSH transport failure or non-zero remote docker exit (ssh.rs:475-500) — and unconditionally returns `Ok(())`; `SshTarget::kill_process` (ssh.rs:305-321) only debug-logs a non-zero remote `kill -TERM` and returns `Ok(())`. Both are reachable from the new task-273 kill-and-mark paths: every spawn arm (including ssh-docker and ssh-bare) inserts its `SpawnBackend` into `state.spawned_backends` (`spawn.rs:2716`), and `kill_and_mark` (`maintenance_jobs.rs:672-712`, shared by `remote_agent_cleanup`'s fast path at :291 and the admin kill fast path at `admin.rs:546-576`) marks the durable `agent_instances` row terminated and purges the in-memory registries after `kill_process` returns `Ok`. Reproduce: spawn an agent on an ssh-docker compute target whose remote docker is unreachable, mark the agent Dead, run `remote_agent_cleanup` — the record is marked terminated (`remote_agent_cleanup`) and removed from `list_running()` while the remote container keeps running, permanently invisible to every future sweep. This is the identical hazard class the candidate's own repair commit eliminated for container/kubernetes/docker (its in-code invariant at `maintenance_jobs.rs:283-287`: "kill_process now fails on every non-NotFound error … marking the orphan terminated while the pod kept running"); `ssh.rs` has zero diff lines vs base and was missed. No test pins SshDocker/SshBare kill-failure semantics. Fix: propagate `remote_docker` errors (treating remote "No such object" as already-gone, mirroring `container_already_gone`), fail on non-zero remote `kill`, and add failure-semantics tests mirroring `kill_and_mark_failure_leaves_record_running`.
- [-] **F2 (Minor — hardening, same repair area): the kill subprocesses behind `remote_agent_cleanup`/admin kill are unbounded.** ssh kills, `docker rm --force` (container.rs:224) and `kubectl delete` (kubernetes.rs:313) run without a timeout (only `LocalTarget` bounds its wait, 10 s); a hung remote daemon or a packet-dropped SSH target stalls the sequential sweep loop indefinitely. `check-unbounded-external-http.sh` covers HTTP only, and the repo's own precedent bounds equivalent subprocess work (`maintain_repo`'s 10-minute git gc). Fix: wrap the kill invocations in `tokio::time::timeout`.
