## Findings

- [major] **F1 (code): `GcpServiceAccountHandler::rotate` destructively rewrites the stored service-account credential.** `crates/gyre-server/src/secret_rotation.rs:203-212` (`GcpSaDoc` = type/client_email/private_key/token_uri/access_token only) and `:320-327` (re-serialize the struct as the new value). Serde ignores unknown fields on deserialize, so the first refresh of an expiring GCP SA secret silently drops `project_id`, `private_key_id`, `client_id`, `auth_uri`, `auth_provider_x509_cert_url`, `client_x509_cert_url` — and any other field — from the re-stored document. The task requires "re-storing the refreshed document"; the stored value after refresh is a lossy 5-field projection, no longer a complete Google-issued SA key (the cred-proxy emulator keeps working since it only reads `client_email`/`private_key`, but an admin exporting the secret, or any consumer parsing it as an SA key, gets a mutilated document — irreversible data loss in the credential). Reproduce: create a secret whose value is a full SA JSON with `expires_at` inside the rotation window, point `token_uri` at a stub token endpoint, run `run_once`, `get_value` → `project_id` et al. gone. Fix: deserialize to `serde_json::Value` and only overwrite `access_token` (or `#[serde(flatten)] extra: Map<String, Value>` round-tripped). Note: the analogous OAuth-doc rewrite is pre-existing behavior on a Gyre-internal document format and is not attributed to this task.
- [moderate] **F2 (tests): the GCP SA JWT-bearer grant and shape-based dispatch have zero tests.** No test anywhere constructs an SA-key secret, runs the rotation job against a token endpoint, and verifies the RS256 assertion (grant_type `urn:ietf:params:oauth:grant-type:jwt-bearer`, iss/aud/scope claims, signature verifiable with the SA public key) or that the rotated document/expiry land — and no test that an OAuth credential document under a non-`_refresh_token` name is refreshed (every `seed_oauth` test uses the `oauth_refresh_token` name; the dispatch change the task exists to make is unproven). The AC's "real RS256 JWT-bearer grant" currently rests on code reading alone.
- [moderate] **F3 (tests): `maintenance_jobs.rs` has no test module, and the new SQL adapters have none either.** `repo_maintenance` (gc invocation, per-repo failure isolation), `job_history_cleanup` (finished-rows-only deletion), `oauth_state_cleanup` (only-expired), `remote_agent_cleanup` (kill + mark terminated; live agents untouched) are untested; `sqlite/postgres job_run.rs`, `oauth_state.rs`, `agent_instance.rs` have zero tests (restart durability, `delete_older_than` finished-only, single-consume, `mark_terminated` failure constraints). These behaviors are exactly the verifier's acceptance probes, but the repo's own standard is a hard test per behavior; nothing in-tree fails if they regress.
- [moderate] **F4 (tests): the SQL-path audit filters added by this task are untested.** `tenant_id` scoping (incl. the NULL-legacy-row union) and the free-text `q` path (LIKE-escape, paged `query_rows`/`count_rows`, `detail_matches` zstd decompress-match) have no adapter test in either `sqlite/audit.rs` or `postgres/audit.rs`; only the mem parity path is exercised via the `admin.rs` handler tests. The AC's zstd-compressed + `q` combination is untested anywhere.
- [minor] **F5 (code): `admin_jobs` in-memory fallback reports the OLDEST run's status.** `crates/gyre-server/src/api/admin.rs` (~line 133): durable history is newest-first so `.first()` is correct there, but the fallback `registry.history()` returns the in-memory VecDeque oldest-first, so when only in-memory history exists (durable persist failed, or a pure-mem state before `start_job_registry`) the job's `status` pill shows the oldest run, not the most recent. Reachable only on the fallback path; cosmetic.
