## Findings

- [-] **F1 (code, admin kill orphan reconstruction — `crates/gyre-server/src/api/admin.rs:618,628`):** the restart-orphan branch of the admin kill path reconstructs container/Kubernetes targets with bare `ContainerTarget::new("unused")` / `KubernetesTarget::new("unused")`, ignoring the persisted `backend_config` that the sweep's `reconstruct_container_target` / `reconstruct_kubernetes_target` (maintenance_jobs.rs:568, 594) exist to apply — despite the branch's comment claiming "the same reconstruction remote_agent_cleanup performs". A k8s agent spawned into a configured non-default namespace (backend_config persisted at spawn, spawn.rs:2582-2608), after a server restart, is admin-killed with `kubectl delete pod <id>` missing `--namespace`: the delete hits the default namespace, fails NotFound, `pod_already_gone` returns Ok (kubernetes.rs:340-348), and `kill_and_mark` marks the record terminated `admin_kill` while the pod still runs — the sweep then permanently skips the terminated record. Same class for a container record whose persisted runtime differs from kill-time auto-detection. This reintroduces on the admin surface the exact unverified-kill-marked-terminated hazard commits 39fe7ae7/48ca4294 eliminated for the sweep. **Repair:** route the admin kill's container/kubernetes arms through the shared `reconstruct_*_target(&instance)` helpers.
- [-] **F2 (code, Vault duplicate-constraint TOCTOU — `crates/gyre-adapters/src/vault/mod.rs:753-780`):** `create` enforces the port's "Fails if the same id, or the same (scope, scope_id, name) within the tenant, already exists" (gyre-ports/src/secret.rs:19-21) as check-then-write with no KV v2 CAS: two concurrent creates of the same scoped name both pass the reads and both land as new KV versions, so the constraint is best-effort only, unlike the SQLite/PG UNIQUE constraints and the mem guard. Vault KV v2 supports `{"options":{"cas":0}}`; the fix is to write with cas=0 (keeping the id index check) and map the 400 cas-mismatch to the port's duplicate error. Narrow window, admin-only writes — but the repo's adapter-contract invariant demands absolute enforcement where the backend offers it.
- [-] **F3 (code, mem audit q-filter loses compressed rows — `crates/gyre-server/src/mem.rs:2179-2226` vs 2348-2371):** `audit_entry_matches` matches only `e.detail`; `compress_details_before` moves the payload to `detail_zstd` and sets `detail = Null`, after which compressed rows match no `q` term. The port contract written by this task (gyre-ports/src/audit.rs) requires "zstd-compressed details decompressed transparently so compressed rows stay searchable", which the SQLite/PG adapters implement (`detail_matches` decompresses); the mem adapter silently diverges — a parity gap of exactly the class `check-mem-port-contracts` exists to prevent (it only covers create-duplicate constraints, so this is not caught mechanically). Production SQLite/PG paths are correct; pure-mem deployments and mem-based tests lose q recall on compressed rows. **Repair:** decompress `detail_zstd` in `audit_entry_matches` when `detail` is Null, mirroring the SQL adapters.

## Minor (non-blocking, recorded for completeness)

- `JobRunLog` has no per-run size cap; `repo_maintenance` emits ≥1 line/repo per daily run and the whole `Vec<String>` is persisted per run for the retention period — disk growth on repo-heavy deployments (also shipped in full on each 20-row API read).
- Vault `is_auth_rejected` (vault/mod.rs:725-730) triggers AppRole re-login by substring-matching "HTTP 403"/"HTTP 401" in rendered error chains — brittle; the typed `VaultPermissionDenied` plus a typed 401 would be safer.
- Audit migration 000070 backfills tenant only via workspaces/users; the runtime `record()` derivation additionally resolves agent-principal events via the agent's tenant, so pre-migration agent events with no workspace/user stay NULL and are invisible to tenant-scoped admin queries (documented NULL-tenant contract; a pre-migration blind spot, not a regression).
- Vault `resolve_for_agent_as` yields `Ok(vec![])` when the agent's policies deny every scope — indistinguishable from "no secrets exist" and unlogged; a misconfigured `gyre-agent` role silently delivers nothing (spawn logs resolution errors only on transport failure).
- Docs: `docs/server-config.md` documents a default `GYRE_CLAUDE_MAX_REDIRECT_URI` of `/api/v1/oauth/claude-max/callback` but the code fails closed on unset/relative values; `docs/api-reference.md` says 302 where the code (correctly) emits 303.
- The sweep's fast-path local kill (in-memory backend present) performs no pid-identity verification — pid reuse within the server's own lifetime in the narrow window where the exit monitor errored and the stale detector already marked the agent Dead could SIGTERM an unrelated process; the identity check exists only on the restart-orphan and reconstructed paths.
- Server-logs ring is process-global and lost on restart — correct by spec ("recent server log events", durability required only for the audit trail), noted so it is not mistaken for the durable surface.
- OAuth enrollment start/complete emit `tracing::info!` only, not durable audit events, unlike other admin credential operations — consistency gap, not required by the task text.
