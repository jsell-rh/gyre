## Round 1 — findings

- [-] **F1 (major, code): one production notification-creation path bypasses channel fan-out.** `crates/gyre-server/src/workspace_ownership.rs` `notify_tenant_admins` (called by the scheduled `workspace_ownership::run_once` job via `jobs.rs:511`, and by `scim.rs:397` / user-removal paths) persists `WorkspaceOwnerless` notifications via `state.create_notification` and never calls `notification_dispatcher::dispatch_to_channels`. `AppState::create_notification` (lib.rs:602) only SSE-broadcasts; channel fan-out is call-site responsibility, and every other call site in the server does it. A tenant admin with email/webhook/Slack configured gets no channel delivery for an ownerless workspace. This contradicts the task's Shipped claim ("every production notification-creation path in gyre-server dispatches after the in-app record persists") and coverage row 16's "fans every persisted in-app notification to configured channels". The path arrived with the task-125 base, but task-112 closes §Delivery Channels with an explicit completeness claim and wired every other base path. Repair: dispatch in the `Ok` arm (or route through `notify_rich`) plus an emitter-path guard test asserting the outbox entry.
- [-] **F2 (major, spec accuracy): the team-lead routing amendment justifies the interim superset routing with a false premise.** The note added to `user-management.md` (and echoed in coverage row 17) states "Teams currently carry only `member_ids` with no lead field". The assigned base already ships `Team.lead: Id` — `user-management.md` §Team Management's own `Team` struct (line ~236), `gyre-domain/src/team.rs`, and base migration `2026-11-13-000062_team_slug_lead_membership` (which even backfills `lead` to the workspace Owner). The genuine gap is only the **repo→team mapping** (nothing links a repository to a team, so "the repo's team lead" / "dependent repo team leads" cannot be resolved). As written, the amendment directs the future narrowing at work that already exists ("until Teams gain a lead concept") and misstates the domain model in the spec of record. Repair: correct the note and coverage row 17 to name the actual gap (repo→team ownership mapping); the interim superset routing and deferral themselves are sound and can stand.
- [-] **F3 (moderate, coverage): §Who Gets Notified row "Spec drift detected → Spec owner" is neither implemented nor disclosed.** `SpecDriftDetected` (spec_patrol.rs `create_notifications_for_error_findings`) routes to workspace Admin/Developer members; `MetaSpecDrift` (reconciliation sweep / `emit_reconciliation_completed`) routes to Admins/Owners. Neither resolves the spec's owner, although the spec ledger carries `owner` per spec (`gyre-domain/src/spec_ledger.rs:35`, e.g. `user:jsell`) and spec_patrol already loads `spec_ledger.list_all()` while resolving workspace context. No spec amendment records the deviation, yet coverage row 17 marks §Who Gets Notified implemented and the acceptance criterion "Routing table maps events to correct recipients per spec" is claimed satisfied. The recipient choice predates this task, but closing the section is this task's act. Repair: route drift notifications to the spec's owner (resolving `user:`/`team:` owner refs), or amend the row with a recorded interim routing exactly as was done for the team-lead rows.
- [-] **F4 (minor, pre-existing in base, recorded for consistency): two notification emitters still pass a literal `"default"` tenant_id** — `spawn.rs` `complete_agent` (~line 2430, AgentCompleted) and `merge_processor.rs`'s circuit-breaker escalation (~line 709, AgentEscalation to all workspace members). The candidate itself treated this exact pattern as a defect class and fixed it in `fail_agent` and `notify_mr_reverted` (both previously passed `"default"`), so these siblings are inconsistent leftovers on notification paths within the sections being closed. (The circuit-breaker path also bypasses `escalation_recipients`, but its all-members fan-out is a superset — no specced recipient is missed.)
