## Verified (independently, at HEAD 28ddc3ae)

- **Selection is real and pure.** `manifest_gates_for_mr(manifest, spec_ref)` (gate_executor.rs:101) resolves the manifest `SpecEntry` matching the MR's `spec_ref` path (`specs/`-prefix and bare-path normalization), returns its `gates:` entries with `min_attestation_level` defaulting to 1, `stack_hash`, and `spec_path`; dedupes repeated personas (first wins). Four unit tests assert on the resolved gate set directly.
- **Sourcing reuses task-193's reader.** `resolve_manifest_gates_for_mr` calls `crate::spec_registry::read_manifest(repo_path, "HEAD")` — no second manifest reader. HEAD matches the policy source of the other production callers (api/specs.rs:1020, api/specs_assist.rs:1151); the spec_ref SHA is the ledger's blob SHA and cannot address `specs/manifest.yaml`, so HEAD is the correct treeish.
- **Union without double-spawning.** Repo-level gates whose persona is covered by a manifest gate are skipped (manifest gate wins — it carries the constraints); every other repo-level gate still runs. Tests: manifest gates for both personas; no-`spec_ref` and no-manifest repos run exactly today's repo gates; same-persona overlap runs the persona exactly once; re-enqueue reuses the running gate agent.
- **Real persona gate, never the stub.** Manifest gates materialize as `AgentReview` `QualityGate`s with deterministic ids (`manifest-gate:<repo>:<spec>:<persona>`), run through the existing `GateResult` flow, and execute `run_persona_review_gate`: passes only on an `Approved` review from an agent running the named persona (KV `agent_personas`) whose workload attestation meets `min_attestation_level` and, when pinned, an exact `stack_hash` (level derived from the real `workload_attestations` record via `derive_attestation_level`); latest-verdict-per-reviewer with approval-wins; final `ChangesRequested` rejects; otherwise fails closed at the gate timeout. The no-command/no-constraints repo-gate arm fails closed (base behavior) — no auto-pass anywhere.
- **Merge-blocking participates.** Manifest `GateResult`s live in the same `gate_results` store; `check_gates_for_mr` defaults unknown gate ids to `required = true`, so pending holds the MR and a failure errors the check. Tested both ways.
- **Forge spawn is real (spec §16).** `spawn_manifest_gate_agent` creates a real `Agent` record, writes the persona to `agent_personas`, mints a `review:submit`-scoped EdDSA JWT (fail-closed on mint/registration failure — no unscoped fallback), dispatches a `ReviewRequest` with the attestation constraints in the payload, and launches the runtime through the platform's single launch path (`api::spawn::launch_agent_workload`) with `GYRE_AUTH_TOKEN` + review-context env and a workload attestation recorded at launch. Tests assert the launched process received the token/env (real process env dump), the attestation level ≥ 1, the JWT scope/sub/traceability, and the ReviewRequest payload constraints. Teardown kills the runtime through the owning `spawned_backends` backend (regression-tested against LocalTarget misuse), removes registry entries, revokes the token, stops the record.
- **Reviewer identity binding hardened.** `submit_review` binds every agent-token principal to the verified token subject; human non-admin principals may record only under their own verified `user_id` (never the user-controlled display name); Admin may record on behalf. Blocks the forged-reviewer attack against persona/attestation constraints. Tested (forged review not persisted). The new spawn `persona` field is validated fail-closed against the Approved persona chain before any state is created, so a spawn-capable caller cannot mint an unvetted persona identity into `agent_personas`.

## Findings

- [ ] **F1 (code, doc-accuracy on a security-relevant decision): false counterfactual in the manifest-wins rationale.** `crates/gyre-server/src/gate_executor.rs`, `trigger_gates_for_mr` comment (~lines 646-652) and the `trigger_gates_manifest_gate_wins_over_repo_gate_for_same_persona` test comment (~lines 4502-4506 and 4517) claim that skipping the manifest gate — keeping the repo-level gate — "would let a no-command repo-level AgentReview gate auto-pass and merge without them", and describe the fixture's no-command repo gate as "the legacy configuration whose stub auto-passes". There is no auto-pass stub in the current AgentReview path. The valid rationale (the manifest gate carries `min_attestation_level`/`stack_hash` the repo-level gate cannot enforce) stands on its own; the false clause misstates the safety tradeoff of the precedence decision in the direction that justifies the less conservative option — the same defect class as the two previous rounds' blocking findings on this surface. Reproduce: read the cited comments against the `None =>` arm of `run_agent_review_gate` (gate_executor.rs ~1085-1090) or run `git show b9487b1b:crates/gyre-server/src/gate_executor.rs` and inspect its `run_agent_review_gate`. Fix: rewrite both comments to the true rationale — repo-gate-wins would fail closed for a no-command gate (blocking, not merging) and would run a command-based reviewer without the manifest's attestation constraints; manifest-wins is chosen because the manifest is the reviewed per-spec policy artifact carrying those constraints.
