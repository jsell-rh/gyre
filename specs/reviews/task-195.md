### Diff inspection (gate_executor.rs +~2100, spawn.rs, merge_requests.rs, abac_middleware.rs, mcp.rs, ralph_loop.rs, signal_chain.rs, docs, coverage, web)

- **Selection (pure, per plan/AC):** `manifest_gates_for_mr(Option<&SpecManifest>, Option<&str>) -> Vec<ManifestGateSpec>` (gate_executor.rs:101) — resolves the entry whose normalized path matches the `spec_ref` path (leading `specs/`/`./`/`/` stripped; bare no-`@sha` paths handled, matching spawn.rs's two recorded forms at spawn.rs:2343/2346), returns its `gates:` entries with `min_attestation_level` defaulting to 1 and `stack_hash` carried; empty for no manifest / no spec_ref / no match / no gates; repeated personas within an entry deduped (first wins).
- **Sourcing:** `resolve_manifest_gates_for_mr` reads the manifest via task-193's `read_manifest` (no second reader — grep confirms the only other use is task-193's approval resolver) at repo **HEAD**. The deviation from "prefer the spec SHA" is justified and documented in-source: the SHA in `spec_ref` is the spec file's *blob* SHA (ledger `current_sha` from `git rev-parse <commit>:<path>`, spec_registry.rs:1100-1111), which is not a treeish and cannot address `specs/manifest.yaml`; HEAD is the same policy source task-193's approval resolver uses. Consistent with the task plan's escape hatch ("or repo HEAD if you determine HEAD is the correct policy source").
- **Union, not replace; no double-spawn:** `trigger_gates_for_mr` keeps all repo-level gates except those whose persona (path form normalized via `persona_name_from_path`) is covered by a manifest gate, then adds each manifest gate. On persona overlap the **manifest** gate wins (it carries the attestation constraints); persona still runs exactly once. Gates with `persona: None` are always kept (`is_none_or`). No-spec-ref / no-manifest / no-gates paths run repo gates only — both covered by dedicated regression tests (`trigger_gates_no_spec_ref_runs_repo_gates_only`, `trigger_gates_repo_without_manifest_runs_repo_gates_only`).
- **Merge-blocking visibility (no parallel results table):** each manifest gate materializes as an `AgentReview` `QualityGate` with deterministic id `manifest-gate:<repo>:<spec_path>:<persona>` and a `Pending` `GateResult` saved to the same `gate_results` store; `check_gates_for_mr` (gate_executor.rs:2316) defaults unknown gate ids to `required = true`, so failed/pending manifest gates block the merge exactly like repo gates. Proven by `trigger_gates_failed_manifest_gate_blocks_merge` (asserts `Err` naming the manifest gate id) and `trigger_gates_runs_manifest_gates_for_spec_ref_mr` (asserts `Ok(false)` while gates run).
- **Real persona path, never the auto-pass stub:** `run_agent_review_gate` routes command-less gates carrying `GateConstraints` to `run_persona_review_gate`, which polls `evaluate_persona_reviews` and FAILS closed at timeout ("no Approved review … within Ns") when no qualifying review exists — `persona_gate_fails_without_qualifying_review` explicitly kills any regression to the legacy auto-pass stub. Approval requires: reviewer persona match (`agent_personas` KV, both key forms), `attestation_level >= min_attestation_level` via the same `derive_attestation_level` task-193 uses, and exact `stack_hash` match when pinned (`check_reviewer_attestation`; missing workload → level 0 → fail; empty fingerprint vs pinned → mismatch → fail — fail-closed in both degenerate cases). Latest-verdict-per-reviewer with approval-wins semantics, matching `check_review_verdict`/mem `is_approved`; superseded-approval and stale-veto cases each pinned by a test.
- **Forge spawns the gate agents (spec §16's core sentence):** `spawn_manifest_gate_agent` creates a real workspace-scoped `Agent` (`gate-<persona>-<mr-id>`, `spawned_by: "server"`), records the persona in `agent_personas` (a production writer for the namespace the persona check reads), mints a **`review:submit`-scoped** EdDSA JWT (fail-closed on mint/register failure — no unscoped fallback), dispatches a `ReviewRequest` message carrying the constraints, and launches the runtime through the platform's compute-target machinery (`launch_agent_workload` — the same dispatch `spawn_agent_core` uses), delivering the token via `GYRE_AUTH_TOKEN` and recording a workload attestation so the agent's own reviews derive at level ≥ 1. Idempotent while the gate runs (re-enqueue reuses the Active agent — tested); teardown kills the runtime through the backend that owns the handle (container/Pod/remote-pid — `gate_agent_teardown_routes_kill_through_registered_backend` proves a LocalTarget regression would be caught), removes the registry entries, revokes the token with an audit event, and keeps the record for attribution.
- **Reviewer identity binding closes the forgery hole:** `submit_review` binds every agent-token principal to its verified token subject (`agent_tokens` KV key = server-assigned agent id — verified in `authenticate_token`, auth.rs:1244), and restricts human principals' request-body `reviewer_agent_id` to their own verified `user_id` (Admin-only on-behalf). Comparing against `user_id` rather than `agent_id` is correct — for user JWTs `agent_id` is the user-controlled display name (auth.rs:1527). The two dashboard flows that posted hardcoded pseudo-ids now submit the caller's own identity (`selfReviewerId()`, fail-closed to a server-rejected legacy id on lookup failure). The inbox poll route added to `REVIEWER_ALLOWED_ROUTES` is safe: `poll_messages` restricts non-admin callers to their own inbox (messages.rs:355).
- **Bare-persona spawn field is validated, not trusted:** `spawn_agent_core` resolves `req.persona` through `resolve_persona_in_chain` (Approved-only, same posture as `persona_slug`) BEFORE any state is created; only the validated name reaches `agent_personas`/`GYRE_PERSONA`. `gyre_spawn_worker` MCP param and re-spawn paths funnel through the same core. The forge's manifest-sourced writer bypassing this validation is correct — its persona comes from the reviewed manifest, not a caller.
