## Findings

None blocking. The candidate satisfies every acceptance criterion with real production behavior:

- **Selection is real and pure.** `manifest_gates_for_mr(Option<&SpecManifest>, spec_ref)` resolves the manifest entry matching the `spec_ref` path (normalizing `specs/` prefixes and bare no-`@sha` paths), returns its `gates:` entries with `min_attestation_level` defaulted to 1, dedupes repeated personas (first wins), and is empty for every missing-input case — asserted directly by four selection tests.
- **Sourcing matches task-193's policy source.** `resolve_manifest_gates_for_mr` reads `specs/manifest.yaml` via task-193's `read_manifest` (no second reader) at repo HEAD — the same source `resolve_new_approval_status` uses, and the spec_ref SHA is a blob SHA that cannot address the manifest. The task explicitly permits this.
- **Union without double-spawning.** `trigger_gates_for_mr` keeps all repo-level gates except those whose persona a manifest gate covers, and runs each manifest gate once. On persona overlap the manifest gate wins (it carries the constraints a repo-level gate cannot enforce); tested to produce exactly one run per persona with the manifest gate id.
- **Real persona path, never the stub.** Manifest gates materialize as `AgentReview` gates with `command: None` + `GateConstraints`, routing to `run_persona_review_gate`, which polls for an `Approved` review from an agent running the named persona whose workload attestation satisfies `min_attestation_level` (via the same `derive_attestation_level` task-193 uses) and an exact `stack_hash` match when pinned. Fails closed at timeout; `persona_gate_fails_without_qualifying_review` kills any regression to the auto-pass stub.
- **Merge-blocking is the existing flow.** Manifest-gate `GateResult` rows flow through `check_gates_for_mr` (unknown gate ids default `required = true`): pending holds the MR, failed blocks it — asserted by both a trigger integration test and a direct blocking test. No parallel results table.
- **Forge really spawns gate agents (§16).** Per manifest gate: an `Agent` record (workspace-scoped, idempotent per MR+persona while running), persona in `agent_personas`, a `review:submit`-scoped EdDSA JWT minted fail-closed (mint/registration failure stops the agent, never an unscoped fallback), a dispatched `ReviewRequest` carrying the constraints, and a runtime process launched through the platform's shared `launch_agent_workload` (token via `GYRE_AUTH_TOKEN`, workload attestation recorded). Teardown kills the runtime through the backend that owns the handle, removes the registry entries, revokes the token with an audit event, and keeps the record for attribution.
- **No regression surface.** No-`spec_ref` and no-manifest cases run exactly the repo-level gates (tested). `submit_review` now binds every agent-token principal to its verified token subject and restricts human principals to their own verified `user_id` (Admin excepted) — closing the forged-reviewer hole against the manifest constraints; the dashboard's two human review flows submit the caller's own identity. The bare `persona` spawn field is validated fail-closed through `resolve_persona_in_chain` before any state is created, so a spawn-capable caller cannot mint a gate-satisfiable persona identity. The task-134 lookalike-scope probe was updated to the stronger semantics (route allow-list discriminator + identity binding) — it asserts more, not less.

**Non-blocking observations (recorded, not defects):**

- A manifest gate with `min_attestation_level: 3` cannot be satisfied by a locally-launched gate agent (its launch-time attestation derives at level 1); the gate fails closed until a container-launched (level 3) persona agent reviews. This is the constraint enforcing itself, not a gap.
- Re-enqueue after a terminal (failed) queue entry creates fresh `GateResult` rows while old failed rows persist, so `check_gates_for_mr` keeps blocking until the retry's gates pass and the old rows age out of consideration via the queue lifecycle — identical to the pre-existing repo-level gate behavior (unchanged by this task; `enqueue_core` already guards double-trigger while queued).
- Generated `web/dist/` was not regenerated in this checkpoint — owned by the deterministic verifier per process; authored frontend source and tests reviewed here and pass.
