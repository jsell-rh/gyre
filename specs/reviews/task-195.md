## Verified against acceptance criteria

- **Selection is real and pure**: `manifest_gates_for_mr(manifest, spec_ref)` normalizes `specs/` prefixes and bare (no-`@sha`) paths, dedupes repeated personas within an entry, defaults `min_attestation_level` to 1, carries `stack_hash`/`spec_path`. Empty for no manifest / no spec_ref / no matching entry / no gates — no-regression criterion covered by two dedicated tests.
- **HEAD (not spec_ref SHA) as the manifest policy source is correct**: the SHA in `spec_ref` is the spec file's blob SHA (ledger `current_sha` from `git rev-parse <commit>:<path>`), which cannot address `specs/manifest.yaml` via `git show`; task-193's `resolve_new_approval_status` reads the manifest at HEAD for the same reason. Documented in code. Single manifest reader reused (`spec_registry::read_manifest`); no second reader added.
- **Union + dedup**: repo-level gates keep running; on persona overlap the manifest gate wins (it is the only one of the pair that can enforce the attestation constraints) and the repo-level duplicate for that persona is skipped — persona runs exactly once (test asserts exactly one security result, and it is the manifest gate).
- **Real persona path, not the auto-pass stub**: `run_agent_review_gate` routes constrained gates to `run_persona_review_gate`; passes only on an Approved from a persona-matching reviewer (KV `agent_personas`) whose derived workload-attestation level ≥ `min_attestation_level` and, when pinned, exact `stack_hash` — using task-193's `derive_attestation_level`, no invented levels. Fails without a review (kills stub regression), on below-minimum attestation, on stack-hash mismatch, ignores other personas. Verdict ordering is latest-per-reviewer, approval-wins in both directions (two mutation-sensitive tests). Pass/fail participates in `check_gates_for_mr` (unknown gate ids default `required=true` — pre-existing, verified at base): pending manifest gates hold the MR (`Ok(false)`), a failed one blocks with `Err` naming the gate.
- **Forge-spawned gate agents that execute (§16; prior R3 rounds)**: per manifest gate, a real `Agent` record (Active, workspace-scoped, `spawned_by: "server"`), persona in `agent_personas`, scoped EdDSA JWT in `agent_tokens` (authenticates via the standard auth path — signature + KV registration verified in auth.rs), `ReviewRequest` dispatched with the constraints, and the runtime **launched through the platform's compute-target machinery** — `api::spawn::launch_agent_workload`, extracted verbatim from `spawn_agent_core` (line-by-line diff review; container/ssh/local dispatch, process registry, exit monitors, audit events, workload attestation all moved, `spawn_agent_core` semantics unchanged). ## Non-blocking observations (recorded, not findings)

- Teardown kills the runtime via `LocalTarget::kill_process` regardless of the launch target — for container/SSH handles this is a no-op (pid None), mirroring the pre-existing admin kill path (admin.rs:291) exactly; token revocation remains the containment. Platform-wide pattern, not introduced here.
- A manifest gate with `min_attestation_level ≥ 2` is satisfiable only by container-launched runtimes (level 3) or operator-spawned persona workers: a locally-launched gate agent derives level 1, and `POST /agents/:id/stack` writes `agent_stacks`, which only the *launch* path reads into `workload_attestations` — a live agent's stack self-report never raises its derived level. This is the platform's pre-existing attestation model (task-193's agent-approval validation has the identical shape) and the gate fails closed, never open. Worth a future platform task if level-2 self-attestation is meant to be reachable locally.
- `std::env::set_var("GYRE_AGENT_COMMAND", ...)` in `trigger_gates_launches_gate_agent_runtime_with_token` is process-global; concurrent trigger tests may launch the dump script as their stand-in runtime during that window (benign today — full suite green — but a latent flake source if a future test asserts on the default command).
- Concurrent `find_by_name` → `create` for gate-agent idempotency has the same check-then-create race `spawn_agent_core` has always had; the deterministic name (contains the MR UUID) makes collisions practically impossible.
- The shipped notes' test counts transpose e2e_ralph_loop (1) and auth_integration (21); immaterial — all pass.
