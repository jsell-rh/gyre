Findings (blocking):

1. **[spec] The forge-spawned gate agent never executes — the manifest-gate pass path is still unreachable in production** (`crates/gyre-server/src/gate_executor.rs:204-333`, `docs/agent-protocol.md` "Manifest-declared gates" step 2). `spawn_manifest_gate_agent` creates an Agent record, registers a JWT in `agent_tokens`, records the persona, and dispatches a `ReviewRequest` — but launches nothing: no `ComputeTarget::spawn_process` (the platform's execution model, used by every `spawn_agent_core` path at api/spawn.rs:865/1052/1103), no local process, no container. The token is never delivered to any runtime — normal spawns inject it into the launched container's env (`GYRE_AUTH_TOKEN`, spawn.rs:724) or return it to the caller (orchestrator spawn); the gate agent's token sits in server-side KV with no API that returns or delivers it (admin surface has no generic KV read). Nothing can authenticate as the gate agent, poll its `ReviewRequest`, or submit its verdict. The documented protocol — "the gate agent runtime authenticates with its token, polls the message (`gyre_message_poll`), fetches the MR diff, reviews, and submits its verdict" — describes behavior that cannot occur, and the §16 coverage row's "the forge spawns a real gate agent per manifest gate" overstates what runs. Net production behavior: every manifest-declared persona gate waits its timeout (default 300s) then fails closed — **every MR referencing a spec whose manifest declares gates is blocked from merging**, unless an operator separately spawns a persona worker (new `SpawnAgentRequest.persona`) and has it review. Spec §16's "Forge spawns security gate agent and accountability gate agent for this MR" is not genuinely implemented; the R3 repair moved the identity provisioning but not the execution. Fix direction: launch the gate agent through the existing compute-target machinery (reuse `spawn_agent_core` or `ComputeTarget::spawn_process` with the token/persona/review context in env) so a real runtime receives the token and its workload attestation is created — or route the `ReviewRequest` to a real executing agent instead of an inert record; and until then, do not document an executing runtime protocol.
2. **[code] The spawned gate agent could not satisfy its own gate even if it executed** (`crates/gyre-server/src/gate_executor.rs:204-333` vs `:118`). The spawn path creates no workload attestation (unlike `spawn_agent_core`, which attests the launched PID/container at api/spawn.rs:1154-1183 — `workload_attestations` appears in gate_executor.rs only as a read at :1124 and test fixtures). `derive_attestation_level(None)` returns 0 (constraint_check.rs:905-907), below the manifest-schema default `min_attestation_level` of 1 (gate_executor.rs:118): the gate agent's own `Approved` review would be a permanent near-miss ("attestation level 0 < required 1") for every default-configured manifest gate. The spawn is internally inconsistent with the enforcement it feeds. (Note: `run_persona_review_gate`'s teardown also never fires for it in the intended flow, since no verdict ever arrives before timeout — the timeout path does tear it down.)
3. **[code, medium] Manifest-wins dedup can disable a working gate in favor of one that cannot pass** (`crates/gyre-server/src/gate_executor.rs:388-401`). When a repo-level AgentReview gate with a real `command` (a genuinely executing reviewer today) shares a persona with a manifest gate, the dedup now skips the working repo-level gate and runs the manifest gate — which per findings 1-2 cannot pass in production. For such repos, an MR referencing a spec with manifest gates regresses from "command gate reviews it" to "blocked 300s then failed". The R2 rationale (manifest attestation constraints must be enforced) is sound *once the manifest gate's pass path actually works*; until finding 1 is fixed, the dedup direction converts functional configurations into deterministic blockers.

Non-blocking observation: `SpawnAgentRequest.persona` is caller-supplied and becomes the agent's persona in `agent_personas`, the namespace gate persona matching trusts. Any principal with spawn rights can therefore mint a persona-matching reviewer; the substantive control remains the (server-created, non-caller-controlled) workload attestation level and pinned stack hash. Consistent with the platform's agentic trust model, but worth an explicit note in the docs if persona gates are meant to carry security weight beyond attestation constraints.
