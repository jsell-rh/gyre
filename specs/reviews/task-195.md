## What the candidate ships (verified in source)

- **Pure selection helper** `manifest_gates_for_mr(Option<&SpecManifest>, Option<&str>) -> Vec<ManifestGateSpec>` (`gate_executor.rs:101`): splits `spec_ref` at the last `@` (bare no-SHA paths also handled, matching what `spawn.rs` records for un-ledgered specs), normalizes `specs/`-prefix differences against manifest entry paths, returns the matching entry's `gates:` with `min_attestation_level` defaulting to 1 and `stack_hash` optional; empty for absent manifest / absent spec_ref / no matching entry / no gates; repeated personas within an entry dedupe (first wins).
- **Sourcing** `resolve_manifest_gates_for_mr` (`gate_executor.rs:153`) reuses task-193's `crate::spec_registry::read_manifest` at repo HEAD — no second manifest reader added (`spec_registry.rs` itself is untouched by this task). HEAD (not the embedded SHA) is justified: the ledger's `current_sha` is a blob SHA, not a treeish, matching task-193's policy source.
- **Union with manifest-wins dedup** in `trigger_gates_for_mr` (`gate_executor.rs:628`): repo-level gates still run; a repo gate whose persona (`persona_name_from_path`) is covered by a manifest gate is skipped so the persona runs exactly once under the manifest's constraints. Repo gates with no persona are unaffected.
- **Real persona gate, never the stub**: each manifest gate materializes as a non-persisted `QualityGate` with deterministic id `manifest-gate:<repo>:<spec_path>:<persona>` and a Pending `GateResult` row; `run_agent_review_gate` routes it (no command + constraints present) to `run_persona_review_gate`, which passes only on an `Approved` review from an agent running the named persona whose workload attestation satisfies `min_attestation_level` and, when pinned, an exact `stack_hash` match (`check_reviewer_attestation`, level derived via `constraint_check::derive_attestation_level` — never invented). No qualifying review → gate FAILS at timeout (fail-closed), and `check_gates_for_mr` (unknown gate ids default `required=true`) blocks the merge — the merge processor's two call sites are unchanged and see these results. No parallel results table.
- **Forge-spawned gate agents** (`spawn_manifest_gate_agent`): real `Agent` record per (MR, persona), persona written to the `agent_personas` KV namespace, `review:submit`-scoped EdDSA JWT (mint failure fails the spawn closed — no unscoped fallback token), ReviewRequest dispatched with the attestation constraints, runtime launched through the platform's compute-target machinery (`api::spawn::launch_agent_workload`, token via `GYRE_AUTH_TOKEN`, workload attestation recorded so the agent's own reviews can satisfy level ≥ 1). Idempotent per (MR, persona) while running; teardown kills the runtime via the backend that owns the handle (`spawned_backends` routing, not a bare LocalTarget kill), removes both registry entries, revokes the token, and keeps the record for attribution.
- **Reviewer identity binding hardened** (`api/merge_requests.rs submit_review`): every agent-token principal is bound to its verified token subject (the per-agent token path keys `agent_id` by the KV entry the token resolves to, so this is the verified identity); human principals may use a body reviewer id only when it equals their own verified `user_id` (Admin may record on behalf). The frontend (`selfReviewerId()`) resolves the caller's own id instead of the legacy `'human'`/`'human-reviewer'` pseudo-ids. `api/spawn.rs` validates the new bare `persona` spawn field fail-closed against an Approved persona in the repo/workspace/tenant chain before any state is created — a spawn-capable caller cannot mint a gate-satisfying persona identity.
- **Reviewer allow-list tightening**: the REST agent-inbox route is kept off `REVIEWER_ALLOWED_ROUTES` (least privilege; the ReviewRequest reaches the runtime via launch env + `/mcp gyre_message_poll`, which is own-inbox by token subject). The unrouted legacy `agent_messages` module and `messages.rs` dead types were deleted; a new probe test (`scoped_review_token_cannot_read_agent_inbox_route`) proves the 403 with builtin policies seeded so only the allow-list explains the denial.

## Test-quality assessment (counterfactual)

The acceptance-required "fails if manifest-gate sourcing is removed" property holds structurally: `trigger_gates_runs_manifest_gates_for_spec_ref_mr` seeds a real git repo with a committed `specs/manifest.yaml`, an MR with `spec_ref`, and an **empty** repo-level gate store, then asserts exactly 2 `manifest-gate:` GateResult rows (security + accountability) — removing `resolve_manifest_gates_for_mr` (or the helper) yields 0 rows and fails the assertion; `trigger_gates_spawns_gate_agents_for_manifest_gates` and `trigger_gates_manifest_gate_wins_over_repo_gate_for_same_persona` fail likewise. The pure-helper tests assert the resolved gate set directly (persona, default level 1, pinned level/stack_hash, empty-input cases, intra-entry dedupe). The persona-gate tests kill the specific regressions they name: no-review → Failed (kills the auto-pass stub), attestation level 0 < min → Failed with reason, stack-hash mismatch → Failed, other-persona approval ignored, latest-verdict-per-reviewer in both directions, teardown (token revoked, status Stopped, record kept), backend-routed kill (a LocalTarget-kill regression fails the alive-assertion), scoped-token subject/scope/task_id claims, and the launch contract (GYRE_AUTH_TOKEN/persona/MR/gate/min-level reach the launched process; workload attestation recorded with a PID and level ≥ 1). `check_gates_for_mr` merge-blocking is asserted both for pending (Ok(false) holds the MR) and failed (Err naming the manifest gate) results.
