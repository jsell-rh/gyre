### Implementation verification (all verified by source inspection at the candidate)

- **Selection (pure):** `manifest_gates_for_mr(manifest, spec_ref)` — matches the manifest entry whose normalized path equals the spec_ref path (leading `./`, `/`, `specs/` stripped; bare no-`@sha` paths accepted), returns `ManifestGateSpec {persona, min_attestation_level (default 1), stack_hash, spec_path}`, dedupes repeated personas (first wins). Directly unit-tested on the resolved set (4 tests), satisfying the AC's "pure helper, assert on the resolved gate set".
- **Sourcing:** `resolve_manifest_gates_for_mr` reads `specs/manifest.yaml` at HEAD via task-193's single `read_manifest` reader (no second reader added — verified by grep). HEAD is the correct policy source: the SHA in `spec_ref` is the ledger's *blob* SHA, not a treeish, and task-193's approval resolver (`api/specs.rs:1020`) also reads HEAD.
- **Union, don't replace:** repo-level gates still run; on persona overlap the manifest gate wins and the repo-level duplicate is skipped (the manifest gate carries the attestation constraints; skipping it instead would let a no-command repo-level gate auto-pass). Tested (`trigger_gates_manifest_gate_wins_over_repo_gate_for_same_persona` asserts the persona runs exactly once, as the manifest gate).
- **Real persona path, never the stub:** a manifest gate materializes as an `AgentReview` `QualityGate` (deterministic id `manifest-gate:<repo>:<spec_path>:<persona>`, not persisted to the gate store — per-MR selection, not repo config) and routes to `run_persona_review_gate`, which passes only on an `Approved` review from a persona-matching agent whose workload attestation satisfies `min_attestation_level` and, when pinned, an exact `stack_hash` match; otherwise it fails closed at its timeout, naming the missing constraint. `persona_gate_fails_without_qualifying_review` kills any regression to the auto-pass stub; attestation-level and stack-hash mismatch each have a failing test.
- **Merge-blocking:** manifest gate results flow through the ordinary `GateResult` store (no parallel table); `check_gates_for_mr` defaults unknown gate ids to `required = true`, so Pending holds the MR and Failed blocks it — both asserted in tests (`trigger_gates_runs_manifest_gates_for_spec_ref_mr`, `trigger_gates_failed_manifest_gate_blocks_merge`).
- **Forge-spawned gate agents (spec §16):** `spawn_manifest_gate_agent` creates a real `Agent` record, writes the persona to `agent_personas` (the namespace the persona check reads), mints a `review:submit`-scoped EdDSA JWT (fails closed on mint/registration failure — no unscoped fallback), dispatches a `ReviewRequest` through `state.messages`, and launches the runtime through the platform compute-target machinery (`api::spawn::launch_agent_workload`) with the token in `GYRE_AUTH_TOKEN` plus review-context env and a recorded workload attestation. Re-enqueue reuses the still-Active agent (no double-spawn; tested). Teardown kills the runtime via the backend that owns the handle (`spawned_backends` routing — regression-tested with a Container-backend fixture a LocalTarget kill would wrongly kill), revokes the token, and Stops the record. Tests assert the launched process received the token and env (`trigger_gates_launches_gate_agent_runtime_with_token`), and that the token is a scoped reviewer JWT with the gate as `task_id` (`gate_agent_token_is_scoped_reviewer_jwt`).
- **Reviewer identity binding:** `submit_review` binds agent-token principals (any scope) to the verified token subject (`auth.agent_id` is the server-minted `agent_tokens` KV key — verified in auth.rs); humans may use a body `reviewer_agent_id` only when it equals their own verified `user_id` (never the user-controlled display name), Admin excepted. Three tests incl. forgery attempts from a non-admin human and an ordinary agent JWT. The web review flows were updated to send the caller's own id (`selfReviewerId`), fail-closed documented.
- **Bare-persona spawn (`persona` field):** fail-closed validation against Approved personas in the scope chain before any state is created; the validated name is what gets recorded in `agent_personas`. Positive + negative tests (unknown and Pending personas reject with no orphaned state).
- **No-regression paths:** no `spec_ref` → repo gates only; `spec_ref` but no manifest → repo gates only. Both tested.

### Findings (blocking, doc-accuracy on security surfaces — the runtime posture is safe)

1. **`crates/gyre-server/src/abac_middleware.rs:66-72`** — the doc comment on `REVIEWER_ALLOWED_ROUTES` still claims "The inbox poll route lets a forge-spawned manifest-gate agent receive its ReviewRequest over REST (the handler restricts non-admin callers to their own inbox …)". 2. **`crates/gyre-server/src/gate_executor.rs` (spawn_manifest_gate_agent token comment), `docs/agent-protocol.md` ("Manifest-declared gates", step 3), `crates/gyre-server/tests/task134_review_probe.rs:213`** — these assert `GET /api/v1/agents/:id/messages` "has no caller-identity check" and would let a scoped token "drain and clear any agent's inbox". The handler actually routed at that path is `messages::poll_messages` (api/mod.rs:293, unchanged since f2539d20 and identical at the base and at prior candidate 272427e4), which enforces own-inbox for non-admin callers (messages.rs:355-360) and is non-destructive; the no-check drain-and-clear handler (`agent_messages::get_messages`, kv_store `agent_messages` namespace) is unrouted dead code (no route registration references it anywhere in `crates/`). The prior round's finding misidentified the handler; this repair enshrined that misidentification as fact in three places while the shipped notes claim the docs were "corrected". The route is still denied to scoped tokens by the allow-list (which is what the regression test actually proves), so nothing is exploitable — but the documented security rationale is false. State the true rationale (least-privilege: delivery is via launch env + /mcp; the routed handler does enforce own-inbox), and consider deleting or routing the dead `agent_messages` handlers that caused the confusion.
