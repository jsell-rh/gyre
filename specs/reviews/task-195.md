## Verified working (no findings)

- **Selection is real and pure.** `manifest_gates_for_mr(Option<&SpecManifest>, Option<&str>) -> Vec<ManifestGateSpec>` resolves the manifest entry whose normalized path matches the `spec_ref` path (leading `specs/`/`./`/`/` stripped; bare no-`@sha` paths handled), returns its `gates:` entries with `min_attestation_level` defaulting to 1, `stack_hash`, and the declaring `spec_path`; empty for no manifest / no spec_ref / no match / no gates; repeated personas within an entry dedupe (first wins). Sourcing goes through task-193's `read_manifest` (no second reader), at repo HEAD — correctly justified: the `spec_ref` SHA is the ledger's blob SHA (not a treeish), and HEAD matches task-193's policy source.
- **Union without double-spawning.** `trigger_gates_for_mr` keeps every repo-level gate except those whose persona is covered by a manifest gate, and runs each manifest gate. Manifest-wins on persona overlap is the right dedup direction: the manifest gate is the one carrying the attestation constraints; skipping it instead would let a no-command repo-level AgentReview gate auto-pass without them. `persona_name_from_path` normalizes both `personas/security.md` and bare `security` forms.
- **Real persona path, never the auto-pass stub.** Manifest gates materialize as `AgentReview` `QualityGate`s (deterministic id `manifest-gate:<repo>:<spec_path>:<persona>`, deliberately not persisted to the repo gate store — correct, they are a per-MR selection) and route to `run_persona_review_gate` when constraints are present: it polls `evaluate_persona_reviews`, which passes ONLY on an `Approved` review from an agent running the named persona (persona from the `agent_personas` KV — the same source `build_agent_context` reads) whose workload attestation satisfies `min_attestation_level` (level derived from the real `workload_attestations` record via `derive_attestation_level` — never invented) and, when pinned, an exact `stack_hash` match. Otherwise it fails closed at the gate timeout with a message naming the missing constraints. Latest-verdict-per-reviewer with approval-wins mirrors `check_review_verdict` semantics, in both directions (tested).
- **Merge-blocking participation is real.** Manifest gates create `Pending` `GateResult` rows in the same `gate_results` store; `check_gates_for_mr` defaults unknown gate ids to `required = true`, so pending holds the MR in the queue (`Ok(false)`) and a failure blocks with `Err` naming the `manifest-gate:` id — no parallel results table.
- **Forge-spawned gate agents are real.** `spawn_manifest_gate_agent` creates an `Agent` record (workspace-scoped, `spawned_by: "server"`), writes the persona KV entry, mints a `review:submit`-scoped EdDSA JWT (fail-closed on mint/registration failure — no unscoped fallback), dispatches a `ReviewRequest` via the signed message bus, and launches the runtime through the platform's compute-target machinery (`launch_agent_workload`, extracted from `spawn_agent_core` — the refactor is faithful: the four-backend dispatch is moved verbatim, workload attestation recorded, `register_spawned_agent` retained). Teardown kills the runtime via the owning backend (`spawned_backends` routing — the admin-kill invariant, with a test that fails on a LocalTarget regression), removes the registry entry, revokes the token, and keeps the record for attribution. Re-enqueue reuses the still-Active agent instead of double-spawning.
- **Reviewer identity binding closes a real forgery hole.** `submit_review` now binds every agent-token principal to its verified token subject (not just `review:submit`-scoped ones), and human principals may use the body `reviewer_agent_id` only when it equals their own verified `user_id` (Admin may record on behalf). The comparison against `user_id` — never the user-controlled display name that fills `agent_id` — is correct. Web callers updated to `selfReviewerId()` with fail-closed fallback. Tests cover the agent forger, the non-admin human forger (403 + nothing persisted), own-identity, and Admin on-behalf.
- **Bare-persona spawn is fail-closed.** The new `persona` field on `SpawnAgentRequest`/`gyre_spawn_worker` is validated against `resolve_persona_in_chain` (Approved personas only) BEFORE any state is created, then recorded in `agent_personas` and injected as `GYRE_PERSONA`. Without this, any spawn-capable caller could mint a gate-satisfiable persona identity — the repair is genuine and tested (unknown → 400, Pending → 400, no orphaned rows, nothing recorded; approved → recorded + env-injected).
- **Tests are hard, not inflated.** The selection helper is asserted on directly (persona set, levels, stack hashes, dedupe, empty cases); `trigger_gates_runs_manifest_gates_for_spec_ref_mr` fails if manifest sourcing is removed; `trigger_gates_manifest_gate_wins_over_repo_gate_for_same_persona` asserts the exact surviving gate id and the single run; the no-spec-ref and no-manifest fixtures assert exactly-one-repo-gate with no spurious gates; the stub-killers (`persona_gate_fails_without_qualifying_review` etc.) fail if the path regresses to the legacy auto-pass; teardown tests use real spawned `sleep` processes and real backend routing.

## Findings

- [-] **F1 (major, security): `REVIEWER_ALLOWED_ROUTES` gains `AGENTS_MESSAGES_ROUTE` on a false enforcement claim — a least-privilege widening of confined gate-agent tokens with no functional payoff.** The added comment (and docs/agent-protocol.md §"Manifest-declared gates" step 3) claims "the handler restricts non-admin callers to their own inbox". `agent_messages.rs::get_messages` has no caller-identity check at all, the route's `resource.id` is suppressed (no policy can scope it), and every agent JWT — including `review:submit`-scoped gate-agent tokens — authenticates with role `Agent`, which the builtin `agent-scoped-access` policy (priority 700, `resource_types ["*"]`) allows. So a single-purpose gate-agent token can now drain AND clear any agent's KV inbox, where it was previously denied by the allow-list. The entry is also useless for its stated purpose: the ReviewRequest is persisted via `state.messages` (MessageRepository port), while this route drains the `kv_store` `"agent_messages"` namespace — a different store — so the documented REST poll path cannot deliver it (only `/mcp gyre_message_poll` and the launch env do). Full evidence with reproduce steps: `/tmp/stage/review-evidence/finding-f1-inbox-route-widening.md`.
  **Repair (small):** drop `AGENTS_MESSAGES_ROUTE` from `REVIEWER_ALLOWED_ROUTES` and correct docs/agent-protocol.md step 3 — or implement the claimed own-inbox restriction in `get_messages` (compare path id to the verified principal; `Forbidden` on mismatch) and fix the store/docs mismatch.
