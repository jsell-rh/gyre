## Findings

- [**F1 — blocking: unvalidated caller-supplied `persona` on spawn mints gate-satisfiable persona identities.**] `SpawnAgentRequest.persona` (crates/gyre-server/src/api/spawn.rs:45-49) is recorded verbatim into the `agent_personas` KV namespace at spawn time (spawn.rs:766-774) — the exact trust source `evaluate_persona_reviews` (gate_executor.rs:1682-1699) uses to decide whether a reviewer "runs the persona" a manifest gate requires. The same MCP surface exposes it (`gyre_spawn_worker` `persona` param, mcp.rs:587/1002-1005). Any caller with spawn rights — a Developer via `POST /api/v1/agents/spawn` (builtin-developer-write-access allows the `spawn` action), and, decisively, a **repo-orchestrator agent** via MCP `gyre_spawn_worker` (repo-orchestrator JWT, mcp.rs:691-699) — can spawn a worker labeled with the gate's persona. After the prior round's identity-binding fix, that worker submits its Approved review under its own *verified* identity, `lookup_reviewer_persona` matches, and `check_reviewer_attestation` passes at the manifest-schema default `min_attestation_level: 1` (the launch records a workload attestation; a local launch derives level 1, a container-target launch level 3). The repo-orchestrator — the actor whose MRs the manifest gates exist to police — can therefore self-satisfy every default-configured persona gate (e.g. `agent-gates.md`'s `[security, accountability]`, both level 1) and merge without any independent review. This is precisely the weakened-persona scenario the task's spec excerpt says the constraints exist to prevent ("prevents a weakened persona from producing approvals that satisfy policies written for the original persona") and reopens, for the agent threat model, the bypass class the prior round's F1 closed. It is also internally inconsistent: the same function fail-closes `persona_slug` on unapproved personas ("an unapproved persona is exactly what the spec forbids", spawn.rs:651-655), and the validated `persona_slug` path does not even write `agent_personas` — so the only production writer feeding the gate's persona check is the unvalidated one. **Reproduction:** as a repo orchestrator, call `gyre_spawn_worker` with `persona: "security"` for a task in the repo; have the worker `POST /api/v1/merge-requests/{id}/reviews` `{decision: "approved"}` with its own token; the manifest `security` gate's `GateResult` transitions to Passed and `check_gates_for_mr` unblocks the merge. **Fix direction:** validate the bare persona like `persona_slug` does (resolve against Approved personas via `resolve_persona_in_chain`, or an equivalently human-approved registry) before recording it, and/or restrict the field to server-side/admin callers; the forge's own writer in `spawn_manifest_gate_agent` (server-controlled) can remain unvalidated. A test should fail if an unapproved bare persona is recorded (or if an orchestrator-spawned persona worker can satisfy a manifest gate).

- [**F2 — secondary: `submit_review` still honors a request-body `reviewer_agent_id` for human principals, so a human can forge a review attributed to a persona-holding agent.**] api/merge_requests.rs:1047-1075 binds the reviewer to the verified principal only for agent-token principals; a user-JWT/API-key caller keeps the body value. A Developer can `POST /api/v1/merge-requests/{id}/reviews` with `reviewer_agent_id` set to the MR's forge-spawned gate agent (id discoverable via the agents listing; persona recorded in `agent_personas`, attestation level ≥ 1 recorded at launch) and `decision: "approved"` — `evaluate_persona_reviews` counts it and the gate passes. The repair's stated rationale ("a human recording a review is an attributed human action") does not hold for this shape: the `Review` row attributes only the named agent, nothing records the submitting human. Mitigating context, and why this is secondary rather than blocking: the same principal can already `PUT /api/v1/merge-requests/{id}/status` to `merged` directly (transition_mr_status blocks only the Agent role from setting `approved`; `Approved → Merged` is open to humans) and can push to the default branch, so within the platform's humans-are-trusted model this adds no new capability — but the manifest-gate feature is a new consumer that turns attribution forgery into gate satisfaction, and the task instruction was to mirror task-193's validation, which derives agent-approver identity from verified claims only, for every principal (approve_spec, api/specs.rs:560-596). **Fix direction:** accept the body `reviewer_agent_id` for human principals only when it equals the caller's own identity (humans record under their own id), or require an Admin principal to record on behalf of another agent.
