## Findings

- [**F1 (major): the release artifact omits two content items the task plan explicitly requires — conversation SHAs and chain attestation data.**] The task's implementation plan item 1 reads: "Include: all agents that contributed commits, their model contexts, attestation levels, **conversation SHAs**, and **the chain attestation data**." The candidate's `AibomReleaseResponse`/`ReleaseAgent` (aibom.rs) contains zero references to conversation data (`grep -c conversation` on the candidate file = 0) and `build_release_aibom` never touches `state.chain_attestations` — the per-commit chain attestation block exists only in the pre-existing summary format (aibom.rs:348-383). Both are cheaply available in production state: conversation SHAs per agent via `state.conversations.list_by_agent(agent_id, tenant_id)` (`ConversationRepository` port, wired; used by the Explorer provenance links), and chain attestation per commit via `state.chain_attestations.find_by_commit(sha)` — the exact lookup the summary path already performs. This also undershoots the spec section itself (§AIBOM Contents: the AIBOM "captures which AI models, **prompts**, and tools produced each commit" — conversation SHAs are the platform's only prompt reference), and coverage row 14 was marked `implemented` while silently dropping the two fields, which is the fake-completion pattern the goal forbids. **Reproduce:** `git show 52955e5b:crates/gyre-server/src/api/aibom.rs | grep -c conversation` → 0; inspect `build_release_aibom` (no `chain_attestations` / `conversations` access). **Repair:** extend `ReleaseAgent` (or add a per-commit block) to carry conversation SHAs from `list_by_agent` scoped to the release range's agents, include the per-commit chain attestation data (reuse the summary path's `find_by_commit`/`load_chain` lookup over the release commit set), assert both in `aibom_release_format_full_attribution` against fixtures, and amend coverage row 14 to match.

Minor (non-blocking, recorded for completeness):

- `get_stack_drift` reports `total` from an audit query capped at `limit: 1000` (stack_attest.rs `stack_drift_events_for_repo`), so a repo with >1000 drift events reports `total: 1000` — the "honest total" comment holds only below that cap. A count query or documented cap note would fix it.
- The release artifact's `attested_commits`/`unattested_commits` count only agent-attributed commits (human commits are a separate counter) — the field names could mislead a compliance reader into reading `unattested_commits: 0` as "everything attested" on a repo with human commits; `all_commits_attested` is the honest aggregate and is correct.
