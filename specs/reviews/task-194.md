## Findings

- **F1 (minor): manifest-less fallback drops old-side prefix matching for renames — a narrow regression vs base, against AC3's "no regression".** Base `fefde2946` `parse_spec_changes` admitted a rename when EITHER side was watched, and `classify_spec_change('R', …)` always yields a task, so `R specs/system/a.md → specs/milestones/a.md` (or → `docs/a.md`) created an `Update spec references` task. The candidate's fallback arm checks only the NEW path against `SPEC_WATCHED_PATHS`, so those renames now create no task in manifest-less repos. Probe (evidence: `probe-rename-fallback.log`, temp test restored afterwards): `parse_spec_changes` admits both renames, but `should_create_lifecycle_task(None, 'R', "specs/milestones/a.md") == false` and `should_create_lifecycle_task(None, 'R', "docs/b.md") == false`. Note the manifest-mode new-path matching is per the task's explicit instruction ("For renames (R), match on the new path") and is not a finding; only the fallback deviates from its "preserve today's path-prefix behavior" mandate. Remedy: in the `None` arm (or by threading `old_path` into the gate), also accept when the rename's old path matches a watched prefix.

Not blocking, recorded for completeness:

- Auto-invalidation now fires for ALL `specs/` changes (parse widened from watched prefixes to `specs/`), so e.g. a modification to an unregistered `specs/coverage/…` file or to an entry with `auto_invalidate_on_change: false` revokes its approvals where base did not. The task explicitly scoped invalidation as "keep intact, independent of task creation", so this is compliant with the task contract; the per-spec `auto_invalidate_on_change` manifest policy remains unwired and should get its own task if §15's "manifest is the single source of truth for policy" is to cover it.
