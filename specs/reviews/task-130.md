## Findings

### Round 5 (this review) — blocking

**F1 (code, crates/gyre-server/src/mcp.rs handle_spawn_repo_orchestrator + auth.rs extractor):** the new tenant containment consumes the fabricated extractor default, breaking the workspace-orchestrator → repo-orchestrator spawn flow. `spawn_repo_orchestrator_core` (orchestrator.rs:346-369) compares the target workspace's real tenant against `caller_tenant`, and the MCP caller passes `&auth.tenant_id` (mcp.rs:1305). But the `AuthenticatedAgent` extractor hardcodes `tenant_id: "default"` on the per-agent-token path (auth.rs, pre-existing task-099 F1 exempted site) — `with_hierarchy_from_claims` mirrors workspace_id/repo_id/scope from the verified claims but NOT tenant_id. So a workspace orchestrator holding a correctly minted scoped token (tenant t1) is denied its own happy path: `cargo test -p gyre-server --lib` fails deterministically at the candidate with `mcp::tests::mcp_spawn_repo_orchestrator_happy_and_wrong_workspace` (mcp.rs:6224, happy-path `!isError` assertion; **1264 passed / 1 failed**, reproduced twice in full run and once isolated). Diagnostic probe (probe-diagnostic-output.txt): `gyre_spawn_repo_orchestrator {"repo_id": "r-1"}` from the ws-1 workspace orchestrator (token tenant t1) → `"Failed to spawn repo orchestrator: repo r-1 belongs to tenant t1, not the caller's tenant default"`. This (a) violates the acceptance criterion "cargo test --all passes" (deterministic lib failure — the same class for which prior rounds 4e8e1b2/7be3363d were rejected), (b) falsifies the shipped evidence "lib 1262 passed / 0 failed" at the candidate, and (c) functionally breaks the specced workspace-orchestrator capability (`workspace:{id}:spawn` scope exists exactly to spawn repo orchestrators) in any deployment whose workspace tenant is not literally "default". The failure direction is fail-closed (no privilege escalation), but the enforcement uses the wrong identity source: the token carries a signature-verified `tenant_id` claim that the containment ignores. The same latent issue affects the REST handlers for global-token admins spawning orchestrators in admin-created non-default-tenant workspaces. Remedy: derive the containment tenant from the validated claims (extend `with_hierarchy_from_claims` to populate `tenant_id` from the claims, or read the claims tenant in `handle_spawn_repo_orchestrator`/the REST handlers) so `mcp_spawn_repo_orchestrator_happy_and_wrong_workspace` passes for the right reason; the wrong-workspace and cross-tenant denial arms must keep failing.

## Non-blocking notes (recorded for completeness)

- `is_agent_jwt` classifies any JWT whose `scope` claim is a non-empty array as a Gyre-scoped agent token. A Keycloak/IdP token that happened to carry a scope *array* would enter validate_tool_scope and fail closed (denial, not escalation) unless it also carried well-formed `repo:`/`workspace:` entries — trusting those would require the IdP to mint Gyre-shaped scopes. Fail-closed direction; not a defect for this task, but the trusted-mint assumption is implicit.
- Worker mint still passes persona/attestation_level as None. The task's plan lists them as claim fields (implemented in the struct and accepted by mint_with_workload); the shipped note discloses this residual honestly — spawn requests carry no persona input and attestation is recorded post-spawn. Claim surface exists; no production caller populates them for workers. Acceptable as disclosed; a follow-up could thread persona from the spawn request.
