## Findings

- [ ] **F1 (major): the committed `web/dist/` bundle still ships the pre-task-209 profile UI — and its preference save is now incompatible with the new backend.** The candidate changes `web/src/components/UserProfile.svelte`, `web/src/locales/en.json`, and the profile tests, but the base..candidate diff touches no `web/dist/` file; the committed bundle (`web/dist/assets/index-jpFOlnlZ.js`, last regenerated by task-123's `d65920511`) still contains the old fabricated `NOTIF_TYPE_IDS` (`SpecApproval`, `GateOverride`, `MetaSpecEdit`, `MergeRequestReview`, `AgentFailure`, `SpecDrift`) and PUTs the old wire shape (a bare prefs map, not `{preferences:[{notification_type, enabled}]}`). Against the candidate's backend, that save fails (request deserialization, plus the new 400 validation rejects the old ids), so in the documented `SKIP_WEB_BUILD=1 cargo build -p gyre-server` path (`spa.rs` RustEmbeds `web/dist/`) the profile's Save Preferences button is broken, the last-login display is absent (no `last_login` string in the committed bundle), and the judgment tab renders with the old field names. Same defect class as task-208 review F1; repo convention is to commit regenerated dist when web sources change (`d65920511`, `71967943d`, `000dec2a1`).
  **Repair:** `cd web && npm run build`, commit the regenerated `web/dist/` with a task-209-labeled conventional commit, append the SHA to task-209.md `commits:`, and grep the dist (`SpecApproval[^R]|GateOverride|MetaSpecEdit|MergeRequestReview|AgentFailure|SpecDrift"` must return nothing; `last_login` and `preferences:[{notification_type` must appear).
- [ ] **F2 (major): two of the 22 shipped preference toggles are inert — legacy parse aliases instead of canonical `as_str()` names.** `NOTIF_TYPE_IDS` in `UserProfile.svelte` contains `SpecPendingApproval` (canonical `SpecApprovalRequested`) and `BudgetWarning` (canonical `AgentBudgetWarning`). The PUT validation gates on `NotificationType::parse`, which accepts the aliases (`gyre-common/src/notification.rs:193,196` — they exist so *legacy notification rows* keep parsing, per the enum's own doc comment), and stores the raw string; notification rows are persisted with the canonical `as_str()` name (`sqlite/notification.rs:107`) and the exclusion is a raw string `ne_all`. Disabling "Specs Pending Approval" or "Budget Warnings" therefore filters nothing. This violates the candidate's own amended HSI §12 clause ("the stored `notification_type` is the canonical `NotificationType::as_str()` name") and is exactly the silently-inert-toggle failure the amendment's 400-validation clause was written to prevent — the gate checks parse-ability, not canonical-ness. Both test suites miss it (canonical names only).
  **Repair:** use the canonical ids in `NOTIF_TYPE_IDS` (labels can stay human-readable), or normalize server-side (`NotificationType::parse(...)?.as_str()` before storing). Add a round-trip test: disable the alias-named type via the API, assert the canonical-typed notification is excluded from the inbox.
- [ ] **F3 (moderate): the judgment-ledger SQL read path bypasses `detail_zstd` decompression.** The `log-compression` job (`log_compression.rs`, registered in `jobs.rs:407-415`, daily, 7-day age) blanks `audit_events.detail` and moves the JSON to `detail_zstd`; its module contract requires every read path to decompress transparently. The new `list_for_user` Source-2 query in `sqlite/user_profile.rs` and `postgres/user_profile.rs` selects only the raw `detail` column (`serde_json::from_str(...).unwrap_or(Value::Null)`), never consulting `detail_zstd`. Judgment events older than 7 days surface with null detail: trust entries render `trust  -> ` (HSI §1416 requires from → to), gate entries lose `gate_type`, meta-spec entries show the opaque resource id instead of the name. The mem adapter materializes (decompresses) correctly, so mem-backed tests stay green while SQLite (the default backend) deployments degrade — and the ledger is specced as a long-horizon "compounding asset", so >7-day-old entries are the norm, not an edge case.
  **Repair:** route the audit-source read through the established materialization (select `detail_zstd` and reuse the `AuditEventRow::into_event` decompression semantics, or query via `AuditRepository`) in both SQL adapters; add an adapter test that compresses a judgment event's detail and asserts the ledger still renders from→to/gate_type.
