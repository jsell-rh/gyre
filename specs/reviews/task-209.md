## Verified working

- **Part 1 (spec amendment)**: HSI §12 now specifies the concrete judgment sources (spec_approvals joined to spec_ledger_entries for workspace attribution; audit_events rows `gate_override`/`trust_change`/`meta_spec_publish` with `user_id` attribution), documents the canonical-user-Id attribution key (vs the KeyBinding `user:<name>` label, which stays on the approval-history events where spec_registry's `human_approvers` matching needs it), and fixes `?type=` wire values to `approval|rejection|gate|trust|meta-spec` — exactly the `JudgmentType` strings.
- **`JudgmentType::GateOverride`**: `as_str() = "gate"`, `from_db_str("gate")` parses; domain tests cover it.
- **Part 2 (aggregation)**: SQLite and Postgres `list_for_user` are in genuine parity (Postgres was previously all `bail!` stubs — now real Diesel queries). Spec approvals are left-joined to `spec_ledger_entries` (keyed by path, so no join fan-out); `?workspace_id=` is a real SQL filter (NULL-workspace rows drop when set, per the amended spec); rejections/revocations are attributed to the *declining* human (`rejected_by`/`revoked_by`), not the original approver; the merged stream is sorted reverse-chronologically with a deterministic entity_ref tie-break and limit/offset applied after the merge. Audit-sourced rows are materialized through the shared `AuditEventRow::into_event` decompression path, so log-compressed rows (blanked `detail`, `detail_zstd` payload) still yield full judgment details — proven by a dedicated test running the real `compress_details_before`.
- **Part 3 (write paths)**: trust transition (`PUT /workspaces/:id`) writes a `trust_change` audit event only on an actual transition (same-value PUT writes nothing — asserted); human approval on an MR with FAILED gate results writes one `gate_override` event per failed gate with mr_id/gate_id/gate_type/status (agent-token approvals with no user identity excluded — asserted); meta-spec registry create/update write `meta_spec_publish` events with kind/name/version/content_hash. All three propagate record failures (`?`), broadcast on the audit channel, and use server-derived identity fields only.
- **Notification filtering**: `exclude_types` is applied inside the SQL query before limit/offset in both SQL adapters and the mem adapter; the inbox list and badge count endpoints load disabled types from `user_notification_preferences` (no row = enabled); the MCP `notifications://` resource applies the same exclusion for HSI §11 parity; background de-dup callers pass `&[]` per the port contract. PUT rejects non-canonical type names with 400 and normalizes legacy parse aliases before storing (a dead-toggle class the old code silently accepted).
- **Auth provider info**: `users.oidc_issuer` added by migration `2026-10-07-000056` (single Diesel version key; `last_login_at` correctly left to task-120's `2026-10-08-000058` to avoid a duplicate-column collision — documented in the migration). `validate_jwt` records the verified issuer + login time via `UserRepository::record_login`, implemented as one conditional UPDATE (no read-modify-write race) in SQLite/Postgres and in the mem adapter, with a 60 s debounce that never suppresses an issuer change. `GET /users/me` returns both; `PUT /users/me` has no field for either (read-only confirmed); the UI renders both.
- **Attribution-key fix in specs.rs**: approve/reject/revoke now write the canonical user Id into `spec_approvals.{approver_id,rejected_by,revoked_by}` while keeping the `user:<name>` label on the history events (preserving spec_registry `human_approvers` matching and the revoke authorization check). End-to-end JWT tests assert writer/reader key agreement — these exist precisely because adapter tests seeding their own key shape once hid a mismatch.
- **Adjacent hardening (in-file, tested)**: meta-spec registry DELETE gained scope-level per-handler authorization (admin-of-scope-tenant / workspace Owner-Admin with tenant containment, 403-before-404 existence oracle), replacing a global-admin-only check on an ABAC-exempt route — covered by three new tests. Mem-mode wiring shares the audit/spec-approval/spec-ledger stores with the judgment ledger (`store_shared!`), so in-memory ledger aggregation reads what the handlers actually write; DB-backed mode uses the SQL adapters via `store!`.
