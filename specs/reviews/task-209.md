### Findings

- [ ] **F1 (major, code): the judgment ledger's `approval`/`rejection` category never surfaces production-written approvals — identity-key mismatch between writer and reader.** The production writers (`approve_spec` `specs.rs:589/597`, `revoke_spec_approval` `specs.rs:1056`, `reject_spec` `specs.rs:1188`) store `spec_approvals.approver_id = format!("user:{}", auth.agent_id)` = `"user:<display_name>"` (`auth.rs:927`: JWT users get `agent_id = user.display_name`), while `get_judgments` passes `resolve_user_id(&auth)` = the user's UUID `Id` (`auth.user_id`; provisioned via `uuid::Uuid::new_v4()` in `find_or_create_user` `auth.rs:977`) into `list_for_user`, which filters `spec_approvals.approver_id = <UUID>`. `specs.rs:640` is the ONLY production `spec_approvals.create` call site (the gates.rs/git_http.rs call sites are test modules), so no production row ever matches: a human's spec approvals and rejections — the first-listed HSI §12 judgment category, and the ledger's pre-existing half — are invisible in `GET /users/me/judgments`. Proven end-to-end above (201 on approve, empty judgments). This violates AC "list_for_user aggregates all 4 categories from real tables" and contradicts coverage row 53's implemented claim. The HSI §12 amendment's own note that `spec_approval_events.approver_id` carries `user:<display name>` applies equally to `spec_approvals.approver_id` — both writes share the same `approver_id` variable (`specs.rs:608`/`625`) — so the amended Sources table names an attribution key whose format the reader never reconciles. Remedy: reconcile the key on both sides (prefer writing the authenticated user's `Id` into `spec_approvals.approver_id`, keeping the KeyBinding `user:<name>` label only where the KeyBinding contract requires it; alternatively resolve the caller's `user:<display_name>` key in `list_for_user`), and add an end-to-end test that approves a spec via the production endpoint and asserts it appears in `/users/me/judgments` — mirroring the gate/meta-spec endpoint tests that exist for the other categories.

  Note: the same filter existed in base, so the mismatch predates this task — but this task's contract was precisely to make the ledger aggregate from real tables, its Shipped notes claim the approval category works ("spec_approvals LEFT JOIN spec_ledger_entries (?workspace_id= now FILTERS...)"), and it flipped row 53 to implemented. A hollow category behind a green matrix is the fake-completion class the goal forbids.
- [ ] **F2 (major, test): the adapter tests mask F1 by seeding a key shape production never writes.** `seed_judgments` (`sqlite/user_profile.rs`) creates `SpecApproval::new(..., "u1")` with the raw user Id as approver; no production writer emits that shape. All four judgment_ledger adapter tests pass while the end-to-end behavior they imply (a human's real approvals surfacing) does not exist — the stub-backed/mirrored-logic class. The gate/trust/meta-spec categories each have a production-write-path endpoint test; approvals has none, which is exactly why F1 shipped green. Remedy folds into F1's end-to-end test.
