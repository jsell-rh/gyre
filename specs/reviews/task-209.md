## Findings

- **F1 (code — needs revision)**: `crates/gyre-server/src/api/specs.rs:1142-1147` — the revoke handler's new `caller_is_agent` derivation checks `scope.as_str() == Some("agent")`, but Gyre agent JWTs carry `scope` as a **non-empty array** (this is exactly how `approve_spec` at specs.rs:564 and `is_agent_jwt` at mcp.rs:674 detect them), so `caller_is_agent` is effectively always false and the computed caller label is `user:<agent-uuid>` — which never matches the approval event's `agent:<agent-uuid>` written by approve. Result: an agent can no longer revoke its own approval (403 "only the original approver or an Admin can revoke"). At base `6ffd6799` any JWT got the `agent:` prefix, so agent self-revoke worked (human self-revoke was broken — the candidate fixed that and broke this). Fail-closed, admin path unaffected, and no test covers agent-JWT self-revocation (`approve_then_revoke` uses the system token). The comment above the check claims the label is "derived the SAME way approve_spec derives" — the code does not match. Reproduce: approve a spec with an agent JWT (scope array), then POST /specs/:path/revoke with the same token → 403.
- **F2 (minor)**: `specs.rs:1326` — the reject endpoint only transitions `Pending` `spec_approvals` rows (pre-existing loop, kept by this task). A human rejecting a spec that already has an Approved row gets no `rejected_by` written anywhere, so that judgment never surfaces in the ledger, and the amended HSI source table ("rejection ... written by POST /specs/:path/reject") is only true for the pending flow. The new reject test seeds only a Pending row.
- **F3 (minor)**: the postgres adapter mirrors sqlite line-for-line for `list_for_user`, `exclude_types`, and `record_login`, but carries none of the 13+ tests the sqlite module has (repo precedent for PG SQL-shape tests exists at `postgres/search.rs`). Parity is currently correct by inspection only.
- **F4 (minor)**: the Profile UI ledger tab calls `api.myJudgments()` with no params — no type/workspace filter and no pagination; judgments beyond the first 50 are unreachable from the Profile. The endpoint implements all specced params; HSI §12 does not explicitly require UI filter controls.
- **F5 (minor)**: `GET /users/me/judgments?type=<unknown>` silently maps to no filter (unfiltered results) via `and_then(JudgmentType::from_db_str)`, inconsistent with the 400 the sibling prefs PUT and notifications `priority` param return on bad input.
