## What was verified

### 1. Bindings as registry metadata + re-approval cascade (AC 1, AC 3)

- `SpecLedgerEntry.bindings_sha` (`gyre-domain/spec_ledger.rs`) records `canonical_bindings_sha` over sorted `{meta_spec_id}\t{pinned_version}` lines; `registry_sha()` derives the composite identity over content SHA + bindings SHA and equals `current_sha` when unbound, so pre-existing approvals of unbound specs keep their identity (no mass invalidation on upgrade).
- `put_spec_meta_spec_bindings` (`api/meta_specs.rs:9189`) loads the ledger entry fail-closed (lookup error → 500, unregistered spec → 404 — kill test `spec_bindings_reject_spec_absent_from_ledger`), preserves the pin-version-exists history check, the cross-workscope leak guard (Workspace-scoped meta-spec cannot bind outside its workspace), and the role gate (global Admin or Developer+ membership of the owning workspace; agent tokens refused). A changed set writes the ledger FIRST (bindings_sha update + `approval_status = Pending` via the same stored-status the content-edit invalidation uses), then replaces the binding rows, then clears `stale_pin:{spec}:` dedup keys — so a later drift re-notifies. An identical re-PUT is a no-op (does not invalidate).
- Approvals are recorded and validated against the registry SHA: the approve handler records `spec_sha: registry_sha` in both the approval-history event and the durable approvals ledger, and the mode-based resolver (`resolve_new_approval_status`) and manifest-less fallback validate events against `entry.registry_sha()` — so a pin change both flips the stored status to Pending and makes the prior approval events stale under the ordinary validity check (belt and braces, each independently sufficient).
- Spawn gate (`api/spawn.rs:746-780`): worker spawns (Implementation tasks, non-interrogation) refuse with 409 when the referenced spec's ledger status is not Approved; ledger lookup errors fail closed. Kill test `spawn_blocks_worker_for_pending_spec_until_reapproval` asserts the 409, zero agents/worktrees created, and that re-approval unblocks the same spawn.
- Merge gates (`api/gates.rs` `verify_spec_ref`/`verify_signed_spec_ref`): both now deny when the ledger entry is not Approved even if a (signed) approval row for the content SHA is active — exactly the post-pin-update state. Kill test `verify_spec_ref_denies_pending_ledger_despite_active_approval_row` with control/re-deny/re-approve phases.
- The existing cascade is reused, not re-invented: approve → `resolve_new_approval_status` → ledger Approved → `SpecApproved` emit → signal-chain delegation task; band 3 of prompt assembly resolves the binding rows (keyed by the same ledger-relative path the delegation task carries in `spec_path`) at pinned versions via version-history lookup. Content-edit invalidation (`sync_spec_ledger`) mutates the existing entry in place, preserving `bindings_sha` — a content edit under bindings produces a new composite registry SHA.
