## Findings

- [**F1 — blocking, mechanical: the candidate fails the repo's rustfmt gate.**] `python3 scripts/check-rustfmt-diff.py 73c504f2` exits 1 with changed-line violations in 24 files (evidence: `/tmp/stage/review-evidence/rustfmt-gate.txt`; full `cargo fmt --check` shows 69 diffs, base is clean). Representative defects: `bindings_sha: String::new(),` inserted at column 0 in ~20 struct literals (production code in spec_registry.rs:580 and test scaffolds elsewhere), misindented `RouteResourceMapping::api(` (abac_middleware.rs:600), unformatted `gyre-domain` re-export (lib.rs:120-121), join-collector chains (api/meta_specs.rs:8707-8709, api/specs.rs:6049-6050, reconciliation.rs:5099-5102, merge_deps.rs:355-359). Pre-commit (`cargo fmt --all -- --check`) and CI (`scripts/check-rustfmt-diff.py HEAD^1`) both fail on this tree. **Repair:** run the pinned rustfmt (`cargo fmt`) over the touched files and recommit; no semantic change required.
- [**F2 — weak tests: the two new enforcement gates have no test that fails when they are removed.**] (a) The worker-spawn approval gate (api/spawn.rs:754-766): no test spawns an implementation worker for a task whose spec is in the ledger as Pending — the AC1 clause "no worker agent is spawned for tasks referencing that spec until it is re-approved" is enforced by code I verified by inspection (and `cargo check`), but nothing pins it. (b) The stored-status denial added to `verify_spec_ref`/`verify_signed_spec_ref` (api/gates.rs:832-849, 892-909): the pre-existing Pending-denial test exercises the approval-row path, not the new ledger-status check (a spec with an active approval row but Pending ledger status — exactly the pin-update state — is not covered). The ledger-reset half of AC1 IS well tested (`pin_update_on_approved_spec_resets_approval_and_registry_sha`: Pending + new registry SHA, identical re-PUT no-op, bump and unbind re-invalidate, unbound identity = content SHA — a real kill test for the base bug). **Repair:** one focused test per gate — spawn → 409 + no agent/worktree created for a Pending spec (then approve and spawn succeeds); `verify_spec_ref` denies a Pending-ledger spec despite an active approval row for the content SHA.

Minor (non-blocking, recorded for completeness):

- The bindings panel's registry listing uses GET /api/v1/meta-specs, which is Admin-only per the canonical contract (task-301). A non-Admin Developer author — exactly the role the PUT authorizes — gets only per-binding fallback lookups, so they can edit existing bindings but cannot discover/select new optional meta-specs, and unbound required meta-specs are invisible to them. Acknowledged in the shipped notes; stems from the canonical API contract this task was told to build against, not from a defect in this diff.
- The spawn gate blocks on the stored ledger status for ALL specs, including manifest `requires_approval: false` specs whose stored status stays Pending (the §17 resolver treats them as Approved but nothing writes that into the ledger). This aligns with agent-runtime §1 ("spec approval is the single trigger") and mirrors the pre-existing merge-gate row check, but it is a behavior change vs the base for that manifest configuration.
- `mr_recorded_meta_specs_used` keys the prompt-set record by author agent id (the agent's latest spawn), not by the MR's task — matches the task text's "resolved from the author agent's spawn-time prompt-set record"; noted as a modeling approximation for multi-task agents.
- `web/dist` was not rebuilt or committed by the agent — verifier-owned per the stage contract; not a finding.

Test-inflation check: none found in the new tests I read. The cascade killing test, the drift/strict-hold tests, the API-driven reconciliation-trigger tests, the registry-context test (hand-constructed expected SHA, not mirrored through the production resolver), and the web bindings-panel tests all fail if their target behavior is disabled.
