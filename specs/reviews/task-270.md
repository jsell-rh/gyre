## Requirement 1 — agent-principal default-branch push rejection

- **Placement and strength.** The check is a direct, unconditional guard in `git_receive_pack` (git_http.rs, after repo resolution/authorization/ABAC and body read, BEFORE `run_git_stateless("receive-pack", …)`), so on 403 the ref is never created/updated/deleted server-side. It is not routed through `check_pre_accept_gates` (which returns Ok early for repos with no configured gates) — matching the task's explicit "direct check in the push handler".
- **Caller-class scoping is correct.** Rejection applies when `auth.user_id.is_none() && !auth.is_system_principal()`. Verified against `AuthenticatedAgent` semantics (auth.rs): agent tokens (legacy UUID agent tokens, Gyre-minted agent/orchestrator JWTs) have `user_id: None` → rejected; API keys and user/federated JWTs carry a backing `user_id` → exempt; the global dev/system token is discriminated by `is_system_principal()` (agent_id "system" AND user_id None — not spoofable by a user named "system", whose key resolves to their own user id). This preserves spec-lifecycle.md §Automatic Task Creation for human and system principals.
- **Ref resolution.** The protected ref is `refs/heads/{repo.default_branch}` from the Repository record (`Repository::new` defaults "main"; no hardcoding at the check site). Test `protection_resolves_real_default_branch_not_literal_main` proves both directions on a trunk-default repo (refs/heads/trunk rejected, literal "main" accepted).
- **Deletion bypass closed.** The guard matches `parse_ref_update_commands` — the RAW pkt-line command list including deletions — not `parse_ref_updates` (which now filters zero-SHA deletions for push-acceptance processing, preserving prior post-receive semantics for the filtered list). Test `agent_deletion_of_default_branch_rejected` drives a real delete command and asserts 403 + ref survival.
- **Parser robustness.** `parse_ref_update_commands` strips the NUL capability suffix on the first command line and validates both SHAs (`is_valid_sha`), so a real git client's `<old> <new> <ref>\0caps` command cannot evade the refname match. Single receive-pack route (`/git/:ws/:repo/git-receive-pack` → this handler only).
- **Rejection is observable and self-explaining.** 403 body explicitly directs to the MR flow ("push a feature branch and signal completion (gyre_agent_complete)"); `PushRejected` message-bus event + `GitPushRejected` audit event (gate_name `default-branch-protection`, outcome Blocked) are emitted.
- **Tests discriminate.** `agent_push_to_feature_branch_succeeds` uses the same body construction (with a real packfile via `pack_objects_for`/`receive_pack_body_with_pack`) and the same agent token, and lands `refs/heads/feat/dbp` — proving the token has push permission and the body is appliable, so the 403 in the default-branch test is definitively the new invariant (also confirmed by the gate-named audit event). `human_push_to_default_branch_accepted_and_spec_lifecycle_runs` asserts a push-capable API-key principal's specs/ push to main is accepted, the ref lands, and `process_spec_lifecycle` creates the spec-change task (spec_changed audit with task_id).
- **Server-side landing unaffected.** The guard exists only in the HTTP handler; merge-queue landing and post-merge reverts go through the git_ops/jj_ops ports. `merge_queue_auto_merges_mr_and_commit_on_main` (git_integration.rs) exercises the full loop; its initial main push now uses the system token (correct caller class), the agent pushes only its feature branch.

## Requirement 2 — continuous PR hygiene

- **Registration and cadence.** `pr_hygiene_check` registered in `jobs.rs` with `interval_secs` (default 300s, `GYRE_PR_HYGIENE_INTERVAL_SECS`) and `run_at_utc_hour: None`, spawned via `jobs::spawn_job` in main.rs (interval loop, not the daily wall-clock path). Test `pr_hygiene_check_registered_on_interval_not_daily` asserts None-hour, minutes-scale interval, and that a manual trigger runs a real evaluation. The daily `abandoned_branch_check` (HSI §8) is untouched by the diff.
- **Real state, real actions, one per MR (most severe first).** `evaluate_workspace` filters `MrStatus::Open | Approved`, computes age from persisted `updated_at`, then: close (≥ close threshold) → conflict → escalate (≥ escalate threshold) → nudge-if-unreviewed (≥ nudge threshold, zero review records via `reviews.list_reviews`).
  - **Close:** `transition_status(Closed)` (valid from Open/Approved) persisted via `merge_requests.update`, gate trace deleted (mirrors the close endpoint), explanatory `ReviewComment` on the MR, `MrStatusChanged` bus event, author delivery (agent → bus message with the explanation; user → `MrAutoClosed` notification), Admin/Owner notifications, `pr_hygiene` audit event. Never silent. Tests: `abandoned_mr_is_closed_with_explanation_delivered_to_author` asserts every one of these.
  - **Conflict:** `has_conflicts == Some(true)` OR a real merge-base check (`git_ops.can_merge` — the production adapter performs an in-memory `merge_commits` of the two tips; infra errors are correctly NOT treated as conflicts). Applicable rebase: author agent Active with a live worktree in the MR's repo → real `jj_ops.jj_rebase` with the same safeguards and shared 60s KV backoff window as the merge processor's §4 rebase (no double-rebase); success clears the persisted conflict flag and notifies the agent (`baseline_moved`); conflict re-persists the flag and falls through to a `MrNeedsRebase` escalation to Developers/Admins. Never silence: every path records a `jj_rebase` audit event (source `pr_hygiene`) or notification rows + `pr_hygiene` audit. Tests cover the rebased case (via port doubles — legitimate unit doubles; production path is the real adapter), the no-applicable-rebase escalation case, and assert no escalation after a successful rebase.
  - **Escalate:** `MrStaleEscalation` at priority rank 3 (higher than nudge's 7) to Admins/Owners; MR stays open. Tested.
  - **Nudge:** assigned reviewers get `ReviewerNudge` notifications (user path) or `review_nudge` bus messages (agent path); zero-reviewer MRs escalate `MrUnreviewed` to Developers/Admins; fresh MRs under threshold get nothing; reviewed MRs are not nudged. All tested, including Viewer non-delivery.
- **Idempotence.** User notifications dedupe through `has_active_notification` (exact (workspace, user, type, entity_ref) lookup — same mechanism as `abandoned_branch_check`); agent-reviewer bus nudges dedupe through a persisted KV backoff keyed (MR, agent) with the nudge threshold as window. `consecutive_evaluations_do_not_duplicate_notifications` and `…_agent_reviewer_nudges` run two evaluations and assert exactly one delivery, plus KV persistence across restarts.
- **Thresholds.** `HygieneThresholds::from_env` (`GYRE_PR_HYGIENE_{NUDGE,ESCALATE,CLOSE}_SECS`), defaults 2d/7d/30d, unparseable/zero values fall back to defaults (never zero — a fresh MR cannot become instantly stale).
- **Observability.** Every action records notification rows, bus events, and/or `pr_hygiene` / `jj_rebase` audit events.
