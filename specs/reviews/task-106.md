- [x] [process-revision-complete] **F1 (critical): the adapter parses jj rebase status from stdout, but jj writes it to stderr — conflict detection and the rebase count are dead code against real jj — process surface patched; product fix owned by task-106's revision round.** Process surface patched: checklist item 141 (specs/prompts/implementation.md) requires external-tool contracts to be empirically verified against the real binary (both streams captured separately) and pinned by recorded-fixture tests that run in CI; `scripts/check-ignored-tool-tests.sh` mechanically flags adapter fns shelling out where all same-file test callers are #[ignore]d, with the jj_ops.rs entries recorded in `scripts/ignored-tool-tests-exemptions.txt`; verifier.md names the class (ignored-only tool coverage, unverified stream contracts). `run_jj` (`gyre-adapters/src/jj_ops.rs:20-33`) returns `output.stdout` only, yet `jj_rebase` detects conflicts via `out.contains("New conflicts appeared in")` (`:161`) and parses the count from a `"Rebased "` line prefix (`:165-170`). Empirically verified against jj 0.39.0 (the binary on this machine): for both clean and conflicting rebases, `jj rebase -r @ -d main` writes `Rebased N commits to destination`, `Working copy (@) now at: …`, and `New conflicts appeared in N commits:` to **stderr; stdout is empty**. Consequence in production: `has_conflicts` is always `false` and `rebased_count` always `0`, so every rebase — including ones that produce conflicts — returns `Success { rebased_count: 0 }`. The entire conflict-as-state arm (MR flag, queue annotation, `SpeculativeConflict`/`Escalation` events, `merge_processor.rs:840-913`) is unreachable, and audit records/notifications carry a bogus `rebased_count: 0`. Nothing catches this because the merge_processor tests all inject `ConfigurableJjOps` (`mem.rs`, cfg(test)) and every adapter test that would exercise real jj output is `#[ignore = "requires jj binary on PATH"]` (`gyre-adapters/src/jj_ops.rs:229-354`). Fix direction: capture stderr (return both streams from `run_jj` or a variant) and parse that — or avoid text parsing entirely: `jj resolve --list -r <rev>` exits 2 with `No conflicts found at this revision` when clean and prints the conflicted paths on **stdout** with exit 0 when conflicted (both verified), which is a stable contract for both detection and file listing.
- [x] [process-revision-complete] **F2 (critical): agent worktrees can never contain a jj repo, so in production `jj_rebase` always fails — the feature is a no-op — process surface patched; product fix owned by task-106's revision round.** Process surface patched: checklist items 141 and 142 (specs/prompts/implementation.md) require empirical verification of tool invariants in the production layout (the colocate-in-worktree refusal) and require swallowed best-effort init to log at warn minimum with a tested degraded path - a debug!-level feature-off switch is the named flaw class; `scripts/check-ignored-tool-tests.sh` and `scripts/ignored-tool-tests-exemptions.txt` cover the ignored-only test side; verifier.md names both classes. Worktrees are created with `git worktree add` (`api/spawn.rs:478-492` → `git2_ops.rs:324-375`), then jj-initialized best-effort at spawn via `jj git init --colocate` in the worktree path (`spawn.rs:497`). jj 0.39.0 refuses this: `Error: Cannot create a colocated jj repo inside a Git worktree.` (verified, including the exact `{repo.path}/worktrees/{branch}` nested layout from `spawn.rs:471`). The init failure is swallowed at debug level (`spawn.rs:515-518` "jj init skipped"), so worktree records exist with no jj repo on disk. At merge time, `jj rebase` in the worktree exits 1 with `There is no jj repo in "."` (verified; stdout empty, error on stderr) → `run_jj` returns `Err` → `merge_processor.rs:914-920` logs a warning and moves on. No agent is ever rebased; spec §4's "jj automatically rebases the agent's in-progress work" is unimplemented in effect. Additional hazard when a jj repo *does* exist at `repo.path` (e.g. via `POST /api/v1/repos/:id/jj/init`, `api/jj.rs:66-77`): jj invoked with `current_dir = worktree.path` walks up and resolves the **parent** repo — verified that `jj rebase -r @ -d main` run from the nested worktree operated on the main checkout's working-copy change, i.e. it would mutate the forge's shared checkout instead of the agent's change. The correct primitive (per jj's own hint) is `jj workspace add`, which is a worktree-creation change (spawn/`create_worktree`), not just a rebase-call change; the task scoped only the rebase, so this needs a design decision, not a one-line fix.
- [x] [process-revision-complete] **F3 (major): agents are rebased onto a merge commit that post-merge recovery may revert, with no compensating action — process surface patched; product fix owned by task-106's revision round.** Process surface patched: checklist item 144 (specs/prompts/implementation.md) requires compensating actions when a later stage's failure reverts what an earlier stage moved (rebased agents must not sit on an orphaned base); verifier.md names the class (recovery semantics / missing compensating actions). Not mechanically decidable, so no check script; product fix owned by task-106's revision round. In both paths the rebase runs *before* post-merge gates: single-entry (`merge_processor.rs:1876-1883` rebase, `:1889-1900` gates + `recover_from_post_merge_failure`) and atomic group (`:689-696` rebase, `:704-716` gates + `recover_atomic_group_from_post_merge_failure`). If the gates fail, `recover_from_post_merge_failure` reverts `merge_commit_sha` on the branch (`:2014-2017`) — the baseline moves a second time — but already-rebased agents receive nothing: they sit on the now-orphaned merge commit, their `baseline_moved` notification cites a `new_base_sha` that is no longer on the branch, and the 60s backoff (kv `jj_rebase_backoff`, `:775-781`) actively suppresses rebasing them onto the revert. Net state: in-flight agents on an orphaned base with a stale notification, by construction of the ordering. Fix direction: run the rebase after gates pass, or add a compensating rebase/notification in the recovery path.
- [x] [process-revision-complete] **F4 (major): the rate limit drops rebases instead of batching them, and the backoff is persisted before the rebase runs — process surface patched; product fix owned by task-106's revision round.** Process surface patched: checklist item 144 (specs/prompts/implementation.md) requires guard state to be persisted AFTER the guarded action succeeds and requires suppressed work to be batched/replayed rather than dropped; verifier.md names the class (guard state persisted before the action, deferred work dropped instead of batched). Not mechanically decidable, so no check script; product fix owned by task-106's revision round. Plan item 5: "if target moves multiple times in quick succession, batch into one rebase." The implementation (`merge_processor.rs:775-781`) instead *skips* the agent entirely while inside the 60s window — no deferred or scheduled rebase exists anywhere in the codebase — so a merge landing inside the window leaves the agent on a stale baseline until some *later* merge moves the branch again after the window expires; the skipped movement is never replayed. Additionally, the backoff timestamp is written *before* `jj_rebase` executes (`:799-805` precedes the call at `:807-810`), so a failed rebase (`Err`) also consumes the window: combined with F2, an agent's first attempt writes the backoff and fails, and every merge in the next 60s skips it silently. Fix direction: on window-hit, record that a rebase is pending and perform it when the window expires (batch semantics); write the backoff only after a rebase actually ran.
- [x] [process-revision-complete] **F5 (minor): `jj rebase -r @` moves only the working-copy commit, splitting an agent's stacked changes — process surface patched; product fix owned by task-106's revision round.** Process surface patched: checklist item 141 (specs/prompts/implementation.md) requires flag semantics to be empirically verified against the real binary before building on them (-r vs -s vs -b rebase semantics are exactly this class); verifier.md's ignored-tool-coverage bullet names the class. Not mechanically decidable, so no check script; product fix owned by task-106's revision round. Spec §4: "jj automatically rebases the agent's in-progress work" — all of it. `jj_rebase` is always called with `revision = "@"` (`merge_processor.rs:809`), and `-r` rebases the specified revisions *without their descendants* (jj 0.39.0 `jj rebase --help`; empirically verified: after `jj rebase -r @ -d main` on a two-change stack, the tip moved onto `main` while its parent stayed on the old base). An agent that has stacked changes (the spawn-time `jj new` change plus later work) ends up with history spanning two bases. `-s @` (source and descendants) or `-b @` matches the spec's wording. The task plan's own "rebase their working change" with `-r` matches the implementation, so this is a spec-vs-plan divergence to resolve rather than a coding slip.
