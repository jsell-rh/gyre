## Findings

- [x] [process-revision-complete] **F1: Missing `CallGraphExtractor` port trait in `gyre-ports`.** Acceptance criterion #1 says "`CallGraphExtractor` port trait exists in `gyre-ports`." The task implementation plan step 2 defines the trait signature: `pub trait CallGraphExtractor: Send + Sync { async fn extract_call_edges(&self, repo_path: &Path, language: Language) -> Result<Vec<CallEdge>>; }`. No such trait exists in `gyre-ports/src/`. The subprocess I/O (shelling out to `go-callgraph`) is placed directly in `gyre-domain/src/go_extractor.rs:extract_lsp_call_graph()` (line 673) and `gyre-domain/src/lsp_call_graph.rs:try_go_callgraph_binary()` (line 1513), bypassing the hexagonal architecture boundary. The task's agent instructions say: "Follow the hexagonal architecture: port trait in `gyre-ports`, adapter in `gyre-adapters`, orchestration in `gyre-domain`."
  **Fixed:** `crates/gyre-ports/src/call_graph.rs:26-33` defines `CallGraphExtractor` with the exact specced signature (`async fn extract_call_edges(&self, repo_path: &Path, language: Language) -> Result<Vec<CallEdge>>`), re-exported at `crates/gyre-ports/src/lib.rs:69`. `gyre-domain/src/lsp_call_graph.rs` is deleted (2254 lines removed); domain invokes the port only through `&dyn CallGraphExtractor`.

- [x] [process-revision-complete] **F2: Go adapter subprocess I/O in `gyre-domain` instead of `gyre-adapters`.** Task implementation plan step 3 says "Implement Go adapter in `gyre-adapters`: shell out to `scripts/go-callgraph/go-callgraph <repo-path>`, parse the JSON output." The implementation places this subprocess I/O directly in `gyre-domain/src/go_extractor.rs:685` (`Command::new(&binary).arg(...)`) and `gyre-domain/src/lsp_call_graph.rs:1575` (`Command::new(&binary_path).arg(repo_root)...spawn()`). The `LanguageExtractor` trait doc comment (`extractor.rs:77-78`) explicitly states: "Extractors MUST NOT perform I/O beyond reading the repository root subtree." Shelling out to an external Go binary is I/O beyond reading the subtree, violating the trait's documented contract.
  **Fixed:** All subprocess I/O lives in `crates/gyre-adapters/src/call_graph.rs` (`SubprocessCallGraphExtractor`, `tokio::process::Command` at line 82, 60s `TOOL_TIMEOUT`, graceful degradation to `Ok(vec![])` on missing toolchain/timeout/parse failure). `grep -rn "Command::new\|tokio::process" crates/gyre-domain/src/` returns zero hits; `scripts/check-arch.sh` (updated in 595ec8b2) mechanically enforces this.

- [x] [process-revision-complete] **F3: Double execution of `go-callgraph` binary on every push for Go repos.** Two independent code paths both shell out to `go-callgraph`:
  1. **Inline (blocking):** `GoExtractor.extract()` (`go_extractor.rs:69-70`) calls `ctx.extract_lsp_call_graph()` which runs `go-callgraph` synchronously during `run_all_extractors()` (step 2 of `do_extract()`).
  2. **Background:** `extract_lsp_edges()` (`graph_extraction.rs:794`) → `extract_call_graph_auto()` → `extract_call_graph_go()` → `try_go_callgraph_binary()` runs `go-callgraph` again in the background task (step 7 of `do_extract()`).
  The second run produces zero new edges (the dedup set at `lsp_call_graph.rs:1715-1719` catches them), but the binary still executes — wasting up to 60 seconds of subprocess time per push. The spec's two-pass architecture intends Pass 2 to run only once, in the background.
  **Fixed:** `GoExtractor::extract()` (`crates/gyre-domain/src/go_extractor.rs:46-74`) runs Pass 1 only (`ctx.extract_go_files()`); no `extract_lsp_call_graph` or callgraph references remain in the file. The single Pass 2 invocation is `do_extract()` step 7 (`crates/gyre-server/src/graph_extraction.rs:375-402`) → `extract_and_persist_call_graph()` → the port. `grep -rn "extract_lsp_call_graph\|try_go_callgraph_binary\|extract_call_graph_auto" crates/` returns zero hits.

- [x] [process-revision-complete] **F4: Non-blocking requirement violated — GoExtractor runs Pass 2 synchronously.** Acceptance criterion: "Pass 2 is non-blocking — graph is usable after Pass 1, becomes complete after Pass 2." Spec §6: "Pass 2 is non-blocking — the graph is usable after Pass 1 with partial call data, and becomes complete when Pass 2 finishes." `GoExtractor.extract()` (`go_extractor.rs:66-71`) runs both Pass 1 (tree-sitter) and Pass 2 (go-callgraph binary) synchronously. This method is called from `run_all_extractors()` (`graph_extraction.rs:763`), which runs inside `tokio::task::spawn_blocking` in step 2 of `do_extract()` (line 149). Graph persistence doesn't start until step 3 (line 163). The graph is not usable after Pass 1 — it's held in memory until Pass 2 completes (up to 60 seconds per go-callgraph timeout). The background Pass 2 in step 7 (line 391) correctly implements non-blocking semantics, but the inline Pass 2 in the GoExtractor defeats the purpose.
  **Fixed:** Pass 1 persists (steps 3–6 of `do_extract()`) before step 7 fires Pass 2 via `tokio::spawn` (fire-and-forget) with the temp tree moved into the task. The push response is never blocked; graph is usable after Pass 1 and completes after Pass 2, per spec §6.

- [x] [process-revision-complete] **F5: Integration test tests extractor in isolation, not the sync pipeline.** Acceptance criterion: "Integration test: sync a Go repo → verify `Calls` edges appear in graph." The test `lsp_call_graph_produces_cross_package_calls` (`go_extractor.rs:1439`) calls `GoExtractor.extract(dir.path(), "abc123")` directly and asserts on the returned `ExtractionResult`. It does not invoke the sync pipeline (`extract_and_store_graph`), does not persist edges via `GraphPort`, and does not verify edges appear in the graph store. This is a unit test of the extractor, not an integration test of the sync → graph storage pipeline. The acceptance criterion specifically says "sync a Go repo → verify `Calls` edges appear in graph" — requiring pe…
  **Fixed:** `sync_go_repo_persists_calls_edges_in_graph_store` (`crates/gyre-server/src/graph_extraction.rs` tests) drives the Pass 2 pipeline entry point `extract_and_persist_call_graph` for a repo with a `go.mod`, and asserts the `Calls` edge is persisted in the `GraphPort` store (`MemGraphStore.list_edges(repo_id, Some(EdgeType::Calls))`) resolved to the Pass 1 node IDs. Companion `pass2_dedups_calls_edge_already_present_from_pass1` covers dedup against Pass 1 edges; `crates/gyre-domain/src/call_graph_resolve.rs` tests cover resolution/dedup/unknown-endpoint paths; `crates/gyre-adapters/src/call_graph.rs` tests cover graceful degradation. The `go-callgraph` binary itself was exercised on a two-package Go fixture and emits the expected `[{"from": "example.com/fixture/api.Handle", "to": "example.com/fixture/svc.DoWork"}]` JSON.

### Findings

- [x] [process-revision-complete] **F6: Go Pass 1 / Pass 2 qualified-name formats diverge — process surface patched; product fix owned by task-072's revision round.** The procedural flaw was a mirrored fixture: domain tests constructed identical qnames on both the node side and the raw-edge side, so exact-match resolution always succeeded in tests while any real layout with package name ≠ directory name failed in production. Checklist item 137 (specs/prompts/implementation.md) now (a) requires producer-side and consumer-side test data to be constructed independently from the SPEC's format rule, never copied from each other or the implementation, (b) makes divergence cases mandatory — at least one fixture where a naive format assumption produces a mismatch, and (c) requires grepping every producer and consumer of a shared identifier format to verify they apply the same rule (this finding's exact divergence — `pkg.Pkg.Path()` import path vs `format!("{}/{}", module, package_clause)` — is cited as the worked example). The format divergence itself remains on main pending task-072's revision round.
  **Fixed (product, R3):** Pass 1 qnames rebuilt on Go's import-path rule — `go_extractor.rs:209-230` derives `<module>/<directory-path>` from the file's directory (package clause never used; root files get the bare module path), matching the binary's `pkg.Pkg.Path()` exactly; module docs (`go_extractor.rs:10-15`) state the scheme as the contract. Regression tests on both producer and consumer side, constructed independently: `qualified_name_uses_import_path_not_package_clause` (go_extractor: dir `internal/handlers/` declaring `package handlers` → qnames `…/internal/handlers.Server.Handle`/`Serve`) and `resolve_go_import_path_when_package_clause_differs_from_dir` + `resolve_go_divergence_package_clause_name_does_not_resolve` (call_graph_resolve, raw names built by a `callgraph_name` helper encoding the spec rule, with a clause-derived name proven non-resolving).
- [x] [process-revision-complete] **F7: `resolve_go_node` method branch guesses `candidates[0]` under ambiguity — contradicts its own drop policy and is non-deterministic — process surface patched; product fix owned by task-072's revision round.** Process surface patched: checklist item 146 (specs/prompts/implementation.md) forbids arbitrary tie-breaking on order-unspecified collections (`candidates[0]` on HashMap-derived vecs) and requires ONE documented ambiguity policy applied to every ambiguous branch in the module; verifier.md now names the class (arbitrary tie-breaking). Not mechanically decidable, so no check script; product fix owned by task-072's revision round. `call_graph_resolve.rs:217-227`: when a `Type.Method` suffix matches multiple candidate nodes and the package hint fails, the method branch returns `Some(candidates[0])` — an arbitrary HashMap-iteration-order pick. The plain-function branch (lines 251-253) explicitly refuses under the same condition with the comment "Ambiguous with no package hint → do not guess (wrong edges are worse than missing ones)". The asymmetry is unspecced and undocumented. Combined with F6 this is not hypothetical: with mismatched dirs, `example.com/app/main` calling `svc1.Handler.Handle` and `svc2.Handler.Handle` yields two candidates for each `.Handler.Handle` suffix; the package hint (`qualified.rsplit_once('.')` prefix `example.com/app/svc1.Handler`) matches neither node's `qualified_name.starts_with` nor `file_path.contains`, so `candidates[0]` fires and the edge lands on an arbitrary node — a wrong `Calls` edge, the exact harm the drop policy exists to prevent. (Verification note: could not run a probe test — target dir locked by concurrent orchestrator builds; verified by source analysis of `resolve_go_node` at `call_graph_resolve.rs:188-257` against the binary output above.)
  **Fixed (product, R3):** One policy in `call_graph_resolve.rs` — the `select` closure: a suffix match survives only if exactly one candidate is corroborated by the raw name's package hint, else `None`; no branch consults ordering. The method-branch `candidates[0]` is gone, along with two further arbitrary picks the R2 finding didn't name: a dead exact-match `by_name` fallback inside `resolve_go_node` and a dead `c[0]` fallback in `resolve_node` (both dominated by the `by_qname` lookup; removed with the domination argued in comments). Hint matching is boundary-aware (`node_in_pkg`: `strip_prefix(pkg)` + next char `.`): the old `starts_with` let hint `…/svc1` claim `…/svc10.Process`, and the old single-candidate shortcut resolved `svc1.Process` into a lone `svc10` node — both wrong edges. Tests `resolve_go_prefix_similar_package_is_not_guessed` (fails on old code) and `resolve_go_function_hint_boundary_picks_the_real_package`.
- [x] [process-revision-complete] **F8: Pass 2 `Calls` edges are soft-deleted and re-created with new UUIDs on every subsequent push — process surface patched; product fix owned by task-072's revision round.** Process surface patched: checklist item 147 (specs/prompts/implementation.md) requires content-derived identity keys for background-pass data (no fresh UUIDs per run), scopes deletion so it cannot race the async writer, and mandates idempotence + mid-flight-race tests; verifier.md now names the class (unstable identity for derived data, deletion racing the async writer). Not mechanically decidable, so no check script; product fix owned by task-072's revision round. `do_extract()` step 5 (`graph_extraction.rs:294-299`) soft-deletes every old edge not in Pass 1's `new_edge_map` — which includes all Pass 2 `Calls` edges persisted by the *previous* push's background task (Pass 1 extractors emit no `Calls` edges for Go). Pass 2 then recreates them with fresh `Uuid::new_v4()` ids (`call_graph_resolve.rs:148`). Consequences: (1) edge IDs and `first_seen_at` are unstable across pushes, breaking any consumer that tracks edges by ID; (2) if pushes arrive faster than Pass 2 completes (60s tool timeout on large repos), the previous run's edges are soft-deleted before their replacement is written — the graph temporarily loses all `Calls` data, contradicting spec §6's "graph is usable after Pass 1 with partial call data, and becomes complete when Pass 2 finishes" only in the overlap window; (3) a Pass 2 still in flight from push N reads `old` edges... in fact it never reads old edges — `extract_and_persist_call_graph` receives `existing_edges` = Pass 1's `new_edge_map` only, so a slow Pass 2 from push N and the step-5 delete from push N+1 can interleave: push N's Pass 2 persists edges that push N+1's step 5 will delete as "not in new_edge_map", then push N+1's Pass 2 recreates them. Net effect is churn, not wrong data. Severity: medium — correctness (final state converges) but violates the intent of stable IDs/first_seen_at (sqlite `create_edge` upsert: "first_seen_at is immutable — never updated on conflict", `sqlite/graph.rs:449`) and creates duplicate-row risk when concurrent Pass 2 runs overlap the delete window (SQLite has no unique constraint on `(repo_id, source_id, target_id, edge_type)` — `schema.rs:789`, PK is `id` only).
  **Fixed (product, R3):** (a) Step 5 sweep (`graph_extraction.rs` `sweep_stale_edges`) exempts `Calls` — the type Pass 2 owns — so it can never delete a row Pass 2's writer is mid-flight on. (b) Edge ids are content-derived (`call_graph_resolve.rs` `calls_edge_id`: SHA-256 over `repo|source|target|calls`, UUID-shaped) so re-derivation upserts in place; both adapters' `create_edge` conflict on `id` and preserve `first_seen_at` (mem adapter mirrors SQLite, `mem_graph.rs:53-69`). (c) Pass 2 reconciles its own edge type in `extract_and_persist_call_graph`: soft-deletes live `Calls` rows whose pair is absent from this run's resolved set, plus legacy pre-content-id duplicate rows — skipped entirely when no toolchain produced output, so a missing binary can't wipe call data. Tests: `pass2_edge_ids_stable_across_runs` (idempotence, `first_seen_at` preserved), `sweep_preserves_calls_edges_owned_by_pass2` (mid-flight race), `pass2_reconciles_stale_calls_edges`, `pass2_reconcile_skipped_when_toolchain_unavailable`, `pass2_reconcile_removes_legacy_duplicate_id_rows`.
