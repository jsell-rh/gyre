## Findings

- [-] **F1 (moderate): the P2 notification's `spec_sha` goes stale on iterative saves — Inbox Approve becomes a permanent masked no-op.** `save_spec`'s existing-open-MR append path (`crates/gyre-server/src/api/specs_assist.rs:643-661`) writes the new content to the MR branch and returns early (HTTP 200) without updating or re-creating the SpecPendingApproval notification, so its body keeps the FIRST save's blob SHA. Empirical probe (temporary test, evidence `probe-stale-spec-sha.txt`): first save sha `6a16eb95…`, second save sha `ecf19815…` (what the MR branch then holds), notification still `6a16eb95…`. `resolveSpecSha` (`web/src/components/Inbox.svelte`) returns `body.spec_sha` unconditionally when present, and `approve_spec` (`crates/gyre-server/src/api/specs.rs:769`) only updates ledger status when `entry.current_sha == req.sha` — so every Approve click on that card records an event for a SHA that never becomes the ledger's `current_sha` after merge. The card shows "Approved" while the spec stays Pending, and re-clicking keeps using the stale SHA (unlike the single-save case, where the body SHA equals the merged blob). This is the same masked-no-op class as prior-round F3, reachable through the normal edit→save→edit→save→approve flow. Remedy: on the append path, update the existing notification's body to the new blob SHA (or create a fresh P2 notification per save), and/or have the client resolve the SHA from the MR's current branch content instead of the possibly-stale body value.
- [-] **F2 (minor): P5 losing-MR resolution cannot match in production — the "resolved best-effort by merge-commit SHA" claim is dead code in every real flow.** `resolveConflictMr` (`web/src/components/Inbox.svelte`) matches the divergence body's `commit_sha_a/b` against MR `merge_commit_sha`. But the divergence SHAs are pushed ref tips (`git_http.rs` runs the agent-context extraction only for default-branch pushes, using `update.new_sha`; `mirror_sync.rs`/`repos.rs` pass no agent context), while `merge_commit_sha` comes from the merge processor — `git2_ops.rs merge_branches` always creates a true merge commit (never fast-forwards; comment at task-095 R2-2), and `mem.rs` returns the zero SHA. The two values can never be equal, so the lookup always returns null and every Pick A/Pick B task description says "unresolved — locate by commit SHA". Not spec-blocking: the specced P5 mechanism (create a revert task) works and the commit SHAs are genuinely actionable; but the shipped summary's claim that the F1 enrichment makes the losing MR resolvable is overstated, and the next round should either match on a SHA that can coincide (e.g. the MR's source-branch tip or head SHA) or drop the resolution step and say so.
- [-] **F3 (minor): dead API wrappers added by this candidate.** `web/src/lib/api.js` adds `revertMr` — its only caller was removed by the F4 repair, it is now referenced solely by negative assertions in `Inbox.test.js`, and its comment still claims "Used by Inbox P5 arbitration" (false) — and `stopAgent`, which has zero references anywhere (DetailPanel's stop uses `api.adminKillAgent`). Remove both or wire them to real consumers.

## Context note (pre-existing, outside this diff — for the next round's F1 remedy)

`approve_spec` only applies an approval when the ledger's `current_sha` already equals the approved SHA, and `sync_spec_ledger` resets status to Pending on content change without re-resolving recorded events. So even a correct branch-SHA approval recorded while the MR is open only takes effect if Approve is clicked again after the merge (the ledger then holds the approved content). Any F1 remedy that keeps approving pre-merge should account for this: either resolve/refresh at approve time against the MR branch (recording an event that matches what will land is still not sufficient without a post-merge re-resolution), or gate the Inbox Approve on the merged state the way the ledger fallback already does.
