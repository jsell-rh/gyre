## Verified working (by source inspection + the probes above)

- **Deliverable 1 — version discrimination.** `get_meta_spec_blast_radius` (api/meta_specs.rs:402) accepts `?from_version=&to_version=`; `from_version` is the superseded version, defaulted to the registry's current version; `to_version <= from_version` is a 400 (`ApiError::InvalidInput` → 400, error.rs:78). A workspace is affected only when a spec-level pin (`meta_spec_bindings` joined to the ledger entry's workspace scope) is at exactly the superseded version, or the required flag (visible per Global/Tenant/Workspace scope) resolves at the registry's current version. Workspaces bound at other versions land in `skipped_workspaces` with their pinned version and are excluded from every total — the spec's "internal-tools on v2, not affected" case.
- **Deliverable 2 — per-repo counts from real provenance.** `blast_radius_repo_provenance` (api/meta_specs.rs:695) queries three real storage surfaces per repo: `agent_commits.find_by_repo` joined with the author's spawn-time prompt-set record (`meta_specs_used`, kv namespace `agent_meta_spec_sets` — the same record the merge processor persists), `chain_attestations.find_by_repo` (commit SHA from the attestation, spec identity from the signed input's `spec_path`), and merge attestation bundles via `merge_requests.list_by_repo` + `attestation_store.find_by_mr_id` (the bundle's own `meta_specs_used`, merge commit SHA, spec identity from the `path@sha` ref via `rsplit_once('@')` — no byte slicing). Matching is exact on `(meta_spec_id, superseded_version)`; spec identities and commit SHAs are deduplicated across surfaces; per-workspace `repos`, flat `affected_repos` with zero counts for provenance-less repos, and `totals {repos, specs, commits}` all derive from storage — never from repo membership.
- **Deliverable 3 — §8 labels.** `reason` is `workspace_binding` for own pins and Workspace-scoped required flags, `tenant_inheritance` for Global/Tenant-scoped required flags (`required_binding_reason`), with the granular registry-model kind in a separate `binding` field. The pre-existing registry-model test was updated to the new two-field shape rather than weakened.
- **Deliverable 4 — read-only + ABAC.** Route unchanged (GET, api/mod.rs:986, ABAC-mapped at abac_middleware.rs:836); no new route, no exemption entries.
- **SQLite clamp repair (7a50c088).** `created_at` is stored i64; `u64::MAX as i64 == -1` made the old predicate `created_at <= -1` match nothing, so the chain-attestation surface was silently empty on SQLite while mem-backed tests stayed green. The clamp (`since/until.min(i64::MAX as u64)`) preserves the u64 port contract on both backends; the new SQLite-backed guard test proves it (and the handler uses the cast-safe `i64::MAX as u64` sentinel). The only other caller set of `chain_attestations.find_by_repo` is this handler, so no behavior regression elsewhere.
- **Tests 1/3/4 are sound** (not self-confirming): exact-value assertions on independently seeded data through the real router (`api_router()` + Bearer test-token, the established pattern), and they fail at the base by construction (the base response has no `skipped_workspaces`/`totals`/per-repo count fields at all). Version exclusion of v2-records under a v3 change is asserted on every surface; the no-provenance repo (repo-br-va3) is asserted zero-count and off the repos-with-work list; both §8 label classes get counts from different surfaces.

## Findings

- [**F1 — blocking, test defect**] `blast_radius_defaults_superseded_version_to_registry_current` (reconciliation.rs:5593) never creates the workspace row `ws-br-dc-own`: it calls only `require_for_ws(&state, "ws-br-dc-own", "own-required", 2)` (line 5621), which creates just the meta-spec. The handler resolves Workspace-scoped required flags by iterating `state.workspaces.list()` and matching `ms.scope_id == ws.id` (api/meta_specs.rs ~505-530); `MemWorkspaceRepository::list` (mem.rs:2746) returns only stored rows, and only ws-br-dc-stale/ws-br-dc-current are stored. For the `own-required` query `affected_workspaces` is therefore empty, `json["affected_workspaces"][0]["id"]` is Null, and `assert_eq!(None, Some("ws-br-dc-own"))` (line 5629) fails — followed by the pinned_version/reason/binding assertions. The bug is present in the original implementation commit `0e3bd118` and survives the rustfmt commit; the retained verification run evidently never executed the server blast-radius tests (it would have caught this), so the task's "probes recorded" claims rest on tests that were never run. Consequence: the task's own deferred-verifier command (`cargo test -p gyre-server reconciliation::tests::blast_radius`) ships red, and the "Workspace-scoped required flag is the workspace's own binding (workspace_binding)" default-context claim is unproven by test (the handler logic itself is correct). **Repair:** seed the workspace before the required flag, e.g. `let _ws_own = make_workspace_in_tenant(&state, "ws-br-dc-own", "default").await;` before the `require_for_ws` call. Evidence: `/tmp/stage/review-evidence/finding-test2-seeding-bug.txt`.

Minor (non-blocking, recorded for completeness):

- `to_version <= from_version` is rejected only when BOTH query params are present; a lone `to_version` below the defaulted current version is accepted (informational field only).
- Storage failures fail open to empty lists (`workspaces.list().unwrap_or_default()` etc.) — pre-existing base pattern on this read-only informational endpoint, now extended to the new stores; not a new defect class.
- Required-flag bindings are modeled at the registry's CURRENT version (required meta-specs have no pin), so a blast-radius query for a historical `from_version` lists in-scope workspaces as skipped with pinned = current. Defensible reading of the registry model (required specs are injected at current versions) and documented in-code; the spec's example only exercises the spec-level-pin skip case.
