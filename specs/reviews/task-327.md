Findings:

- [BLOCKING] **F1 (code / production-dead provenance surface): `blast_radius_repo_provenance` passes `u64::MAX` as the `until` bound to `ChainAttestationRepository::find_by_repo`, which the SQLite adapter casts to `-1` — the chain-attestation surface returns an empty set on the production backend, silently omitting all chain-attestation provenance from the per-repo spec/commit counts and totals.** Call site: `crates/gyre-server/src/api/meta_specs.rs:731` (`.find_by_repo(repo_id.as_str(), 0, u64::MAX)`). Adapter: `crates/gyre-adapters/src/sqlite/chain_attestation.rs:268-270` filters `.filter(chain_attestations::created_at.ge(since as i64)).filter(chain_attestations::created_at.le(until as i64))`; `u64::MAX as i64 == -1` (cast probe: `review-evidence/cast_probe.out`), so the generated predicate is `created_at >= 0 AND created_at <= -1`, satisfiable by no positive timestamp (SQLite demonstration: `review-evidence/sqlite_bound_demo.out`, 0 matching rows). The task's tests stay green because `test_state()` wires `MemChainAttestationRepository` (`mem.rs:7594-7605`), which compares `a.metadata.created_at <= until` in u64 semantics where `u64::MAX` is the intended "no upper bound" — exactly the mem/SQLite contract-divergence class the repo's `check-mem-port-contracts.sh` invariant exists for, here in bound semantics rather than failure constraints. Consequence: in every SQLite deployment, a repo whose only provenance under the superseded version is chain attestations contributes zero counts (AC "counts derive from provenance records" is silently violated for that surface), and the coverage row 8 claim "chain attestations (`chain_attestations.find_by_repo`, spec identity from the signed input's spec_path)" describes a query that cannot return rows in production. The pre-existing §9 drift sweep (`reconciliation.rs:1700`) shows the correct pattern: real bounds `(since, now)`.

  **Repair path:** pass a real upper bound — either `now()` (an unbounded historical blast radius is arguably wrong anyway; the §4 change is evaluated against provenance recorded up to the present) or, if a true "no bound" is intended, `i64::MAX as u64` (and mirror it in any other new caller). Then add a SQLite-backed guard so the mem/sqlite divergence cannot recur — e.g. a `gyre-adapters` test seeding a chain attestation through the SQLite repository and asserting `find_by_repo(repo, 0, <chosen bound>)` returns it (the verifier probe below reproduces the failure at the current candidate).
