- **Cryptographic verification (steps 1–3)**: `ForgeAttestationVerifier` (server) implements the port with real ring Ed25519 — bundle signature over `unsigned_canonical_json()` against the forge key (public half at `/.well-known/jwks.json`); each gate over `unsigned_gate_json()` against the named party's key (`GateAgentSigner::derive` re-derivation for `agent:<id>`); spec approval over `unsigned_spec_approval_json()` with an honest tri-state (absent → `None` + explicit finding, never silently passed; user-approver Sigstore signatures reported not-verifiable, fail-closed `Some(false)`). Sign/verify parity is by construction (both sides share the same canonical helpers and key scheme) and independently proven by the crypto-parity probe above. The `unwrap_or_default()` on the gate verify result is bool (fail-closed). Wired into `AppState.attestation_verifier` in both `build_state` (shares the persisted forge key) and `mem::test_state_inner`.

- Cosmetic: the endpoint's doc comment says a non-bundle body is "a 400"; the actual (and tested) status is 422 (axum `Json` rejection). Comment-only inaccuracy.
- Gate-crypto `Err` detail is dropped (`unwrap_or_default()`) — fail-closed false with no error string; the current `verify_gate_signature` never returns `Err`, so no finding is ever actually lost.
- The placeholder key scheme (gate-agent keys derived from the forge private key) means only a party holding the forge key can verify agent signatures — fully-external offline verification of gate signatures waits on the Sigstore/OIDC integration through the port, as documented in the port's module docs and row 13. The forge bundle signature itself is verifiable with only the published public key.
