## Findings

### F-A (blocking, code): scheduler claim protocol double-processes long delegation runs → duplicate sub-tasks

`scheduler_run_once` re-selects InProgress tasks with `updated_at <= now-60` (`SCHEDULER_CLAIM_STALENESS_SECS = 60`) while the first run may still hold the per-repo mutex inside an **unbounded** LLM call: `decompose()` → `LlmPort::predict_json` → `RigVertexAiAdapter::complete` → `post_json` on a `reqwest::Client::new()` with **no timeout** (`crates/gyre-adapters/src/llm/rig_vertexai.rs:103, 203-224`). A decomposition exceeding ~60 s is realistic in an LLM-configured deployment. The next 30 s cycle re-claims the task, blocks on the repo mutex, and once the first run finishes, `decompose_delegation` runs **again from its stale task snapshot** — it never re-fetches the task after acquiring the lock — creating a second full set of Implementation sub-tasks under the same `parent_task_id` (Phase 4 then spawns duplicate workers) and re-marking the delegation Done. The module comment ("a healthy in-flight run — whose LLM calls are not internally time-bounded — is never re-selected mid-run") is internally contradictory, and the Shipped claim that the "Backlog→InProgress claim makes re-entry idempotent" is false beyond 60 seconds. The claim is also a non-atomic read-modify-write (list → local `transition_status` → `update`; no compare-and-swap), so two concurrent cycles — the loop plus `POST /api/v1/admin/jobs/task_scheduler/run` (`JobRegistry::trigger`, `jobs.rs:151-164`, runs the handler with no serialization) — can both claim one Backlog task. None of the shipped tests can catch this: the mem test state has no LLM, so every run completes in well under 60 s. Fix direction: re-fetch the task after acquiring the repo lock and skip if it is no longer in the claimed state (or make the claim conditional/atomic), and bound the LLM call.

### F-B (blocking, code): `acknowledge_all` falsely acks unprocessed inbox messages

`run_workspace_orchestrator` ends with `messages.acknowledge_all(&orchestrator.id, "processed by workspace orchestrator run")` — it acknowledges **every** message in the orchestrator's inbox, not just the `SpecApproved` signal this run consumed. The stale-agent detector delivers `Escalation` messages to the live workspace orchestrator's inbox (`stale_agents.rs:262-278`, e.g. repo-orchestrator death); nothing in the run reads or acts on them, yet the next spec approval marks them acknowledged. `GET /api/v1/agents/:id/messages?acknowledged=false` — documented as the crash-recovery poll (`api/messages.rs:367-373`) — then hides those escalations: they are recorded as processed with no consumer having seen them. Fix direction: ack only the specific SpecApproved message id delivered to this run.

### F-C (minor, code)

1. `run_workspace_orchestrator` performs `let _ = read_git_file(...)` and discards the result — canonical Phase 2 step 1 ("reads the approved spec content") is satisfied by a decorative read that spawns a git subprocess per approval for nothing; no decision consumes the content. Either use the content (e.g. include it in the delegation task description) or drop the call.
2. `decompose_delegation`'s spec_ref-absent fallback resolves the ledger SHA via `.map(|e| e.current_sha).unwrap_or_default()`; on lookup failure the empty SHA is not an error — the delegation completes with sub-tasks pinned to a malformed `spec_ref` `"path@"` (empty SHA), converting "cannot determine the approved blob" into "empty blob is fine" — the same failure class `check-fail-open-ref-resolution` bans for `resolve_ref`. Fail/block the delegation instead.

### F-D (coverage honesty, not a violation of this task's excerpt)

Canonical §Phase 3 step 2 ("Reads the repo's current codebase state (via MCP tools)") is not implemented — decomposition input is spec content only; tasks are created via the task repository rather than the `task.create` MCP tool (equivalent effect). The task's Spec Excerpt omits this step, so it is outside this task's contract, but §Phase 3 of the coverage matrix must not be marked fully implemented on the strength of this candidate without disclosing it.
