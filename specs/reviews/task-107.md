## Findings

- [ ] **F1: Fulcio issuance request is rejected by every real Fulcio instance — `publicKey.content` is sent base64(DER), but Fulcio parses that field as PEM text or raw DER bytes.** `request_fulcio_certificate` (sigstore.rs:104-118) builds the SPKI, base64-encodes it (`spki_b64`), and puts that ASCII string into `publicKeyRequest.publicKey.content`. The Fulcio v2 proto defines `PublicKey.content` as a `string` documented "PKIX, ASN.1 DER or PEM-encoded"; the server parses it via `challenges.ParsePublicKey` (fulcio `pkg/challenges/challenges.go:97-112`), which first tries `cryptoutils.UnmarshalPEMToPublicKey([]byte(content))` (PEM text) and on failure `x509.ParsePKIXPublicKey([]byte(content))` (raw DER bytes). A base64 ASCII string is neither — both parses fail and Fulcio returns 400 invalid public key. The reference client (sigstore-go `pkg/sign/certificate.go:148-159`) populates `Content` with `keypair.GetPublicKeyPem()`, i.e. the PEM text itself. Consequence: in `fulcio` mode every issuance against a real Fulcio (public or private, including one configured to accept Gyre's OIDC issuer) fails and silently falls back to local Ed25519 (jj.rs:166-181) — acceptance criteria "Fulcio certificate issuance using agent OIDC JWT", "Commits signed with Fulcio-issued certificate", and "Signatures recorded in Rekor" are met only against the in-test mock, never in production. The mock is self-confirming on exactly this point: `spawn_mock_signing_stack`'s signingCert handler itself base64-decodes `content` (jj.rs:759-765), so the tests enshrine the wrong encoding instead of catching it. Fix: send the PEM-encoded public key (`-----BEGIN PUBLIC KEY-----…`) in `content`. (The `proofOfPossession` encoding — base64 of the raw 64-byte P1363 signature into the protojson `bytes` field, over the `sub` claim — is correct: sigstore's `ECDSAVerifier.VerifySignature` accepts IEEE P1363, and signing over `sub` matches Fulcio's challenge check.)

- [ ] **F2: Spec attribution requirement unmet — the signing JWT hardcodes `task_id: "task-107"` and `spawned_by: "system"`, and task/user identity is never bound into the certificate, the record, or the verification result.** Spec §Layer 3: "the signature proves which agent, **on which task, spawned by which user**, made the commit." `sign_fulcio` (jj.rs:215-218) mints a fresh JWT via `state.agent_signing_key.mint(&auth.agent_id, "task-107", "system", …)` — literal placeholder values standing in for runtime values that are available: `AuthenticatedAgent.jwt_claims` (auth.rs:315) carries the caller's validated claims including `task_id` and `spawned_by` (AgentJwtClaims, auth.rs:48-97), or the agent's presented JWT could be forwarded. Downstream, nothing carries the attribution even if minted correctly: the leaf certificate binds only the agent_id (SAN URI + CN, via the JWT `sub`), `CommitSignature` (commit_signatures.rs:116-152) has no task_id/spawned_by fields, and `SignatureVerificationResult` (sigstore.rs:58-74) has no attribution fields to check — `verify_signature_fulcio` verifies agent identity only. Net: the signature proves *which agent* made the commit but proves nothing about the task or spawning user, exactly the two attribution dimensions the spec sentence adds beyond agent identity. Fix: extract task_id/spawned_by from `auth.jwt_claims` at mint time, store them on the `CommitSignature` record (and/or bind them as Fulcio-recognized extension claims where the Fulcio instance supports it), and check them in the verification endpoint's result.

- [ ] **F3: Trust-anchor substitution — verification prefers the record-claimed `fulcio_url`/`rekor_url` over server configuration.** `verify_signature_fulcio` (sigstore.rs:372-375, 406-409) resolves the Fulcio trust bundle and Rekor log from `record.fulcio_url`/`record.rekor_url` first, falling back to `state.signing_config` only when the record fields are absent. The `CommitSignature` store is an in-memory map with no integrity protection of its own (that protection is what the signature chain is supposed to provide), so a tampered record pointing at an attacker-controlled Fulcio+Rekor pair passes checks (b) and (d) trivially: the attacker's stack serves a trust bundle whose root validates the (also swapped) certificate and a 200 on the entry lookup. The server's `GYRE_FULCIO_URL`/`GYRE_REKOR_URL` config is the trust anchor; task plan item 3(b) requires the certificate be "issued by the expected Fulcio instance" — expected means the configured instance, not whatever the record claims. Fix: verify against `config.fulcio_url`/`config.rekor_url` (at minimum, require the record URLs to equal the configured ones and fail on mismatch).

- [ ] **F4: Rekor check is existence-only — the entry is never confirmed to match this commit's signature.** `check_rekor_entry` (sigstore.rs:519-539) performs `GET {rekor}/api/v1/log/entries/{uuid}` and treats any HTTP 200 as pass. The entry body is never fetched and compared: the verifier does not confirm the entry's hashedrekord payload contains this commit's digest, this signature, or this certificate. A record whose `rekor_entry_id` is any existing UUID in the log (any entry at all, from any signer) passes check (d). Task plan item 3(d) requires "a **matching** Rekor entry exists"; spec §Layer 3 requires Rekor recording "for non-repudiation" — an unrelated entry provides neither matching nor non-repudiation. Fix: fetch the entry, decode the hashedrekord body, and compare the `data.hash` (and ideally `signature.content`) against the record.

- [ ] **F5: Certificate validity period is never checked — expired certificates verify.** Spec §Layer 3: "a **short-lived** signing certificate." `check_chain` (sigstore.rs:441-484) validates the root self-signature, intermediate links, and leaf signature, but never examines `not_before`/`not_after` on any certificate. A record whose leaf certificate is expired (or not yet valid) passes check (b) with `certificate_chain_valid: true` and the overall result `valid: true`. The whole point of Fulcio's short-lived certificates is that the validity window bounds the key's usefulness; skipping the time check voids that property. Fix: parse and enforce `not_before <= now <= not_after` on the leaf (and intermediates) in `check_chain`.

- [ ] **F6: Task plan item 3 "Surface verification status in provenance chain API" is unimplemented.** The task's implementation plan (task-107.md, item 3, last bullet) requires verification status to be surfaced in the provenance chain API. The commit adds a standalone endpoint `GET /api/v1/repos/:id/commits/:sha/signature/verification` (api/mod.rs:215-216) but does not touch `api/provenance.rs` — the provenance chain API (`GET …/attestations/:commit_sha/verification`, `/bundle`, `/chain`, api/mod.rs:117-128) has no commit-signature integration (grep: zero `CommitSignature` consumers in provenance.rs). The attestation-chain verification result reports nothing about commit signature status, so a consumer of the provenance API cannot see whether a commit's Fulcio signature verifies. Either integrate the commit-signature verification result into `get_verification`/`get_attestation_chain` responses or strike the plan bullet with justification.

- [ ] **F7: No negative tests for verification checks (a), (b), or (c) — only the Rekor leg has failure coverage.** The four Fulcio verification phases are signature check (a), chain check (b), subject check (c), Rekor check (d). Test coverage: `verification_fails_when_rekor_entry_missing` covers (d) negatively; (a), (b), (c) have zero negative tests — `jj_squash_fulcio_keyless_signs_and_verifies` exercises only the all-pass path, and the mock stack (`spawn_mock_signing_stack`, jj.rs:736-829) has no knobs to produce a tampered signature, an invalid chain, or a mismatched subject (the MockCa always issues a valid chain with matching SAN/CN; the only failure control is the Rekor `AtomicBool`). Plausible regressions that would go undetected: signature verification disabled/inverted, chain check accepting any certificate, subject check accepting any CN. Add one negative test per phase (tampered `signature` bytes → `signature_valid: false`; leaf signed by a different CA → `certificate_chain_valid: false`; certificate CN/SAN ≠ `oidc_subject` → `subject_matches: false`).

- [ ] **F8: New verification endpoint is absent from the ABAC route registry — it authenticates but bypasses all ABAC policy evaluation, and no CI check catches it.** `GET /api/v1/repos/:id/commits/:sha/signature/verification` is registered in `api_router()` (api/mod.rs:214-217) but has no `RouteResourceMapping` in `ResourceResolver::routes` (abac_middleware.rs) — its sibling `…/signature` route does have one (abac_middleware.rs:138, `"repo"`, read). The middleware resolves the matched pattern against the registry and **falls through with no policy evaluation** when the pattern is absent (abac_middleware.rs:769-773: `None => return next.run(req).await`), so the endpoint gets require-auth but skips ABAC entirely: no repo-tenant check, no role/policy check. A route-registry entry is how every other repo-scoped route in the file is authorized, so this endpoint is less protected than its own sibling. The comment at abac_middleware.rs:79 ("Every route in `api_router()` must have an entry here (enforced by `scripts/check-api-auth.sh`)") is not actually enforced: `check-api-auth.sh` only verifies the three middleware layers are layered on `api_router()` (Check 1) and per-handler auth on routes mounted *outside* the api merge (Check 2) — it never compares `api_router()` routes against `all_patterns()`, so the gap passes both CI lints (re-ran `scripts/check-api-auth.sh` and `scripts/check-abac-context-parity.sh`: both pass). The task-107 test suite doesn't catch it either: `verify_and_parse` (jj.rs:848-864) drives the router built by `crate::build_router` but with the `test-token`/`system` identity, which bypasses ABAC (abac_middleware.rs:792), and `resolver_covers_required_routes` (abac_middleware.rs:1000-1028) enumerates a hand-picked list that doesn't include either signature route. Fix: add `RouteResourceMapping::api("/api/v1/repos/:id/commits/:sha/signature/verification", "repo", None)` next to the sibling entry, and (recommended) extend `check-api-auth.sh` with a registry↔router parity check so the "enforced by" comment is true.

**Areas examined and cleared this round (recorded so future rounds don't re-litigate):**

- **Rekor hashedrekord wire format is correct** — `record_in_rekor` (sigstore.rs:158-197) sends `signature.publicKey.content` as base64(PEM). Upstream `DecodeEntry` base64-decodes that field, and `x509.NewPublicKey` PEM-parses the result, accepting a certificate PEM block (`CertificatePEMType` case). The 64-byte IEEE P1363 ECDSA signature (ring `ECDSA_P256_SHA256_FIXED_SIGNING`) is accepted by sigstore's `ECDSAVerifier.VerifySignature` P1363 fallback path. The artifact digest (SHA-256 over the commit-SHA hex string bytes) is computed identically at sign time and record time, so Rekor's own `validate()` cross-check passes. (The Fulcio side of the wire is a different story — that's F1.)
- **"Every commit is cryptographically signed" scope** — `jj new` creates commits without signing and the git push path (`git_http.rs::git_receive_pack`) has no signing integration. Not recorded as a finding: milestone M13.8 (`specs/milestones/m13-forge-native.md:223` "enforce signing at squash time") scopes the enforced surface to `jj squash`, and the task plan wires only squash. The Layer 3 sentence remains unmet at platform scope, but that is a spec-level gap for a future task, not a defect in this task's implementation of its plan.
- **Mock self-confirmation on the Rekor leg** (adjacent to F1's mock note and F7): `spawn_mock_signing_stack`'s `rekor_post` handler discards the request body entirely (`let _ = body;`, jj.rs:796-803), so the tests never assert the recorded entry matches this commit's digest/signature/certificate. This is the test-side enabler of F4 and is subsumed by fixing F4 + F7.

- [ ] **F9: Signature records are process-memory-only — a server restart silently orphans every signed commit, and the verification endpoint (an acceptance criterion) 404s on all of them.** `AppState.commit_signatures` (lib.rs:301-302) is `Arc<Mutex<HashMap<String, CommitSignature>>>` — a bare in-memory map initialized to `HashMap::new()` in `build_state` (lib.rs:936) with no load path. There is no `CommitSignature` port or adapter anywhere (`grep CommitSignature` in `gyre-ports`/`gyre-adapters`/`gyre-common`: zero hits), while every sibling store in `AppState` is repository-backed via `gyre_ports` (47 `store!` wirings in `build_state`: audits, spec registry, trust anchors, …). Consequence: after any restart (or crash) of the server, `GET /api/v1/repos/:id/commits/:sha/signature` and `…/signature/verification` return 404 for every previously signed commit — including commits whose Rekor entries still exist. Spec §Layer 3 requires signatures "recorded in Rekor transparency log … for non-repudiation"; the Rekor entry may survive, but the platform's own retrieval and verification API — task plan item 3 and the acceptance criterion "Verification endpoint checks certificate chain and Rekor entry" — can no longer fulfill its function for any pre-restart commit, and the `rekor_entry_id` needed to even find the Rekor entry is itself only in the lost record. The task's local-mode records (default `GYRE_SIGNING_MODE=local`) have no Rekor entry at all, so for them restart destroys the only copy of the signature. Fix: add a `CommitSignatureRepository` port with a SQLite adapter (mirroring the existing store pattern), persist on insert in `jj_squash`, and load/hydrate lookups from it in `get_commit_signature`/`get_commit_signature_verification`.
