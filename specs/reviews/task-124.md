## Findings

- [**F1 (major): the deactivation cascade misses the impersonation auth path.**] `resolve_impersonation_auth` (crates/gyre-server/src/impersonation.rs:666-704) checks only that the session is un-ended/un-expired and that the target user record exists — it never consults `target.is_deactivated()` and never loads the impersonator's account at all. It is reached from three call sites that all resolve BEFORE the API-key branches that carry the new deactivation check: the HTTP extractor's step-1.5 impersonation branch (auth.rs ~1021), the WebSocket `authenticate_token` impersonation branch (auth.rs ~1288), and the global auth gate (lib.rs ~728). `deactivate_user` also never ends active impersonation sessions. Consequence: a user deactivated by a TenantAdmin retains full authenticated API access for the remaining lifetime of any impersonation session minted before the deactivation — including the case where the DEACTIVATED account is the impersonator (e.g. a rogue TenantAdmin being locked out: their unexpired impersonation JWT keeps authenticating as the target user with the target's roles). This directly contradicts the handler's own cascade claim ("fails authentication on every path (API-key extractor, WebSocket auth, SSO login)") and docs/api-reference.md's "immediately fails authentication on every path", so the task's "deactivates user with cascade" acceptance criterion is not fully met. Full source excerpts, consequence analysis, and a suggested regression test: `/tmp/stage/review-evidence/F1-impersonation-deactivation-bypass.md`.

  **Repair path (mechanical):** in `resolve_impersonation_auth`, reject when the loaded `target.is_deactivated()` and when the impersonator's stored account is deactivated or missing (load it by `session.impersonator_id`); optionally also end the target's and impersonator's active impersonation sessions in `deactivate_user` as defense in depth; add the regression test. Record the fix commit in task-124's `commits:` frontmatter.
