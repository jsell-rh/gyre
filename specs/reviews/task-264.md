## Verified working (independent source inspection + probes)

1. **Every commit surface signs.** All four surfaces route through the shared `commit_signatures::sign_commit` and persist through `CommitSignatureRepository`: `jj new` (api/jj.rs; `JjOpsPort::jj_new` now returns `JjNewChange {change_id, commit_id}` — the real jj adapter parses `change_id ++ "\x1f" ++ commit_id` from `jj log`), `jj squash` (api/jj.rs), git HTTP push (git_http.rs `git_receive_pack` — signs every commit in the applied-update ranges *before* responding; on failure undoes refs, emits `PushRejected` + a `git_push_rejected` audit event with gate `commit-signing`, and rejects 403/502), and MR merge (merge_processor.rs `sign_merge_commit`, wired into both the single-MR `process_next` path — failure triggers the existing post-merge recovery protocol — and the atomic-group path — failure rolls the group back). No other production commit surface exists (remaining `git commit` matches are `#[cfg(test)]` fixtures; spawn.rs `jj_new` provisions the agent's private jj workspace, not a landed repo commit — outside the task's enumerated surfaces).
2. **Keyless by default.** `SigningMode::parse("")` → `Fulcio`; production `build_state` → `SigningConfig::from_env()` → `SigningMode::from_env()`; `local`/`none` are explicit opt-ins; an unrecognized value is a hard startup error (documented in server-config.md). No `_ => Local` downgrade remains.
3. **No silent degradation.** The old `unwrap_or_default()` empty-bearer + "falling back to local signing" path is gone: `sigstore::jwt_is_presentable` (decodable JWT with a `sub` claim) gates *before* any HTTP call; refusals are 403 `CommitSigningRefused`; stack failures are 502 `CommitSigningFailed` / push rejection / merge revert, all naming the active mode via `CommitSigningError::describe()`. The only fallback is the operator-configured `GYRE_SIGNING_FULCIO_FALLBACK=local`, which warns and stores an honest `sigstore_mode=local` record. The new tests (`jj_squash_fulcio_unreachable_fails_loudly_no_local_fallback`, `push_rejected_loudly_when_fulcio_unreachable`, `merge_commit_signing_fails_loudly_when_fulcio_unreachable`) assert exactly the task's verification intent: explicit error, no local-key record, refs undone, audit event recorded.
4. **Attribution is cryptographically bound.** Local Ed25519 (`sign_commit_local`), keyless ECDSA (`sign_commit_keyless` step 4), and the Rekor hashedrekord digest (`commit_digest`) all cover `signed_commit_payload {commit_sha, task_id, spawned_by}` (canonical serde JSON, fixed field order). Verification recomputes the payload from the record's own fields on both paths (`verify_commit_signature` → `record_signed_payload`; `check_signature`/`check_rekor_entry`), so a tampered `task_id`/`spawned_by` fails the signature check *and* the Rekor content-match — the tamper tests (`local_verify_fails_on_tampered_task_attribution`, `verification_fails_on_tampered_task_attribution`) exercise the production verify path with real crypto, not mirrored logic.
5. **Real Rekor for attestation bundles.** `NoopRekorClient` is deleted (no production or test wiring remains — only historical task/spec prose references it). Production `build_state` and the mem fixture wire `HttpRekorClient` (latency-bounded, explicit `Err` on unconfigured log / HTTP failure / unsigned bundle, entry UUID from the response map). `store_merge_attestation_bundle` returns `Result`, persists the entry UUID in the KV namespace `rekor_attestation_entries` (port-backed, restart-durable), treats `Ok(None)` as an explicit error, and both merge-processor success paths surface failures as warnings while not rolling back the landed merge. The wire behavior is proven by the adapters test suite run here.
6. **Non-regressions handled deliberately.** `mem::test_state` pins `SigningMode::Local` (was effectively local via env-unset default before — no test-behavior change), and the four production-wired integration harnesses that push/merge with dev tokens explicitly set `GYRE_SIGNING_MODE=local`; no other integration binary drives a commit-producing surface (checked `api_integration`, `task134_review_probe`, `tenant_isolation`, `workspace_scoping`, `auth_integration` — their merge-queue/push usages never reach `MergeResult::Success` or an applied ref update). Docs (server-config.md, api-reference.md) updated coherently, including the GYRE_REKOR_URL asymmetry (commit signatures default to the public Rekor; attestation bundles require explicit configuration — documented).

Test-inflation check: none found. The fail-loud tests drive the real router/transport against an unreachable `fulcio.invalid` with a real minted JWT and assert absence of local-key records; the tamper tests break real signatures; the adapters Rekor test asserts on the actual HTTP request bytes.

## Findings

- [F1] **Major (code, `crates/gyre-server/src/git_http.rs` — `list_new_commits`, signing loop at ~line 999): a branch-creation push signs the ENTIRE reachable history and overwrites existing attribution-bound signature records.** `list_new_commits` uses `git log <new_sha>` (full walk) whenever `old_sha` starts with `00000000` — the normal case for every new branch push (probe: 5-commit repo → branch-creation push selects 5 SHAs to sign vs 2 for the equivalent fast-forward push). The signing loop has no dedup, and `CommitSignatureRepository::save` **upserts** on `(repo_id, commit_sha)` (mem.rs:7478-7491; SQLite `save_upserts_on_same_key`). Consequences: (a) **attribution rewrite** — any agent pushing a branch over already-signed history re-signs every ancestor commit with *their* agent/task/spawned_by attribution and replaces the original records, so the platform's stored proof for commits made by other agents is destroyed (the layer-3 requirement "the signature proves which agent, on which task, spawned by which user, made the commit" no longer holds for those commits; the replacement record verifies cleanly, so nothing detects it); (b) **cost/fail-loud amplification in the default keyless mode** — pushing a feature branch (the mainline agent workflow: agents push `feat/*` branches for MRs) performs O(total repo history) sequential Fulcio certificate issuances + Rekor submissions, each latency-bounded at 10 s, synchronously before the push response — on any established repo this makes branch pushes impractically slow or guarantees a 502 rejection. Existing tests miss it because they use fast-forward pushes and local mode (upsert is silent). **Repair (small):** skip SHAs that already have a persisted `CommitSignature` record (lookup before `sign_commit`), which preserves the intended "every new commit gets signed" behavior for genuinely-new commits and stops both the overwrite and the re-signing storm; add a regression test that pushes a second branch over already-signed history and asserts the original records (signer_id/task_id/spawned_by) are unchanged.
- [F2] **Minor (code, same path): landed-commit enumeration fails open.** `list_new_commits` warn-and-`continue`s on a `git log` failure, and the signing block is skipped entirely when the enumeration returns empty — a push whose enumeration fails lands with unsigned commits and a success response, contradicting the fail-loud mandate. Not exploitable via a forged `old_sha` (real `git receive-pack` enforces the CAS old-value on applied updates, and `verify_applied_ref_updates` only admits genuinely-applied refs), so the reachable modes are pathological (git spawn failure mid-request, corrupted object store) — but the failure mode should reject the push rather than skip signing.

Non-blocking observations (recorded for completeness):

- `sign_merge_commit` in keyless mode mints a short-lived forge-issued JWT for the merge committer (the MR author agent, or `forge-merge-queue` for human MRs). Against the default public `fulcio.sigstore.dev` this will be rejected (untrusted issuer) and the merge reverts/escalates — fail-loud per spec, and the docs say to point `GYRE_FULCIO_URL` at a private Fulcio trusting the forge's OIDC issuer or opt into `local`; noting that out-of-the-box default deployments cannot complete keyless signing until so configured.
- jj new/squash mutate the repo before signing fails (the change/commit exists, the response errors, no signature record). This matches the task's verification intent ("no local-signed record and no success response"), so accepted.
- Server-side lib/integration test execution is deferred to the verifier exactly as recorded in task-264 `## Shipped` (build-budget constraint; `cargo check -p gyre-server --tests` clean here).
