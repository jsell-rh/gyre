## Verified against the five required behaviors

1. **Every commit surface signs.** A single shared entry point `commit_signatures::sign_commit` is called by all four surfaces, each persisting through `CommitSignatureRepository`: `jj new` (`api/jj.rs`; the `JjOpsPort::jj_new` port now returns `JjNewChange {change_id, commit_id}` so the signable content-addressed commit id is available — implemented by both the real `JjOpsAdapter` and the mem doubles, satisfying the mem-port-contract check), `jj squash` (rewired to the shared entry point), git HTTP push (`git_http.rs` `git_receive_pack`: `list_new_commits` enumerates every commit each applied ref update landed, signs synchronously before responding, undoes refs + emits a `git_push_rejected` audit event naming the `commit-signing` gate and the active mode on failure; enumeration failure rejects the push fail-closed; already-signed SHAs are skipped so branch pushes over signed history preserve original attribution records), and MR merge commits (`merge_processor.rs` `sign_merge_commit` in both the single-MR path — signing failure triggers the post-merge recovery protocol: queue pause, revert, escalation — and the atomic-group path, which rolls the group back). Authorization precedes signing on every surface (repo ABAC checked before the signing blocks). `GYRE_SIGNING_MODE=none` remains an explicit opt-in only.
2. **Keyless by default.** `SigningMode::parse` maps unset/empty → `Fulcio`; `local`/`none` are explicit opt-ins; any unrecognized value is a hard startup error (panic at `build_state` boot) instead of the old silent `_ => Local` downgrade. Production wiring uses `SigningConfig::from_env()` (lib.rs:2030). Docs (`server-config.md`, `api-reference.md`) updated to match.
3. **No silent degradation.** `sign_commit` refuses keyless signing for callers with no presentable OIDC JWT (`sigstore::jwt_is_presentable` gates before any HTTP call — an empty/dev-token bearer is never presented to Fulcio; surfaces as 403 `CommitSigningRefused` / push rejection) and fails Fulcio/Rekor stack errors loudly (502 `CommitSigningFailed` / push rejection / merge revert+escalation), with the error naming the active signing mode. The only fallback is the operator-configured `GYRE_SIGNING_FULCIO_FALLBACK=local`, which warns and stores an honest `sigstore_mode=local` record — allowed by the AC's "operator-configured behavior surfaced in the response/audit". The old "Fulcio keyless signing failed; falling back to local signing" path is gone (grep-verified).
4. **Attribution is cryptographically bound.** The canonical `signed_commit_payload` `{commit_sha, task_id, spawned_by}` (serde struct, fixed field order) is what the local Ed25519 key signs, what the Fulcio ephemeral P-256 key signs, and what the Rekor hashedrekord digest covers (`commit_digest` now takes all three fields). Verification recomputes the payload from the record's OWN fields (`record_signed_payload`) in both the local path (`verify_commit_signature`) and the fulcio path (signature check + Rekor entry content-match), so tampering a stored `task_id`/`spawned_by` — exactly the task's second verification-intent probe — breaks both the signature check and the entry match. The rogue-leaf test was correctly repaired to sign the canonical payload (a real forger controls their key), so it still isolates leaf-CA binding. Push/merge attributions come from real lookups (validated JWT claims, or the pusher/author agent's stored task/spawner context via `resolve_agent_context`) — never fabricated literals.
5. **Real Rekor for attestation bundles.** `NoopRekorClient` is deleted from the codebase (grep: only a doc comment mention remains); production `build_state` and the mem fixture wire `HttpRekorClient`, which submits each signed bundle as a hashedrekord to `GYRE_REKOR_URL` (latency-bounded reqwest, 10 s timeout — passes `check-unbounded-external-http`) and whose entry UUID is persisted keyed by MR id (KV namespace `rekor_attestation_entries`). `store_merge_attestation_bundle` returns `Ok(())` only when storage AND the transparency-log submission with its persisted UUID succeeded; unconfigured log and outages are explicit `Err`s surfaced as warn/audit states by both merge-processor success paths — never a silent `Ok(None)` — while the already-landed merge is not rolled back. The Rekor entry binds the bundle digest, the existing multi-party `bundle_signature`, and the forge public key PEM (same key `ForgeSigner` signs with — verified consistent in both production and mem wiring).

## Non-blocking observations (recorded, not findings)

- Recovery/revert commits created by the post-merge failure protocol and atomic-group rollback (`revert_commit`) are commit-producing but unsigned. The task's required behavior and AC enumerate exactly the four surfaces (jj new, jj squash, git push, MR merge); recovery reverts are outside that scope. Worth a future task if "every commit" is read literally at the spec level.
- Pre-task-264 local-mode records (signature over the bare commit SHA) will fail verification after the payload change — the payload recompute makes old records unverifiable rather than tampered. Acceptable for this platform's lifecycle (no migration path was required by the task), but operators upgrading an existing deployment with stored signatures should expect verification failures on old records.
- A default deployment (fulcio mode, public `fulcio.sigstore.dev`) will fail every commit operation until the operator points `GYRE_FULCIO_URL` at a Fulcio that trusts the forge's own OIDC issuer (Gyre is an OIDC IdP per Layer 2), or opts into `local`/`none`/fallback. This is the intended consequence of keyless-by-default + fail-loud, and `server-config.md` documents the modes; noting it for operational awareness.
- `unsafe { std::env::set_var(...) }` in the four integration harnesses sets the signing mode before `build_state` in the same test thread; cross-test env races are theoretically possible but each harness sets the same value consistently.
