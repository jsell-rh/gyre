## Observations (non-blocking, recorded for the verifier/auditor)

- **spec_sha comparison source.** `resolve_task_binding_context` prefers the newest non-revoked approval-event SHA, falling back to the ledger's `current_sha`. Consequence: in the window where a spec is *modified but not yet re-approved*, an old SignedInput still passes the spec_sha binding (it is rejected the moment a different SHA is approved, and the ledger-fallback path covers spec-history-less ledgers). This matches the acceptance criterion's literal wording ("the task's **currently approved** spec SHA" — the newest active approval) and the plan's explicit "if unavailable, pass `None`" leniency; the modified-unapproved window is additionally gated by the spec lifecycle (`auto_invalidate` → Pending, signal chain requires Approved). If the stricter reading is wanted (compare against ledger `current_sha` unconditionally, rejecting on any un-reapproved modification), that is a one-line source swap in `resolve_task_binding_context` plus a test — flagging as a conscious semantic choice, not a hollow check. The core §1.2 residual risk (wrong-*context* replay: repo/workspace/generation) is fully enforced regardless.
- Storage errors while resolving the approved spec SHA skip only the spec_sha binding (plan-sanctioned `None` semantics); repo/workspace/generation bindings are unaffected.
- `gyre-cli` could not be compile-verified in this sandbox: `cargo build -p gyre-cli` fails at dependency fetch (`static.crates.io:443` unreachable — infrastructure restriction, exit 101; log in `cli-build.txt`). Not a code defect: gyre-cli defines its own `TaskResponse` DTO and constructs no `gyre_domain::Task` literals, and the additive serde field cannot break its deserialization. The verifier with network access should run `cargo build --all` as the acceptance criterion states.
