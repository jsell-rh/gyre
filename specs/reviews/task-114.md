## Non-blocking observations (recorded, no action required for approval)

- **O1 — the `/@{username}` routing tests are mirrored logic.** `AppShell.test.js`'s `parseUrl`/`urlFor` unit tests run against a copy replicated from `App.svelte` (a pre-existing, repo-wide pattern — the base `b8d63b0d` version of the file already says "replicated from App.svelte"). Mutation probe: disabling the real route branch in `App.svelte` leaves all 77 tests green, and no e2e test navigates to `/@{username}`. Not blocking because (a) the shipped route was independently verified working by the mounted-route probe above, (b) the goal marks "new tests for already-working behavior" out of scope, and (c) the pattern predates this task and covers every other route equally. If a future round touches routing, a mounted-App test (like the existing drawer-navigation tests) or an e2e navigation to `/@{username}` would close the regression-detection gap.
- **O2 — mem `list_by_approver` ordering comment is inaccurate.** `mem.rs` collects `HashMap::values()` and calls `.reverse()` with the comment "insertion order: newest first" — a `HashMap` has no insertion order, so the documented "newest first" port contract is not actually guaranteed by the mem adapter (SQLite/PG order by `id.desc()`). No behavioral impact today: the activity handler re-sorts events by raw timestamp before paginating, and stats is a count. Worth fixing if a future consumer relies on port ordering.
- **O3 — identity-form attribution is inherently fuzzy.** Spec approvals attribute by `user:{display_name}`/`user:{username}` because that is all the durable ledger stores (verified against `approve_spec`'s writes). Two same-tenant users sharing a display name/username cross-attribute approval rows. This follows and improves on the pre-existing precedent — `get_judgments` queries `spec_approvals.approver_id` by `user_id`, which can never match the `user:{display_name}` form production writes (pre-existing defect outside this task's scope). A durable fix needs the ledger to record user ids; that is a spec/data-model change, not a task-114 repair.
- **O4 — generated output (verifier-owned, per protocol):** the committed `web/dist/index.html` serves `index-B7T1ubsg.js`, which already contains the `user_profile` route (3 occurrences), so the shipped bundle includes this feature. Running `npm test` in-sandbox regenerates `web/dist` as a side effect; that rebuild was reverted before finishing (dist is the deterministic verifier's responsibility — it rebuilds, tests, and commits the assets against the integrated tree). No source defect claimed here.
