### Findings

- [-] **F1 (minor, blocking approval): Spec `links` indexed field is never indexed.** search.md §Searchable Entities lists Spec's Indexed Fields as "title, path, full content, owner, links". `spec_document` (`crates/gyre-server/src/search_indexer.rs`) indexes title (with path fallback), path (entity_id), full content (body), and owner (facet) — but `SpecLedgerEntry.linked_tasks`/`linked_mrs` appear nowhere in the document: not in body, not in facets, not in entity_id (`grep linked crates/gyre-server/src/search_indexer.rs` hits only the coordinator test seeding empty vectors). Both call sites — `index_repo_specs` (push path) and `reindex_all` — are affected. Reproduce: seed a `SpecLedgerEntry` with `linked_tasks: ["task-9x9"]`, run the reindex, then `GET /api/v1/search?q=task-9x9` returns no spec. Acceptance criterion 1 ("indexed with the specced fields and facets") is not fully met for the Spec row, so the §Searchable Entities coverage row cannot be truthfully closed yet. Remedy: append the linked task/MR ids to the spec document body (same pattern task labels already use) or add them as facets, in both `index_repo_specs` and `reindex_all`, with the coordinator test extended to assert a spec is findable by a linked id.

### Non-blocking observations (for the record; no action required of this task)

- **PG facet searchability**: the Postgres tsvector (task-201 schema, untouched here) is generated from `title || ' ' || body` only, so facet-only specced fields (commit author, review decision/reviewer, spec owner, event agent_id) are filterable but not full-text-matched on PG. On SQLite they are matched — the FTS5 `metadata` column is tokenized (not UNINDEXED), which matches the spec's own example DDL. Backend divergence owned by task-201's schema, not this task's document builders.
- **Eventually-consistent staleness**: retention purges (`AnalyticsRepository`/`AuditRepository::delete_older_than`) and spec removal from the manifest leave stale docs until the next full reindex. §Index Updates does not require de-indexing; the admin reindex clears both.
- **Double indexing on REST write paths** (decorator + explicit handler call) — idempotent upserts, minor waste only.
