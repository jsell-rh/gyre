## Non-blocking observations

- Sessions bind to **API-key credentials** only; Keycloak/federated JWT auth is not session-tracked. This is a sound adaptation, not a hollow claim: user JWTs are short-lived IdP-issued tokens with no stable per-request session token to bind, while the API key is the platform's native long-lived user credential (HSI §12) whose SHA-256 is the spec's `token_hash`. The coverage note scopes the claim accurately ("on successful API-key auth") rather than claiming all auth kinds.
- Concurrent first presentations of the same credential+device could race-mint duplicate session rows (no unique constraint on the device tuple). Benign: the newest row wins resolution, duplicates age out via retention, no security impact.
- `find_by_token_hash` is implemented per the specced port and tested, but the production auth path resolves sessions by credential+device — the specced method is available for future per-token resolution.
