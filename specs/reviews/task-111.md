### Findings

- [open] **F1 (major): the three TenantAdmin session endpoints have no tenant containment — an Admin of one tenant can view and revoke any user's sessions in any other tenant.** `list_user_sessions` (`crates/gyre-server/src/api/users.rs:859`), `revoke_user_session` (:890), and `revoke_all_user_sessions` (:926) check `auth.roles.contains(&UserRole::Admin)` and that the target user exists, but never compare the loaded user's tenant against the caller's. `UserRepository::find_by_id` is not tenant-scoped and `state.sessions` is a shared unscoped `Arc<dyn SessionRepository>`, so nothing else contains the access. Reproduced with a probe test (restored afterwards; log `/tmp/stage/review-evidence/task-111-probe-cross-tenant.log`): an Admin-role API-key principal of tenant t-1 calling `GET /api/v1/users/{victim_id}/sessions` for a tenant-t-2 user returns **200 OK** with the victim's session rows (`user_agent`, `ip_address`, `last_active_at` — device surveillance data); the revoke variants are the same gap as cross-tenant sign-out DoS. This violates the repo invariant for ABAC-exempt routes ("load the scoped entity, compare tenant/workspace against the caller, return Forbidden on mismatch" — AGENTS.md / `check-abac-exempt-handlers.sh` Rule 4) and the codebase's own precedent: `create_user` in the same file (shipped by this same branch) enforces exactly this comparison and names it "repo per-handler invariant", as do `compute_targets.rs`, `trust_anchors.rs`, and `orchestrator.rs`. Spec-side, `GlobalRole::TenantAdmin` is tenant-scoped ("Full tenant management" of that tenant, user-management.md §Global Role), so "TenantAdmins can view and revoke any user's sessions" means users of their own tenant; only system principals (`is_system_principal()`) may operate cross-tenant. The existing killing tests (`tenant_admin_can_view_and_revoke_another_users_sessions`, `non_admin_cannot_view_or_revoke_another_users_sessions`, `admin_session_endpoints_unknown_user_is_404`) all use same-tenant or system-principal callers, so none catch it. Remedy: in all three handlers, after loading the target user, reject with Forbidden unless `auth.is_system_principal()` or the target's `tenant_id` matches the caller's `auth.tenant_id` (fail-closed on `None`), and add a killing test with a cross-tenant Admin (seed a second tenant as in the probe).
