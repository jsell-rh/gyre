## Non-blocking observations (recorded for follow-up; not task-contract violations)

1. **Eventual-consistency window on the stored half.** The post-receive ledger sync runs in a detached `tokio::spawn`, and push 1's HTTP response can return before its edge lands in `spec_links`. A client that immediately pushes the back-edge in repo 2 is then checked against a graph still missing push 1's edge and is accepted, permanently installing the cycle — the e2e test itself must `wait_for_stored_link` before push 2 to be deterministic. This is inherent to the task-prescribed design ("all stored links in the durable spec_links table") plus the pre-existing async-sync architecture, not to this implementation; a follow-up could make the cycle gate (or the sync) synchronous for the receive path, or re-check at sync time and emit a drift/cycle-detected event when a cycle is found post-hoc.
2. **`if let Ok(stored)` fails open silently.** If `link_repo.list_all()` errors (e.g. pool exhaustion), the stored half of the graph is silently empty and the gate degrades to manifest-only with no log line — the same fail-open posture the gate family already had for unreadable manifests (`read_git_file` Err → `Ok(())`), so not a regression, but a `warn!` (as `replace_for_source` failures get in the sync) would make the degradation observable.
