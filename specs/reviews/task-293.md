## Findings

- [-] **F1 (missing enforcement / fail-open): `build_tenant_cycle_graph` silently skips the stored half when `list_all()` errors (spec_registry.rs:1760-1761).** `if let Ok(stored) = link_repo.list_all().await` — on a storage error (SQLite "database is locked" under concurrent receive-packs, pool/disk failure) the tenant half of the graph is silently dropped: no log, no rejection, and the gate degrades to exactly the pre-task-293 single-manifest scope. A cross-repo cycle is then accepted and, once the post-receive sync stores it, permanent. Probe reproduction: `fail_open_on_list_all_error_demonstrated` (table holds the A→B row, `list_all` errors, push of B→A returns `Ok(())`). The adjacent gate in the same function fails loud by explicit contract (task-264 signing gate: enumeration failure REJECTS the push, "never a silent pass"), and the repo's invariant philosophy treats "cannot determine state → state is fine" on a decision signal as a defect class. **Repair:** propagate the error so the push is rejected (and audited) when the graph cannot be read — or at minimum `warn!` and fail closed; a silent degradation re-opens the gap this task closes under exactly the failure conditions where durable state matters most.
- [-] **F2 (over-broad rejection / spec fidelity): `detect_graph_cycles` reports cycles the push did not create (spec_registry.rs:1828ff).** The BFS scans every node of the combined graph, including stored-only subgraphs the pushed manifest never touches, so a linkless manifest push to repo C is rejected whenever a stored A↔B cycle exists anywhere. The spec says the forge "rejects manifest changes that **would create** cycles" — a push creating nothing is not such a change. Probe reproduction: `legacy_stored_cycle_blocks_unrelated_repo_push`. Stored cycles are realistic on two counts: pre-gate legacy rows are the exact state this task's discovery evidence describes ("the cycle lives permanently in the forge-maintained graph"), and the ungated sync paths (`mirror_sync.rs:57`, `api/repos.rs:997`/`:1148`) store manifest edges into the durable graph without any cycle check, so mirror-synced cycles arise post-gate. Consequence: every manifest push in the deployment is blocked until someone pushes an edge-removing manifest to a participating repo — unrelated repos have no remedy. **Repair:** report only cycles in which at least one edge contributed by the pushed manifest participates (all three ACs hold under that scoping: the AC1 second push's B→A edge participates, single-manifest cycles participate, references/conflicts_with stay excluded); alternatively stand by the combined-graph reading and document/justify the legacy-cycle lockout (and its escape hatch) explicitly in the task and coverage evidence.

- The e2e test polls `wait_for_stored_link`/`wait_for_audit_event` with 30 s deadlines; the post-receive sync is spawned, so the assertion ordering (stored row before push 2) is correct — noted only because flaky-if-slow environments would surface as timeouts, not false passes.
