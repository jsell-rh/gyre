Findings:

- [ ] **F1 (major): migration 000054 uses SQLite-only `json_patch`/`json_object`/`json_extract`/`json_remove`, but the migrations directory is embedded and executed by BOTH storage backends — a PostgreSQL deployment now fails at startup.** `crates/gyre-adapters/src/postgres/mod.rs:54` embeds the same `migrations/` dir as `sqlite/mod.rs:58`, and `PgStorage::new_for_tenant` runs `run_pending_migrations(MIGRATIONS)` on every construction (`postgres/mod.rs:84`); `gyre-server/src/lib.rs:795-803` constructs `PgStorage` whenever `GYRE_DATABASE_URL` starts with `postgres://`, and `docs/server-config.md:45` documents PostgreSQL as a supported deployment ("all port traits persist via Diesel ORM with auto-migrations"). PostgreSQL has none of `json_patch`, `json_object('k', v)`, `json_extract`, `json_remove` as scalar SQL functions (`json_object` exists only as an aggregate form with different syntax; `jsonb_set`/`->`/`#-` are the PG equivalents). This task's up.sql (`json_patch(details, json_object('path', path, 'pid', pid))`) and down.sql (`json_extract`/`json_remove`) are the **first** JSON-function usage in the shared migration dir (verified by scanning all 55 migrations; the only prior non-portable constructs are `INSERT OR IGNORE` in 000013's down.sql and 000045 — also failures on PG, but 000054 is the first on the hot path of a fresh PG deployment, since 000013/45 only break their own statements). The adapter code itself (`postgres/audit.rs`) was correctly rewritten for the 14-column shape, so the PG code path is schema-blocked by the migration alone: a PG instance that has already applied earlier migrations dies at 000054 with a SQL function-not-found error; a fresh PG instance dies at 000001-era statements only in edge files, i.e. this task converts "PG support is mostly portable" into "PG support is broken by this migration". Spec scope says schema expansion must apply to the persistence layer, not only the SQLite dialect. Fix options: split per-backend migration dirs (diesel supports `embed_migrations!` with a backend-specific directory), or rewrite the fold using portable SQL (e.g. plain `CASE WHEN path IS NOT NULL THEN ... END` string concatenation, or per-backend SQL via `diesel::sql_query` guarded by backend), with PG `jsonb` equivalents. Note the renumber commit `f1340baf` reproduced the SQLite-only SQL verbatim into 000054, so the fix must land there.
- [ ] **F2 (moderate): `workspace_id`, `repo_id`, `resource_type`, `resource_id`, `session_id`, and `detail` in the recorded event are caller-supplied and unvalidated — the NEW-31 anti-forgery binding applied to `agent_id` is not applied to the scoping fields, so any authenticated agent can attribute its audit events to another workspace/repo or mislabel the resource.** `record_audit_event` (`api/audit.rs:146-161`) passes `req.workspace_id`/`req.repo_id` straight through (`Id::new` of an arbitrary string — no existence check, no comparison against the caller's own scope) and `resource_type`/`resource_id`/`detail` are free-form. This matters concretely because the new query API filters on exactly these dimensions (`GET /audit/events?workspace_id=...`): an agent in workspace A can (a) pollute workspace B's audit stream by naming B, and (b) after the fact, exfiltrate nothing but *corrupt* the compliance record — an investigator filtering by workspace B sees events that never happened in B, which is the audit-trail-integrity failure class the spec's envelope (and the repo's NEW-31 fix right above this code) is meant to prevent. The ABAC middleware maps `/api/v1/audit/events` to resource `audit` with no per-event workspace containment, so nothing downstream re-derives or checks scope. Minimum fix: for agent-token callers, reject or overwrite `workspace_id`/`repo_id` with the caller's authenticated scope (JWT claims carry `workspace_id`/`repo_id` per `auth.rs:66-70`); for user/API-key callers, validate that the named workspace exists and the caller has access. `resource_type` should at minimum be constrained to the spec's enumerated set ("agent", "task", "mr", "repo", "container", "process", …).
- [ ] **F3 (moderate): `source_ip` is taken from client-controlled `X-Forwarded-For`/`X-Real-Ip` headers with no trusted-proxy gate — the spec's compliance-relevant "who made this call" attribute is caller-forgeable, defeating the point of binding it.** `api/audit.rs:112-124` prefers `X-Forwarded-For` (first hop) then `X-Real-Ip`, unconditionally. A direct-connect client (the default deployment; nothing in `docs/server-config.md` configures or requires a reverse proxy, and there is no trusted-proxy list anywhere in the server) can set `X-Forwarded-For: <arbitrary>` and have it persisted as the event's `source_ip`, then forwarded to SIEM as `src=` in CEF and `source_ip` in syslog JSON — i.e. the two attributes the spec adds for forensic attribution (`source_ip`, `user_agent`) are both trivially spoofable, and `user_agent` doubly so. Given the same handler carefully binds `agent_id` server-side (NEW-31) specifically to prevent audit-trail forgery, persisting an unverified claim two lines later is inconsistent enforcement of the same principle. Fix: record the actual socket peer address (`ConnectInfo<SocketAddr>` extractor) as `source_ip`, and only honor forwarded headers when the immediate peer is a configured trusted proxy (e.g. `GYRE_TRUSTED_PROXIES` CIDR list, empty by default = always use peer address). This is the standard pattern; first-hop XFF without a proxy trust check is a known audit-forgery vector (CWE-348).
- [ ] **F4 (minor): query-time `user_id`/`workspace_id`/`resource_type` filters accept arbitrary strings with no existence or scope validation, and `outcome` filter deserialization returns an unstructured 400 on typo.** `QueryAuditParams.outcome: Option<AuditOutcome>` means `?outcome=succes` produces axum's generic `Query` rejection (400 with a serde message naming the field) rather than the repo's `ApiError` shape used by the other handlers — minor API consistency issue, since `?agent_id=` etc. silently succeed with zero results for nonexistent IDs while `?outcome=` fails loudly. Not a spec violation (spec only lists `?agent_id=&event_type=&since=` as required filters; the implementation superset-filters per the task's own acceptance criteria). Worth a small fix (map to the standard 400 error payload) but not blocking on its own.
