## Findings

- [-] **F1: Kubernetes backend creates Pods that cannot start in the normal flow — the Pod `workingDir` is the server's local worktree path.** The kubernetes dispatch arm (spawn.rs:944-952) passes `&spawn_config` into `KubernetesTarget::spawn_process`. `spawn_config.work_dir` is `effective_work_dir` (spawn.rs:598-605): the **canonicalized server-local worktree path** whenever the worktree exists on disk — which is the standard flow, because the server creates the worktree via `create_worktree` (spawn.rs:471-491) before dispatch. `build_pod_manifest` (kubernetes.rs:147) writes that path into the container's `workingDir`. The path does not exist inside the agent image and the Pod has no volume for it, so under the standard containerd/CRI runtime the container fails to start (runc `chdir` ENOENT → CrashLoopBackOff); even under lenient runtimes the cwd is wrong. The SSH-docker arm in the same function exists as the in-repo counterexample: it builds `ssh_spawn_config` with `work_dir: "/workspace"` with the comment "the remote container clones its own checkout into /workspace (entrypoint.sh), so /workspace is the workdir" — entrypoint.sh clones into `/workspace/repo` and `cd`s there regardless of cwd. The k8s arm forgot the same override. The kubernetes.rs unit tests never catch this because their `SpawnConfig` fixtures hardcode `work_dir: "/workspace"`, and no server-level test drives the k8s arm without kubectl. Acceptance criterion "Kubernetes backend creates/manages Pods" is met only nominally: Pods are created but the agent cannot run whenever a worktree exists. Fix: use a `/workspace` work_dir for the k8s arm (same as SSH container mode) and add a manifest-level test asserting the server worktree path never leaks into `workingDir`.

- [-] **F2: Spawn request-path `compute_target_id` is not validated against the caller's tenant — cross-tenant compute infrastructure use.** spawn.rs:360-373 resolves `req.compute_target_id` through the tenant-unscoped `ComputeTargetRepository::get_by_id` (all three adapters match on id only) with no comparison of the resolved entity's `tenant_id` to the workspace's/caller's tenant. Every sibling surface does enforce this: the workspace-binding path rejects cross-tenant with 400 (workspaces.rs:241-270, added by this task with tests), and the tenant-scoped CRUD handlers 404 on cross-tenant ids. A caller who learns another tenant's compute target id (UUIDs circulate in spawn responses, workload attestations, and audit/analytics events inside the owning tenant) can spawn an agent onto that tenant's SSH host, Kubernetes cluster, or container image config. The shipped notes' claim "Cross-tenant assignment is rejected (workspace update returns 4xx and spawn 404s on an unknown target id)" covers only *unknown* ids on the spawn path — an existing cross-tenant id is accepted and dispatched. The resolution block itself predates the diff (verbatim in base `6a9739e`), but it sits in this task's coverage section (§3 Tenant and Workspace Configuration: "Workspace selects ONE compute target from the tenant's list") and the new SSH-docker/Kubernetes dispatch arms were built directly on the unvalidated resolution. Fix: compare the resolved entity's tenant to the workspace tenant and return 404 on mismatch (same shape as the CRUD handlers); add a cross-tenant spawn rejection test mirroring `update_workspace_rejects_cross_tenant_compute_target`.

- [-] **F3: Nix reproducibility requirement not delivered — no `flake.lock` committed and the nixpkgs input is a moving branch.** Spec §3 Nix-Based Image Build lists `flake.lock # Pinned dependencies` in the required tree and states the flake "pins all dependencies … for bit-reproducible builds". The candidate commits `flake.nix` but no `flake.lock` (`git ls-files docker/gyre-agent/`), and the input is `nixpkgs.url = "github:NixOS/nixpkgs/nixos-24.11"` — a branch pointer that advances. Two `nix build .#agent-image` runs at different times resolve different nixpkgs revisions and produce different images, so the acceptance criterion "Nix flake for reproducible agent image builds" holds only nominally, and the image digests captured as `wl_image_hash` attestations are not stable across rebuilds. The flake's own comment concedes the lock is "created on first run" — it never was, or was not committed. Fix: generate and commit `flake.lock` (or pin the input to a specific revision). Note: `nix build` could not be exercised in this sandbox (no nix binary); the verifier should confirm the flake evaluates and builds.

- [-] **F4: `wl_image_hash` is never present in any issued JWT — spec/task-plan deviation, unamended.** Spec §3: "The image hash is recorded in workload attestation (`wl_image_hash` JWT claim)"; task plan item 7: "Image hash recorded in JWT claims (`wl_image_hash`)". `mint_with_workload` (auth.rs:189) accepts the claim but has no production caller passing a non-None value — the spawn path calls `mint` (spawn.rs:435), which forwards all-None workload claims, and the digest lands only in the KV workload-attestation record. No issued agent token carries `wl_image_hash` (nor `wl_pid`/`wl_container_id`), so the stated purpose of embedded claims — an external verifier reconstructing workload identity from the token alone (auth.rs:172-174) — is unmet for the image dimension. The shipped notes acknowledge the sequencing problem ("the spawn JWT is pre-minted before the digest is knowable") but the spec was not amended via spec lifecycle; per the repo's own rules the deviation should be either fixed (mint after dispatch, or re-mint and update `agent_tokens` once the digest is known) or spec-amended, not shipped as a silent reinterpretation.

- [-] **F5 (minor): `docs/api-reference.md` table broken by mid-table insertion.** The tenant-scoped compute-targets paragraph and its new table were inserted between rows of the admin-endpoints table (between `/api/v1/admin/compute-targets/{id}/tunnel/{tid}` and `/api/v1/admin/bcp/targets`, ~lines 268-281). The paragraph plus a new table header without blank-line separation splits the surrounding markdown table, orphaning the trailing `bcp/targets`, `bcp/drill`, and `scim/v2/ServiceProviderConfig` rows into a headerless fragment. Move the block below the table or separate with blank lines.

## Examined and cleared (so later rounds don't re-litigate)

- **Container backend security defaults** — `--network=none` (opt-in bridge), `--memory=2g`, `--pids-limit=512`, `--user=65534:65534` enforced at spawn time in `ContainerTarget` and identically in `SshDockerTarget::docker_run_args`; Pod-spec equivalents (runAsUser/Group 65534, runAsNonRoot, no privilege escalation, memory 2Gi) with tested overrides; worktree volume mount on the local container path.
- **SSH remote-command injection** — every remote argv element passes through `shell_quote` (single-quote escaping); hostile-image-tag test asserts the metacharacters stay inside one quoted argument; ssh uses BatchMode + bounded ConnectTimeout (≤15s asserted by test).
- **Workspace binding** — existence + same-tenant validation, explicit-null clearing via `deserialize_present` (present null ≠ absent field, tested), no partial application on rejection, 409 on delete-referenced-by-workspace with real mem-mode visibility through the shared workspace store (previously a hardcoded `false`).
- **Tenant-scoped CRUD + ABAC** — handlers are tenant-scoped and admin-gated; resolver entries added and the two stale exemption-file entries removed with `FROZEN_EXEMPTION_COUNT` correctly lowered 53→51; duplicate baseline restored to 22 (`check-abac-route-registry.sh` EXIT 0 re-run by reviewer).
