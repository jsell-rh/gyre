## Verified

- **Message too large (413).** `api_router` (api/mod.rs) reads `GYRE_MAX_MESSAGE_SIZE` (default 64 KiB, same silent-fallback parse convention as the pre-existing `GYRE_MAX_BODY_SIZE`) and layers `DefaultBodyLimit::max` on the send route's method router (api/mod.rs:864-867). The limit covers the TOTAL request body (full JSON envelope); the `Json` extractor rejects with 413 before the handler runs, so nothing is signed, stored, or broadcast. The route-level layer is inner to `build_router`'s global 10 MB layer, so it takes precedence — and the new integration test asserts 413 for a 65 KB body through the full `build_router` (global layer included), making the verifier's test run the empirical precedence probe on the lockfile's axum 0.7.9. Route path literal unchanged on its own line, so the ABAC route-registry extraction still matches.
- **Signature key rotation.** Durable KV entry `agent_signing_key_history` (`server_identity` namespace) retains `{kid, public_key_b64}` — public material only; the private slot and task-107 F12 semantics are untouched (task107_signing_key_env.rs asserts the private slot only, and still holds). Every DB-backed boot records its active key (idempotent by kid); the `GYRE_AGENT_SIGNING_KEY` rotation path additionally folds the pre-rotation current-slot key so pre-feature deployments keep their old kid resolvable on first rotated boot; rotation chains accumulate. `GET /.well-known/jwks.json` (oidc.rs) serves the history minus the active kid, deduped — unchanged document when no rotation has occurred (m18 shape preserved). Load path skips malformed entries and kid/public-key mismatches with warnings. Both SQLite and PostgreSQL adapters expose the `kv_*_sync` accessors used.
- **The new test binary is genuine, not self-confirming.** `reconstruct_sign_input` matches production `sign_bus_message` (lib.rs:587) field for field (Server origin for global-token callers via `origin_from_auth`; payload hash over the identical compact serialization of the same `Value` the server signed; `MessageKind::as_str()` == serde wire form; u64 `created_at`; `{"agent": id}` externally-tagged `Destination`). The test's K2 kid derivation equals `derive_kid` (SHA-256[..16] hex). Verification uses real ring `UnparsedPublicKey::verify` with wrong-key negative controls in both directions; post-rotation messages are asserted to carry `key_id == kid2`. The size tests pin the inclusive boundary (exactly 65536 → 201, 65537 → 413), assert no store (`count_unacked == 0`) and no broadcast frame on 413, and prove the send path works by storing the at-limit message; `GYRE_MAX_MESSAGE_SIZE=2048` override is exercised. Against the base code these tests fail (201 vs 413; missing old kid), so they close the gap rather than mirror it. All imports/dev-deps have precedent in committed test binaries (message_persistence.rs uses the identical import line).

## Non-blocking observation

The 64 KB limit is scoped to the REST send endpoint, exactly as the task contract and the spec row ("Total POST request body") specify. The MCP `gyre_message_send` tool wraps the same send path but arrives via the MCP endpoint under the global 10 MB limit, so a >64 KB message can still be created through MCP. Not a defect against this task; worth a future spec clarification if MCP parity is desired.
