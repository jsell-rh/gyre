## Blocking finding (round 1)

**Field type references are not clickable — and the displayed annotation is the field name, not the type — against real extractor data.** `findFieldTypeNode()` (`model.js`) and the field row in `MoldableTypeView.svelte` use `field.qualified_name.split('::').pop()`. Every extractor stores field nodes as `qualified_name = "Parent::field_name"` with the **type annotation in `doc_comment`** (`rust_extractor.rs:1030-1076`, `go_extractor.rs:401-408`, `typescript_extractor.rs:483-501`, `python_extractor.rs:448-460`), and the graph carries the exact field→type linkage via **DependsOn edges** (`rust_extractor.rs:1058-1076`) plus the FieldOf edge to the parent — none of which the view uses. Probe with real-convention data (field `status`, `qualified_name: 'domain::Task::status'`, `doc_comment: 'TaskStatus'`, DependsOn edge to the `TaskStatus` type node): the row renders `field status : status` and no `.field-type-clickable` element exists (evidence: `review-evidence/field-type-probe-output.txt`, probe source kept alongside). This violates the twice-stated spec requirement "Every field type is clickable → navigates to that type" and the acceptance criterion "All type references are clickable (navigate to that type's view)" for every tree-sitter-extracted repo. The shipped test (`MoldableViews.test.js`, "makes field types clickable") passes only because its fixture invents `qualified_name: 'domain::TaskStatus'` for a field named `status` — a convention no extractor produces (the pre-existing `ExplorerCanvasDrillDown.test.js:111` fixture uses the real `Parent.field` form) — making that test self-confirming against a fictional data shape. The logic was carried over verbatim from the base `NodeDetailPanel` (task-178), but this task's contract explicitly claims the criterion and ships the proving test. Fix: resolve the field's type from `doc_comment` and/or the DependsOn/FieldOf edge targets (which point at the real type nodes) instead of `qualified_name`'s last segment, and use a realistic fixture.

## Non-blocking observations (recorded for the verifier / future tasks)

- **Spec-path prefix tolerance**: `GET /api/v1/specs/:path` (`api/specs.rs:365`) does an exact `find_by_path` with no `specs/`-prefix tolerance, while sibling endpoints strip it (`api/spec_assertions.rs:148`, `api/specs_assist.rs:171`). When a graph node's `spec_path` carries the `specs/` prefix (extractor fixtures do; `realized-model.md` §139 documents the unprefixed `// spec: search.md` form), `MoldableSpecView`'s content fetch 404s and falls back to the extracted preview. Pre-existing (the base's `openSpecEditor(detailNode.spec_path)` flow behaves identically) and the view degrades gracefully; flagging the server-side inconsistency for a follow-up, not this task.
- **Trait View methods/dependents data availability**: the Rust pipeline creates no nodes for trait methods ("methods have no nodes" — `call_graph_rust.rs:293-299`; `rust_extractor.rs` `Item::Trait` emits no method nodes or trait→method Contains edges), so Methods/Dependents render empty for Rust repos. The view logic is correct given the edges and degrades gracefully; this is an extraction-layer data gap, not a view defect.
