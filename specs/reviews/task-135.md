Findings:

- [**F1 (major): optional (`required = false`) RequiredApprovals gates block merging indefinitely — the §Gate Chains "optional gates don't block merging" acceptance criterion is not met.** In `check_gates_for_mr` (`crates/gyre-server/src/gate_executor.rs`, the RequiredApprovals live-recheck branch, ~lines 1710-1745), the early `return Ok(false)` for a Pending/Running approvals gate never consults the `is_required` flag computed directly above it. `run_required_approvals_gate` has no failure mode (only Passed/Running), so an advisory approvals gate short of its minimum never reaches a terminal state: `check_gates_for_mr` returns `Ok(false)` every cycle, the merge processor requeues the MR forever ("gates still running — skip, try next candidate"), and the MR can neither merge nor fail. The branch's own comment ("advisory approval gates wait too") documents reinterpreting the spec instead of implementing it. Reproduction: configure a chain with `[[gates]] name = "peer-approval" type = "RequiredApprovals" min_approvals = 5 required = false` plus one passing required gate, enqueue an MR with no approvals — the MR is stuck in the queue forever. Runtime probe saved at `/tmp/stage/review-evidence/probe_task135_check_gates.rs` (`probe_advisory_approvals_gate_must_not_block_merge` asserts the spec behavior and fails on the candidate). **Repair:** in the live-recheck branch, treat advisory approvals gates like every other advisory Pending/Running gate — record the result but don't wait (`if !is_required { continue; }` before the waiting return), and make the waiting return conditional on `is_required`.
- [**F2 (medium, corollary of F1): the approvals live-recheck early-return masks failed required gates — the author is never blocked/notified.** The `return Ok(false)` fires per-result before the loop examines later results, so any Pending/Running RequiredApprovals gate that precedes a Failed required gate in the result list turns "required gate failed → Err → entry failed + author notified" into "waiting → requeue forever". On SQLite/PG `list_by_mr_id` has no ORDER BY (rowid/insertion order = chain order, since `trigger_gates_for_mr` creates results in chain order), so a chain `[peer-approval, tests]` with `tests` failing deterministically masks the failure in production. Spec: "If any required gate fails, the MR is blocked and the author agent is notified with the failure details." (The Pending/Running-before-Failed masking pattern for *required* gates pre-exists at base; this candidate newly extends it to the advisory case, which at base did not wait.) **Repair:** scan all results for required failures first (Err takes precedence), then decide waiting/readiness — e.g. collect states across the loop instead of early-returning per result.

Worth either filtering the chain replace to PreMerge gates or adding `gate_phase` to the chain format.

New documentation should not repeat it.
