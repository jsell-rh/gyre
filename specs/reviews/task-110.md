## Minor observations (non-blocking, recorded for follow-up)

- `InvitationPolicy.allow_re_invite` is accepted and echoed by `PUT /api/v1/tenant/invitations/policy` but never consulted: re-invite after a terminal status always creates a fresh invitation. The spec's normative bullets under §Invitation Expiry describe re-invite-after-expiry unconditionally and the task's configurability list names only the three knobs that ARE enforced (both expiry days, max pending), so this is not a contract violation — but a settable flag with no effect is a latent trap; a future round should either enforce it (reject re-invite when false) or drop it from the API surface.
- Migration 000056's header comment describes unique constraints on (tenant, email) / (workspace, user) and a partial index that the SQL does not contain — pending-uniqueness is actually enforced in adapter code (read-then-insert). Under concurrent identical invites the check can race and produce two pending rows (mild: distinct tokens, each single-use). Comment should match the SQL; a partial unique index would make the comment true.
- Pre-existing at base, not from this change: `workspace_memberships` is mem-wired even in DB-backed mode (`build_state`, lib.rs:1053), so activated memberships do not survive a restart when `GYRE_DATABASE_URL` is set — identical for the pre-existing M22.8 member endpoints. My SQLite probe confirmed the full invitation flow works on the real backend and the invitation rows themselves persist (`store!`-wired); only the membership store is mem-only. Worth its own upstream task.
- Coverage rows for the four task sections remain `task-assigned` in `specs/coverage/system/user-management.md` — consistent with the task-199 precedent (rows flip outside the implementing task); no `not-started` rows were introduced.
- No TCP listener is bindable in this sandbox, so no live-server smoke ran; the full routing + extractor + handler chain was exercised in-process (shipped tests + my SQLite probe), and the live HTTP surface remains covered by CI at the PR head.
