## Required behavior

Per meta-spec-reconciliation.md §1, meta-specs get the same SHA-pinned versioning, approval flow, and link graph as regular specs, with per-kind approval modes. REGISTRY-MODEL BASELINE (review-feedback correction, matching the revision-2 audit): agent-runtime.md §2 'DB-backed, not repo-backed' explicitly supersedes §1's git-backed registry semantics ('This supersedes the git-backed meta-spec model from meta-spec-reconciliation.md §1'), and its amendments-table row repeats 'Reconciliation spec defers to this for registry semantics'. The existing DB registry (meta_specs + meta_spec_versions tables, content-addressable SHA-256 hashes, immutable version history, DB-API-only writes) IS the amended model; accordingly the manifest-driven registration surface (yaml manifest declaring meta-specs, the auto_reconcile flag, meta-specs 'appearing in the spec registry alongside implementation specs') is SUPERSEDED, not a deliverable: do NOT build a manifest-to-registry bridge, do NOT add a manifest auto_reconcile flag, and leave SpecEntry.kind as vestigial declaration metadata. What remains missing against the amended model (the audit's three live sub-gaps): (1) Per-kind approval modes enforced BY KIND — today update_meta_spec_registry applies caller-supplied approval_status verbatim for every kind (meta_specs.rs:9171-9183 has no kind-conditional branch; kind is read only for event payloads and task titles). meta:persona, meta:principle, meta:process are human_only — only human principals may approve; meta:standard is human_and_agent with DUAL-approval semantics mirroring the spec-registry's resolve_approval_status (spec_registry.rs:301-326): the entry reaches approval_status Approved only when at least one valid human approval AND at least one valid agent approval of the SAME content (SHA-matched, approver-type-discriminated approval events) are recorded; a lone agent approval leaves the entry Pending exactly as a lone human approval does; Rejected remains a direct transition. Approval becomes event-based: the update path records typed approval events (approver_type human|agent, approved content hash) and derives approval_status per kind instead of assigning the caller's string verbatim; a single human PUT {approval_status: 'Approved'} on a human_only kind must remain observably identical to today (shipped UI flow preserved), and the existing reconciliation trigger on Approved (required-flag / approval handler) must fire exactly when the DERIVED status becomes Approved, never on a lone half-approval. (2) Agent admission — the human_and_agent mode must be REACHABLE without granting agents general registry write access: a kind-conditional widening of the approval step ONLY. An agent principal (UserRole::Agent) may record an approval event on a meta:standard entry; agent principals remain forbidden from every other registry mutation (content/name/scope/required writes → 403 with RBAC denied recorded, exactly as authorize_registry_write enforces today) and from approving human_only kinds (403). (3) Repo scope — parse_scope accepts Repo (scope_id = repo id) with the same containment rigor as Workspace scope (repo must exist and belong to the caller's tenant; writer must be tenant Admin or the repo's workspace Owner/Admin; cross-tenant writes 403); agent-runtime.md §2 preserves PersonaScope Repo as nearest-scope-wins overrides that 'cannot be marked required', so required=true on a Repo-scoped entry is rejected; scope-enum widening goes through a dialect-portable migration (both SQLite and PostgreSQL, per check-migration-sql-portability.sh) using the next unused sequence number. (4) Link-graph participation — meta-spec registry entries participate in the spec link graph: links may reference meta-specs as endpoints pinned to the meta-spec's content_hash, under the same SHA-pinning rule task-286 enforces for spec links (no link enters or stays without a target SHA); meta-spec links are listable via the links surface (e.g. GET /api/v1/meta-specs/:id/links); every new route gets an ABAC RouteResourceMapping entry (AGENTS.md route-registry invariant — unregistered routes get no policy evaluation). COORDINATION: task-286 (active, spec-links SHA pinning) reshapes the link store this task extends — build on its result, do not modify its contract. task-302 (active, bindings-registry-cascade) reshapes the consumers of the same PUT /api/v1/meta-specs/:id approval path this task makes kind-conditional (required-flag reconciliation trigger, meta_specs_used drift basis) — compose with its result: the dual-approval derivation and the required-flag trigger must work together (trigger fires on derived Approved), and this task must not reintroduce retired set stores.

## Acceptance Criteria

- [ ] Tenant Admin PUT {approval_status: 'Approved'} on a meta:persona → Approved (human_only behavior unchanged); the same PUT on a freshly edited meta:standard with no agent approval recorded → approval_status stays Pending (dual approval unmet) with the human approval event recorded and SHA-stamped.
- [ ] An agent principal records an approval on that meta:standard → with the human half present the entry becomes Approved and the existing reconciliation trigger fires for required entries; the same agent principal PUT {approval_status: 'Approved'} on a meta:persona → 403; the same agent principal PUT {prompt: '<new content>'} (content write) on the meta:standard → 403 — the widening covers the approval step of meta:standard only.
- [ ] parse_scope('Repo') is accepted with scope_id containment enforced: an Admin of another tenant cannot write a Repo-scoped entry for the target repo (403); required=true on a Repo-scoped entry is rejected (agent-runtime.md: repo-scoped entries cannot be marked required).
- [ ] A link whose endpoint is a meta-spec pins that meta-spec's content_hash; a meta-spec link without a target SHA is rejected; links are listable per meta-spec via an ABAC-mapped route (scripts/check-abac-route-registry.sh stays green with no new exemptions).

## Verification intent

Arm 1 (missing kind discrimination — use a principal that passes the write gate, not a role-gate 403): as tenant Admin, edit a meta:standard's content then PUT {approval_status: 'Approved'}; GET must show approval_status Pending because no valid agent approval of the same content_hash exists. At the base this fails: the Admin's PUT flips the entry to Approved verbatim (meta_specs.rs:9171-9183 applies the caller's status for every kind — no kind-conditional branch exists anywhere in the update path). Arm 2 (unreachable human_and_agent): an agent principal PUT {approval_status: 'Approved'} on a meta:standard must record the agent approval half; at the base the same PUT returns 403 from authorize_registry_write's role gate before any kind discrimination runs — the defect it leaves exposed is that NO code path admits an agent principal to any approval transition, so the specced dual mode can never complete; after the change the same PUT succeeds on meta:standard while the same principal's {prompt} PUT and any approval PUT on human_only kinds still 403. Arm 3 (Repo scope absent): declaring a Repo-scoped meta-spec must succeed and required=true on it must be rejected; at the base parse_scope rejects Repo outright ('invalid scope; must be one of: Global, Tenant, Workspace', meta_specs.rs:8653) so the repo tier cannot even be declared.
