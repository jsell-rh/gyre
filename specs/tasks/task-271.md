## Required behavior

Per specs/development/agent-workflow.md §Fix the Environment, Not the Agent: when an agent hits an error the first response is never 'try again' — the root cause is diagnosed and the environment engineered (lint rule, pre-commit hook, better error message, test fixture) before the retry, with an interrupt ledger recording every error as a signal so recurring classes are structurally fixed once. Today the Phase 7 fail path (ralph_loop.rs) closes the MR and re-spawns the agent with an identical environment (same gates, hooks, tooling), the protocol prompt says 'fix, commit, push, complete again', and no error ledger exists anywhere ('interrupt ledger' appears only in the spec file). Implement: (1) Interrupt ledger — a new gyre-ports trait (e.g. interrupt_ledger.rs: create, find_by_class/recurring queries, record hardening action, list by task/repo) implemented by the SQLite adapter (next unused migration sequence number — current latest is 000066), the PostgreSQL adapter, and the mem adapter with every port failure constraint guarded identically in all adapters (scripts/check-mem-port-contracts.sh), wired into AppState via the existing store! pattern (scripts/check-in-memory-state-stores.sh — no bare Arc<Mutex<HashMap>>). Entry: tenant/workspace/repo/task/agent ids, error class signature (normalized identity of the failure: failing gate id/type plus a failure fingerprint such as the gate command and exit code / leading failure output — stable across iterations of the same class), iteration, occurred_at. DB-backed so it survives restart. (2) Recording — on the Phase 7 gate-failure path (and the agent fail path), write a ledger entry with the computed class signature before the respawn decision. (3) Environment-first enforcement — before re-spawn, query the ledger for the class signature's occurrence count for the task; if the class has recurred (>= 2 occurrences, threshold configurable) with NO recorded hardening action for that class, do NOT re-spawn: transition the task to Blocked with a reason naming the recurring error class and its evidence, and create a priority-1 escalation notification to workspace admins requiring an environment fix — this is the enforcement that makes 'first response is never try again' real. (4) Hardening record — a scoped API/MCP surface (e.g. POST environment-hardenings / a gyre_record_environment_hardening MCP tool) recording {class signature, description, evidence (commit SHA, added gate/lint rule/hook, improved error message, test fixture), recorded_by}; new routes get ABAC RouteResourceMapping entries (scripts/check-abac-route-registry.sh), per-handler scoped authorization where exempt (scripts/check-abac-exempt-handlers.sh), and scope fields derived from the caller (scripts/check-forged-scope-fields.sh). Once a hardening record exists for the class, respawn proceeds. (5) Respawn context — when respawn is allowed, the new agent's failure context (inbox/system://context messages) must lead with the diagnosis directive: identify the root cause and engineer the environment to catch/prevent that error class (lint rule, hook, better error message, test fixture) as part of the fix, before retrying. (6) Protocol prompt — amend the on-gate-failure instruction in crates/gyre-server/src/api/prompts.rs from 'fix, commit, push, complete again' to require root-cause diagnosis and environment hardening before the retry, per this canonical spec section. A ledger that is written but never gates the respawn decision is audit-only theater and does not satisfy this task.

## Acceptance Criteria

- [ ] Ledger persistence and content: a gate failure on a Ralph-loop agent writes a ledger entry carrying the task/agent/repo scope, iteration, and a class signature that is identical across two failures of the same gate with the same failure mode (and different for a different gate/failure mode); entries remain readable after a server restart.
- [ ] Environment-first gate: a class that has failed twice on one task with no hardening record produces, on the next failure, NO re-spawn — the task is Blocked with a reason naming the recurring class, a priority-1 escalation notification to workspace admins exists, and the agent's iteration count is not incremented further.
- [ ] Hardening unblocks: after recording a hardening action for the class (with description and evidence), a subsequent failure re-spawns the agent, and the respawned agent's failure context leads with the diagnose-and-harden-the-environment directive.
- [ ] Adapters: the port's failure constraints are enforced identically in the SQLite, PostgreSQL, and mem adapters (scripts/check-mem-port-contracts.sh passes with no new exemptions), and AppState wiring uses the store! pattern (scripts/check-in-memory-state-stores.sh).
- [ ] The hardening-record endpoint/tool enforces caller scoping: a caller outside the entry's workspace cannot create or read another workspace's hardening records (Forbidden).

## Verification intent

Configure a repo whose test gate fails deterministically with the same output signature, let the loop iterate past the recurrence threshold with no hardening record, then probe: assert the agent was NOT re-spawned again (no new active session, iteration frozen, task Blocked, escalation notification present). The real defect this must catch: the current tree re-spawns unconditionally on every failure until max_iterations with an environment that never changes — on the current tree the probe finds iteration still climbing and no escalation, and fails. Second probe killing the audit-only hollow version: comment out the respawn gate (ledger written but decision unchanged) — the same probe must fail, proving the ledger result actually gates the decision rather than merely recording it.
