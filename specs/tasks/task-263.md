## Required behavior

Complete the Layer-2 token contract and enforce the hard security boundary, per the Task-Scoped JWT Claims reference table and Layer 2. Mint side — every agent JWT from POST /api/v1/agents/spawn (and the orchestrator/gate mints where the fact is known) carries: sub as 'agent:<uuid>' (not the bare UUID), iss = server base URL, aud = 'gyre' (or GYRE_OIDC_AUDIENCE if set), exp/iat with default TTL 3600 s via GYRE_AGENT_JWT_TTL (the current 300 s default is an undocumented-in-spec M27.5 deviation; restore the spec default), jti (already minted), task_id, spawned_by, persona populated from the spawn request's validated persona/persona_slug (today unconditionally None even though the request carries and validates a persona through resolve_persona_in_chain), stack_hash AND its wl_stack_hash alias populated with the real SHA-256 stack fingerprint from the workload attestation record (today every production mint passes None, leaving the spec-registry stack-pinning consumer with a dead enforcement input — spec_registry.rs compares event.stack_hash against a pinned requirement that can never match), attestation_level (already derived from compute-target type), and wl_pid/wl_hostname/wl_compute_target/wl_container_id/wl_image_hash populated from the real spawn-time facts whenever those facts exist (only wl_image_hash is resolved today). Validation side — enable audience validation for self-minted agent tokens (validate_aud with the configured audience; AgentJwtClaims currently has no aud field and sets validate_aud=false), keeping federated-issuer validation behavior correct. Enforcement side — task-scoping as a hard boundary, closed by a BY-EFFECT enumeration: sweep every REST and MCP handler whose execution mutates task rows, task-scoped secrets, or creates task-linked MRs — never by route-family enumeration or illustrative subset — and give each surface found either an enforced agent-principal task-scope check or an explicit, justified out-of-scope statement recorded in the task text. The sweep necessarily includes, beyond any further surfaces discovered during implementation, the following (all verified at this base): (1) REST task mutation: PUT /api/v1/tasks/:id (update_task, crates/gyre-server/src/api/tasks.rs:277 — mutates title, description, priority, assigned_to with generation bump, branch, pr_link, labels) and PUT /api/v1/tasks/:id/status (transition_task_status, tasks.rs:323); both currently take NO auth extractor at all (State/Path/Json only, governed only by ABAC middleware tier scoping); both must take an auth extractor and reject agent principals whose task_id claim does not match the target task with 403. (2) REST agent lifecycle that mutates task-owned state: POST /api/v1/agents/:id/complete (complete_agent, crates/gyre-server/src/api/spawn.rs:2632) takes NO auth extractor, yet create_mr_for_completion transitions the target agent's task to Review (spawn.rs:2581-2591) and opens the task's completion MR; the route maps to RouteResourceMapping ('agent', 'complete') and the seeded builtin 'agent-scoped-access' (priority 700) ALLOWS the 'complete' action for Agent-role subjects on resource type '*', so an agent JWT spawned for task A can complete task B's agent — transitioning task B and opening its MR — under DEFAULT configuration (the MCP twin already enforces self-only completion for agent JWTs, mcp.rs:5006-5010; the REST handler has no equivalent check). The handler must take an auth extractor and, for agent principals, enforce the same boundary the MCP twin enforces: an agent JWT may only complete its own agent / a task covered by its task_id claim. (3) POST /api/v1/agents/:id/stop (spawn.rs:2928) and POST /api/v1/agents/:id/fail (spawn.rs:3067): both take NO auth extractor and sit in the frozen ABAC route-registry exemption file (scripts/abac-route-registry-exemptions.txt), so NO middleware ABAC and NO per-handler authorization governs them at all; both terminate the target agent and revoke the target task's Task-scoped secrets via secret_rotation::revoke_agent_task_secrets. They must take an auth extractor (per-handler authorization is mandated for ABAC-exempt routes by the standing invariants) and, for agent principals, be restricted to the caller's own agent — an agent may terminate itself, never another task's workload or secrets. (4) POST /api/v1/agents/spawn (spawn_agent_core reassigns task.assigned_to, bumps the generation, and auto-advances Backlog→InProgress, spawn.rs:1206-1215): currently contained only by the absence of 'spawn' from the Agent-role builtin allow — policy default, not code. For agent principals, spawning onto a target task must be authorized by the token's own claims — the target task matching the caller's task_id claim, or the token carrying an explicit spawn scope covering the task's repo/workspace (the same claim-level right the MCP gyre_spawn_worker path already validates via validate_tool_scope) — 403 otherwise, so the task-claim boundary holds regardless of policy configuration. (5) MCP task-mutation surface, wherever an agent principal can be the caller, covers BOTH tools dispatched behind the tier-only check_task_target arm (mcp.rs, gyre_update_task/gyre_decompose_spec scope validation resolves the task's repo/workspace tier and never compares the task_id claim): gyre_update_task (handle_update_task — must reach the handler's full mutation set title/description/priority/assigned_to/branch/pr_link/status, not a subset) and gyre_decompose_spec (mutates the parent task's subtask linkage via parent_task_id); each must compare the caller's task_id claim against the target (or parent) task and return PERMISSION_DENIED on mismatch. (6) Repo/MR boundary per the same spec paragraph: (b) write to a repo it was not assigned — git push authorization (git_http.rs authorize_repo_access currently returns Ok for every principal with user_id.is_none()) must require agent principals to hold the target repo in their token's scope list; (c) open MRs outside its task scope — MR creation (MCP gyre_create_mr and the REST path) must check the task_id claim, not only repo scope. Human/system/orchestrator principals keep their existing rights; the new checks target agent task-scoping. Revocation side — wire the existing dead jti-keyed revocation table into production: on successful POST /api/v1/agents/{id}/complete write the token's jti (token hash) via SpawnLogRepository::revoke_token (implemented in SQLite and Postgres adapters, currently never called from any production path), check is_token_revoked during agent-token validation before the expiry check, return 401 for revoked jti, and make revocation persist across restarts (the current KV map-removal may remain for lookup but the jti table is the durable record); tokens cannot be un-revoked.

## Acceptance Criteria

- [ ] Decoding a spawn-minted agent JWT shows sub='agent:<uuid>', aud matching 'gyre'/GYRE_OIDC_AUDIENCE, jti, task_id, spawned_by, persona when a persona was requested at spawn, stack_hash and wl_stack_hash equal to the stored workload-attestation stack fingerprint, attestation_level, and wl_pid/wl_hostname/wl_compute_target/wl_container_id whenever the corresponding spawn fact is known; default TTL is 3600 s.
- [ ] A valid, non-expired agent JWT spawned for task A gets 403 (or MCP PERMISSION_DENIED) on: PUT /api/v1/tasks/:id for task B (content update of title/description/priority/assigned_to/branch/pr_link/labels — not only the status transition), task-status transition of task B, gyre_update_task on task B, gyre_decompose_spec targeting task B as parent — and a git push to a repo not in its token's repo scope is rejected for the agent principal, as is MR creation outside its task scope.
- [ ] A valid, non-expired agent JWT spawned for task A gets 403 on POST /api/v1/agents/{task-B-agent-id}/complete, with task B NOT transitioned to Review and no completion MR created; the same boundary holds for POST /api/v1/agents/:id/stop and /fail against another task's agent (target agent status unchanged, its Task-scoped secrets not revoked), and for POST /api/v1/agents/spawn onto task B when the caller's token carries neither a matching task_id claim nor a spawn scope covering task B's repo/workspace.
- [ ] A token minted with a wrong/absent aud fails agent-token validation (audience validation is live, not disabled).
- [ ] After POST /api/v1/agents/{id}/complete, a request replaying the same jti receives 401 even though exp is in the future; the revocation is present in the SQL revoked_tokens table, survives a server restart, and revocation lookup precedes expiry validation.
- [ ] The spec-registry stack-pinning path is exercisable end-to-end: an approval event carrying the JWT-embedded stack hash matches a pinned requirement of the same hash and fails to match a different pinned hash.
- [ ] Non-agent principals (users, orchestrators, system) are not locked out of the task/repo/MR/agent-lifecycle surfaces they could previously use — enforcement is scoped to agent task-boundaries; any by-effect surface left unenforced carries an explicit, justified out-of-scope statement in the task text.

## Verification intent

Spawn an agent for task A with a valid, non-expired JWT and call, against task B or task B's agent: PUT /api/v1/tasks/:id (content update), PUT /api/v1/tasks/:id/status, MCP gyre_update_task, MCP gyre_decompose_spec with parent_task_id = B, POST /api/v1/agents/{task-B-agent}/complete, POST /api/v1/agents/{task-B-agent}/stop, POST /api/v1/agents/{task-B-agent}/fail, and POST /api/v1/agents/spawn onto task B without a covering spawn scope; also push to an unrelated repo and open an MR for another task: every call must be rejected. Against current code ALL of these succeed: update_task, transition_task_status, complete_agent, stop_agent, and fail_agent take no auth extractor at all (complete is additionally reachable under DEFAULT configuration because the seeded 'agent-scoped-access' builtin allows the 'complete' action for Agent-role subjects on resource type '*'), spawn is contained only by ABAC policy default, the MCP task tools are tier-only (check_task_target never compares the task_id claim), and the push succeeds (authorize_repo_access returns Ok for any user_id.is_none() principal) — so the probe fails on pre-task code, proving the boundary is enforced per-call by a by-effect sweep of every task-mutating surface rather than by tier-level ABAC alone, by route-family enumeration, or by illustrative subset. Second probe: complete the agent, then replay a request with its token while exp is still future — must 401 via the jti revocation table (today only a KV map removal happens and the SQL table is dead code).

Update the relevant coverage rows only after implementing the behavior, with concrete source evidence. Do not mark unrelated rows complete or claim independent verification before it occurs.

### Layer 2 mint completion

`AgentJwtClaims` (auth.rs) carries `aud` and `stack_hash` (alias of `wl_stack_hash`); every mint path sets `sub` = `agent:<uuid>`, `aud` ('gyre', or GYRE_OIDC_AUDIENCE via the `AgentSigningKey` audience wired in lib.rs), and both stack-hash spellings from the same fingerprint. Self-minted agent-token validation enforces the audience (`validation.set_audience`); federated-issuer validation (remote Gyre instances, Keycloak user JWTs) is untouched. Default `GYRE_AGENT_JWT_TTL` restored to the specced 3600 s (lib.rs, docs/server-config.md).

`wl_hostname` is the hostname of the COMPUTE TARGET (identity-security.md claims table), resolved per target on both mint paths (`spawn_agent_core`, `relaunch_agent_session`): Ssh target → the configured remote host (`e.config["host"]`); Kubernetes → honestly absent (no single host fact exists at mint time); local/Container → `read_hostname()` (the workload runs on this machine, so the forge hostname IS the compute-target hostname). Repair `356184ee` restored the Ssh arm that merge `07d01c55` had silently dropped (the mint had regressed to the forge server's own hostname for every spawn, including remote SSH targets). `wl_pid`/`wl_container_id` are not minted (post-launch facts — minting them would fabricate them); they are recorded in the fresh workload-attestation record immediately post-launch.

Proven by `spawn_minted_jwt_carries_task_scoped_claims` (sub/aud/jti/task_id/spawned_by/persona/attestation_level + mint == stored workload-attestation stack fingerprint), `respawn_mint_carries_stored_stack_fingerprint`, and `ssh_spawn_mints_configured_remote_host_as_wl_hostname` (Ssh target with configured host "worker-box" → decoded JWT asserts `wl_hostname == Some("worker-box")`, killing the forge-hostname regression; the suite was previously blind to it — the auth.rs unit test passed the value straight into the mint and the claims route test used a Container target).

### Stack-hash mechanism (merge rounds 07d01c55 / 050ef5e0)

The rebase onto current main merged this task with task-261's Layer-1 SPIFFE workload attestation. The mint-side stack hash uses main's `spiffe::resolve_session_stack_evidence` — resolved ONCE per spawn/re-spawn, the SAME value bound to the JWT `wl_stack_hash`/`stack_hash` claims, the session X.509-SVID, and the launch-written workload-attestation record. EVERY mint — first spawn included — carries the stored workload-attestation stack fingerprint, so the spec-registry stack-pinning consumer's input is live on every agent session.

### Revocation

`agent_audit.rs` `revoke_agent_token` writes the token's jti to the durable `revoked_tokens` SQL table (`SpawnLogRepository::revoke_token`; SQLite + Postgres adapters) in addition to the KV removal. `auth.rs` `jti_revocation_denial` checks `is_token_revoked` BEFORE signature/expiry validation on both the REST extractor and the WebSocket path, returning 401. Proven by the boundary test: after self-completion, replaying the same jti gets 401 with exp in the future, and `state.spawn_log.is_token_revoked(jti)` is true.

### By-effect sweep

Swept by execution effect (mutates task rows, task-scoped secrets, or creates task-linked MRs), not by route family. Enforced surfaces: `PUT /api/v1/tasks/:id` and `/status` (`require_task_claim`, tasks.rs), `POST /api/v1/tasks` (agent callers' scope fields clamped to signed claims), `POST /api/v1/agents/:id/complete` (self-or-task-claim, mirroring the MCP twin), `stop`/`fail` (self-only + tenant containment — the routes are ABAC-registry-exempt, per-handler authorization now present), `POST /api/v1/agents/spawn` (own-task claim or explicit repo/workspace spawn scope), `PUT /api/v1/agents/:id/status` (self-or-task-claim), MCP `gyre_update_task`/`gyre_decompose_spec` (task_id claim compared against target/parent task, PERMISSION_DENIED on mismatch), MCP `gyre_create_task`/`gyre_create_mr` and REST `POST /api/v1/merge-requests` (task-claim boundary), git push (`authorize_repo_access` requires `repo:{name}:write` or a covering workspace scope for agent principals), `POST /api/v1/repos/:id/archive`, compose apply/teardown (task-bound agents denied), and the admin control surfaces (`deny_task_bound_agent` in api/admin.rs): `POST /api/v1/admin/agents/:id/kill`, `POST /api/v1/admin/agents/:id/reassign`, `POST /api/v1/admin/jobs/:name/run`, `POST /api/v1/admin/restore`, and `POST /api/v1/admin/seed`. Human/system/orchestrator principals keep their existing rights (`agent_task_claim()` is `None` for them; the admin boundary test proves the operator kill still works under the same permissive policy).

Other task-mutating surfaces verified as already enforced or unreachable for agent principals: `POST /api/v1/specs/:path/reject` denies Agent-role principals in-handler; MCP `gyre_cross_repo_task` requires a workspace-orchestrator token; `POST /api/v1/repos/:id/graph/thorough-preview` funnels through `spawn_agent_core`, whose task-claim gate rejects agent principals spawning onto its freshly created (uncovered) task.

### Out-of-scope statements (justified)

- **`wl_pid`/`wl_container_id` at mint time**: these facts do not exist until launch completes; minting them would fabricate them. They are recorded in the fresh workload-attestation record immediately post-launch.
- **MCP `gyre_agent_complete`**: already enforced self-only for agent JWTs pre-task — unchanged.
- **Admin snapshot create/delete and BCP drill** (`POST /api/v1/admin/snapshots`, `DELETE /api/v1/admin/snapshots/:id`, `POST /api/v1/admin/bcp/drill`): read-only capture of task state (or deletion of a backup file) — no task row, task-scoped secret, or MR is mutated; the state-replacing effect is `admin_restore_snapshot`, which is gated.
- **`PUT /api/v1/admin/retention`**: mutates retention configuration only; the purge effect runs through the job registry, whose manual trigger (`admin_run_job`) is gated and whose scheduled runs are system-initiated, not agent-callable.
